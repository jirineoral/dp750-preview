Create and organize objects in Unity Catalog

Catalogs, schemas, tables, views, volumes, foreign catalogs, and AI/BI Genie
🗂 Organizing objects in Unity Catalog

Chapter objectives

  • Design consistent naming conventions and use the three-level namespace catalog.schema.object
  • Create a catalog and a schema including managed storage location and workspace bindings
  • Tell managed and external tables apart, and create views, materialized views, and volumes
  • Perform DDL operations — SQL/Python functions, procedures, ALTER, and governance tags
  • Connect an external database through a foreign catalog (Lakehouse Federation) and configure AI/BI Genie instructions
3.1

The three-level namespace and naming conventions

Everything you create in Unity Catalog lives in a three-level namespace: catalog.schema.object. Above these three levels sits the metastore — one per region, shared by all workspaces in that region. You do not create a metastore for every project; it is the roof under which you build your catalogs.

Before you start creating anything, agree on your naming conventions. Unity Catalog has a few hard rules that make the decisions easier:

RuleDetail
Name lengthmax. 255 characters
Letter caseobject names are stored as lowercase; SalesData = salesdata
Forbidden charactersdot, space, slash, control characters (the dot separates namespace levels)
Special characterspossible with backticks, e.g. `sales-data` — avoid them in practice
Columnskeep the case you enter, queries are case-insensitive

The recommended pattern is lowercase with underscores (customer_data, sales_summary) — camelCase gets converted to lowercase anyway and only creates confusion. Prefix views with vw_ and temporary staging tables with tmp_. Align schema names with the layers of the medallion architecture: bronze, silver, gold — then everyone can tell at a glance what they are holding when they see sales_data.gold.monthly_revenue.

For catalogs you decide between two strategies: by domain (sales_data, finance_data) or by environment (dev, test, prod). The combination {domain}_{environment} — that is, sales_dev, sales_prod — scales best, but the number of catalogs grows, so you need discipline in managing them.

💡
Tip: conventions that are not enforced do not last long. Restrict the CREATE TABLE/CREATE SCHEMA privileges to specific teams, validate names in the CI/CD pipeline, and regularly hunt for inconsistencies with a query against information_schema.
ℹ️
Note: versioning does not belong in a name — sales_final_report_v1_updated is a classic antipattern. Version and status belong in metadata (comments, tags), not in the identifier.

3.2

Creating a catalog

A catalog is the top-level container and the primary unit of data isolation: every catalog can have its own storage location, security boundary, and access policies. To create one you need to be a metastore admin or hold the CREATE CATALOG privilege. Every new catalog automatically gets two schemas: default and information_schema.

SQL
-- catalog with dedicated managed storage
CREATE CATALOG IF NOT EXISTS prod_catalog
MANAGED LOCATION 'abfss://prod-data@mystorageaccount.dfs.core.windows.net/catalog-root'
COMMENT 'Production catalog with dedicated ADLS Gen2 storage';

IF NOT EXISTS makes the script idempotent — you can run it repeatedly without an error.

In the UI: Catalog in the left navigation → Create catalog → name plus the Standard type → optionally a managed storage location → Create. After creating it, set the workspace bindings — by default a new catalog is visible from all workspaces attached to the metastore. Restrict a production catalog to the production workspace only.

The managed storage location determines where Unity Catalog physically stores the files of managed tables and volumes in the catalog. Without it, managed objects fall back to the metastore's default storage — and if the metastore has no default, MANAGED LOCATION is mandatory when creating the catalog. To set it you need an existing external location and the CREATE MANAGED STORAGE privilege.

⚠️
Caution: a catalog being visible from all workspaces by default is a common operational foul. A dev workspace that "sees" prod_catalog is one bad USE CATALOG away from an incident. Set the workspace bindings right after creating the catalog.
💡
Tip: dedicated managed storage per catalog also solves compliance — it keeps sensitive data in the storage account and region that match the regulatory requirements, and physically isolates it from the other catalogs.
3.3

Creating a schema

A schema is the second namespace level and organizes data inside a catalog into logical units — typically one use case, project, or team. In Databricks you will also come across the term "database": CREATE DATABASE is an alias for CREATE SCHEMA, they are the same thing. To create one you need USE CATALOG and CREATE SCHEMA on the parent catalog.

SQL
CREATE SCHEMA IF NOT EXISTS prod_catalog.customer_analytics
COMMENT 'Customer behavior and segmentation analysis';

-- schema with its own storage (e.g. finance for compliance reasons)
CREATE SCHEMA IF NOT EXISTS prod_catalog.financial_data
MANAGED LOCATION 'abfss://finance@mystorageaccount.dfs.core.windows.net/schema-data';

Three proven patterns for organizing schemas:

PatternExampleWhen to use
By departmentmarketing_analytics, financial_databusiness units own their data
By projectcustomer_churn_model, pricing_optimizationtemporary initiatives, easy clean-up once the project ends
By processing stagebronze, silver, goldmedallion pipeline, the most common one in data engineering

Managed storage at the schema level is optional — if you do not specify it, managed tables use the catalog's storage (or the metastore's). So the fallback hierarchy is: schema → catalog → metastore.

ℹ️
Note: for a user to see a schema at all and query its contents, they need at least USE SCHEMA (plus USE CATALOG on the catalog). The chapter on securing Unity Catalog covers privileges in detail.
3.4

Tables and views

Managed vs. external tables

A managed table is the default: Databricks manages both the metadata and the data files, the format is Delta Lake (ACID transactions, time travel, schema enforcement), and DROP TABLE deletes both metadata and data. An external table only registers metadata over data in external storage — DROP removes just the registration in the catalog, the files stay.

SQL
-- managed table (default, Delta Lake format)
CREATE TABLE production.sales.sales_transactions (
  transaction_id BIGINT,
  customer_id INT,
  amount DECIMAL(10,2),
  transaction_date DATE
);

-- external table over existing CSV files
CREATE EXTERNAL TABLE production.sales.archived_sales
USING CSV
LOCATION 'abfss://container@storage.dfs.core.windows.net/sales/archive'
OPTIONS (header 'true', inferSchema 'true');

Primary and foreign keys

Unity Catalog can define PRIMARY KEY and FOREIGN KEY constraints — but watch out for expectations carried over from classic databases:

A common misconception: PK/FK constraints enforce integrity▼

Anyone expecting a PRIMARY KEY in Databricks to block duplicate rows will be surprised. PK/FK constraints are informational only — they are not enforced on write. From the documentation: "these constraints are informational only and are not enforced." They serve as metadata documenting the data model, for the query optimizer (better join strategies), and for tools such as AI/BI Genie, which derive join relationships from them. Data quality is enforced only by NOT NULL and CHECK constraints.

SQL
CREATE TABLE customers (
  customer_id BIGINT NOT NULL,
  customer_name STRING,
  CONSTRAINT customers_pk PRIMARY KEY (customer_id)
);

CREATE TABLE orders (
  order_id BIGINT NOT NULL PRIMARY KEY,
  customer_id BIGINT,
  total_amount DECIMAL(10,2),
  CONSTRAINT orders_customers_fk FOREIGN KEY (customer_id)
    REFERENCES customers(customer_id)
);

Views: standard, dynamic, materialized

TypeDataWhen to use
Viewstores nothing, the query runs on every accessencapsulating logic, always current data
Dynamic viewlike a view + row filtering / column maskingaccess control per user (is_account_group_member())
Materialized viewprecomputed results in a Delta tableexpensive aggregations, dashboards, slight staleness acceptable
SQL
-- dynamic view: masking a column by group
CREATE VIEW sales_redacted AS
SELECT user_id,
  CASE WHEN is_account_group_member('auditors') THEN email
       ELSE 'REDACTED' END AS email,
  product, total
FROM sales_raw;

-- materialized view with a scheduled refresh
CREATE MATERIALIZED VIEW daily_sales_summary
SCHEDULE EVERY 1 DAY
AS SELECT transaction_date,
  COUNT(*) AS transaction_count,
  SUM(amount) AS total_sales
FROM sales_transactions
GROUP BY transaction_date;

Materialized views support incremental refresh — they process only the changed data. The condition is that the source Delta tables have row tracking enabled (delta.enableRowTracking = true). Enabling it on a large existing table takes a while, upgrades the table protocol, and is irreversible.

Materialized view vs. streaming table — which one when?▼

A streaming table (CREATE OR REFRESH STREAMING TABLE) processes only the new rows since the last refresh — streaming semantics, exactly-once. It suits incremental ingestion (Auto Loader over cloud storage, Kafka) and bronze/silver layers where data is only appended. A materialized view, by contrast, computes aggregations over the complete dataset with batch semantics. Rule of thumb: the source only appends and keeps no history (Kafka) → streaming table; an aggregation over the whole with periodic recomputation → materialized view. The chapter on ingestion covers streaming tables in detail.

⚠️
Caution: dynamic views require a SQL warehouse or compute with standard/dedicated access mode (for dedicated, on Databricks Runtime 15.4 LTS+). On an older runtime a query through a dynamic view will not run.
💡
Tip: instead of classic partitioning, use liquid clustering (CLUSTER BY) for tables as well as materialized views — the data layout is optimized automatically according to the queries and there is no risk of skewed partitions.

3.5

Volumes: governance for files

A volume is a Unity Catalog object for non-tabular data — CSVs for ingestion, images, audio, ML models. It sits at the third namespace level (catalog.schema.volume) and brings the same governance model you know from tables to files.

Just as with tables, you choose managed (Unity Catalog handles both storage and lifecycle; after a drop the files are marked for deletion after the retention period) or external (the files sit at a path you specify and a drop removes only the registration). Use an external volume when systems outside Databricks access the files too, or when you are adding governance on top of existing storage.

SQL
-- managed volume
CREATE VOLUME IF NOT EXISTS dev_catalog.bronze_schema.landing_files
COMMENT 'Landing area for CSV files from external systems';

-- external volume over existing storage
CREATE EXTERNAL VOLUME prod_catalog.silver_schema.ml_models
LOCATION 'abfss://models@mystorageaccount.dfs.core.windows.net/production/';

-- permissions: read and write for a group
GRANT READ VOLUME, WRITE VOLUME ON VOLUME dev_catalog.bronze_schema.landing_files
TO `data-engineers`;

You access files through the uniform POSIX-style path /Volumes/<catalog>/<schema>/<volume>/<path> — it works in Spark, pandas, SQL, and dbutils.fs, with no credentials or connection strings:

PYTHON
# the same path for Spark and pandas
df = spark.read.format("csv").load("/Volumes/dev_catalog/bronze_schema/landing_files/data.csv")

import pandas as pd
pdf = pd.read_csv("/Volumes/dev_catalog/bronze_schema/landing_files/data.csv")

# file management
dbutils.fs.ls("/Volumes/dev_catalog/bronze_schema/landing_files")
⚠️
Caution: volumes do not support ACLs at the subdirectory level — privileges always apply to the whole volume. If you need different rights for different sets of files, create a separate volume for each security boundary.
ℹ️
Note: READ VOLUME alone is not enough to read a file — the user also needs USE CATALOG and USE SCHEMA on the parent objects. Privileges in the hierarchy are always evaluated from the top down.

3.6

DDL operations: functions, procedures, ALTER, and tags

Functions as governed objects

Functions in Unity Catalog are not just syntactic sugar — they are governed objects with an owner, privileges, and usage tracking. You define them once and call them from anywhere, so a discount calculation or a grade classification is consistent across the whole organization. Both scalar and table-valued functions are supported, in SQL or Python:

SQL
-- SQL scalar function
CREATE FUNCTION dev_catalog.finance_schema.calculate_discount(price DOUBLE, discount_rate DOUBLE)
RETURNS DOUBLE
RETURN price * (1 - discount_rate);

-- Python function (runs on serverless / pro SQL warehouse)
CREATE FUNCTION dev_catalog.analytics_schema.normalize_text(input_text STRING)
RETURNS STRING
LANGUAGE PYTHON
AS $$
  return input_text.lower().strip() if input_text else None
$$;

-- table-valued function
CREATE FUNCTION dev_catalog.utils_schema.split_to_rows(input_array ARRAY<STRING>)
RETURNS TABLE(value STRING)
RETURN SELECT explode(input_array) AS value;

For multi-step workflows (validation → transformation → load) there are SQL stored procedures — CREATE PROCEDURE with IN/OUT/INOUT parameters, variables, and flow control, invoked through CALL. They require Databricks Runtime 17.0+; verify the exact support status in the documentation.

ALTER: ownership, tags, structure

SQL
-- transfer catalog ownership to a group
ALTER CATALOG dev_catalog SET OWNER TO `data_engineering_team`;

-- governance tags for classification and discoverability
-- both the tag name and the value must be string literals
ALTER CATALOG dev_catalog SET TAGS (
  'environment' = 'development',
  'cost_center' = 'engineering',
  'data_classification' = 'internal'
);

-- structural changes to a table without a rebuild
ALTER TABLE dev_catalog.sales_schema.orders
ADD COLUMN shipping_carrier STRING COMMENT 'Name of the shipping carrier';

ALTER TABLE dev_catalog.sales_schema.orders
ALTER COLUMN quantity TYPE BIGINT;

ALTER TABLE handles adding, renaming, and dropping columns and widening types (INT → BIGINT) while preserving the data — it requires the MODIFY privilege. Type widening works on Delta tables from Databricks Runtime 15.2 up; if the type should widen automatically already during ingestion, enable delta.enableTypeWidening on the table. Verify the supported type pairs and the exact feature status in the documentation. Renaming a column requires Delta column mapping to be enabled. Tags are searchable metadata: the basis for data classification, cost management, and later automated governance.

💡
Tip: ALTER CATALOG prod_catalog ENABLE PREDICTIVE OPTIMIZATION turns on automatic maintenance (compaction, vacuum) for every table in the catalog — tables inherit the setting unless they override it at their own level.

3.7

Foreign catalogs and Lakehouse Federation

Not all of your data is in the lakehouse — and not all of it needs to be moved there. Lakehouse Federation makes it possible to query external databases (PostgreSQL, MySQL, Azure SQL, Snowflake, BigQuery…) directly from Databricks, with Unity Catalog controlling access, auditing, and tracking lineage. Ideal for ad-hoc analysis over live operational data, a proof of concept without ETL, and gradual migration.

The architecture rests on two objects: a connection holds the technical connection details (JDBC host, port, credentials — ideally through Databricks secrets) and a foreign catalog mirrors a specific external database into the Unity Catalog namespace. One connection can serve several foreign catalogs (several databases on the same server).

SQL
-- 1) connection: credentials through Databricks secrets, not in plaintext
CREATE CONNECTION postgresql_prod TYPE postgresql
OPTIONS (
  host 'prod-db.example.com',
  port '5432',
  user secret ('prod-secrets','postgres-user'),
  password secret ('prod-secrets','postgres-password')
);

-- 2) foreign catalog mirroring the customers database
CREATE FOREIGN CATALOG IF NOT EXISTS prod_customer_data
USING CONNECTION postgresql_prod
OPTIONS (database 'customers');

-- 3) query it like an ordinary Unity Catalog table
SELECT customer_id, SUM(transaction_amount) AS total_spent
FROM prod_customer_data.public.transactions
GROUP BY customer_id;

Metadata is synchronized automatically on every query. With high-frequency queries this can be slow — in that case refresh the metadata on a schedule through REFRESH FOREIGN CATALOG / SCHEMA / TABLE (for example from Lakeflow Jobs) and queries will run against the cache.

⚠️
Caution: the query executes on the compute of the external database. A federated dashboard that aggregates a production PostgreSQL every few minutes is an excellent way to make an enemy of the operations DBA team. Cache frequently queried external data locally through a materialized view instead.
ℹ️
Note: the privileges you need: CREATE CONNECTION on the metastore for the connection; CREATE CATALOG on the metastore plus ownership of the connection (or CREATE FOREIGN CATALOG on it) for the foreign catalog. Federated access is primarily read-only — verify the write options in the current documentation for the specific system.

3.8

AI/BI Genie instructions

AI/BI Genie lets business users ask about data in natural language — Genie turns the question into SQL over Unity Catalog tables. To generate the right SQL it needs context: that is what the knowledge store of a Genie Agent object (formerly a Genie space) is for, where you adjust metadata at the agent's level without changing the underlying objects in the catalog.

You build a Genie Agent over a selection of tables (max. 25, and it is recommended to start with five or fewer). Then you layer context on top:

ToolWhat it is for
Table and column descriptionsbusiness language instead of technical ("contains all customer purchases…"), synonyms for columns
Hiding columnsget surrogate keys and audit columns out of the way — they confuse users and the model alike
Joinsrelationships between tables including cardinality; Genie loads PK/FK from Unity Catalog by itself
Prompt matchingsamples of real values — "California" gets mapped to the code "CA"
SQL expressionsreusable measures/filters/dimensions (gross margin, fiscal quarter)
Example SQL queriessample questions with ready-made SQL; parameterized ones are marked as Trusted
Text instructionsglobal rules ("the fiscal year starts in February") — use sparingly

This is where the honest work from the previous sections pays off: the PK/FK constraints from section 3.4, descriptive comments, and consistent names are mined automatically by Genie when a Genie Agent is created (knowledge mining) and stored as join relationships. A well-annotated catalog means less manual configuration.

Configuring Genie is an iterative process: test the Genie Agent with your own questions, use Show generated code to check the generated SQL, fix wrong answers and save them as a new instruction (Add as instruction). Keep an eye on user feedback in the Monitoring tab and measure accuracy with benchmark questions.

Genie Agent limits (state per the Learn module, verify in the documentation)▼

A Genie Agent has two separate limits: an instructions limit of 100 (example SQL queries, SQL functions, and the whole block of text instructions together) and a knowledge store snippets limit of 200 (table descriptions, join relationships, and SQL expressions together). Entity matching handles up to 1,024 distinct values per column across 120 columns of a single agent. Column descriptions and prompt matching do not count towards the limits. The limits may change — verify the current values in the documentation.

💡
Tip: start minimal — few tables, few instructions — and expand according to the questions users actually ask. An overloaded Genie Agent with dozens of generic text instructions answers worse than a small, precisely aimed one.
