12.1

Git folders: version control right in the workspace

Git folders (formerly known as Repos) bring a visual Git client and API into the Azure Databricks workspace. You clone repositories, create branches, commit, and push straight from the workspace — with no switching to external tools. The supported providers: Azure DevOps, GitHub, GitLab, and Bitbucket.

You create a Git folder through Workspace → Create → Git folder: enter the repository URL, the provider, and a folder name. Once cloned, the repository contents appear in the workspace and you can work with notebooks, Python files, and SQL scripts right away.

💡
Tip: every team member should have their own Git folder connected to the shared repository. When several people share one folder, one user switching branches changes the contents for everyone — a source of very hard-to-debug "mysteries".

Always pull before starting work — regularly pulling changes minimizes integration conflicts. Be aware that a pull changing a notebook's source code resets its state: cell outputs, comments, and the notebook version are cleared to match the new content.

Keeping the repository tidy means: a .gitignore for temporary outputs, credentials, and environment-specific configuration (it applies to already tracked files only after they are explicitly removed from Git), a logical folder structure, and deleting the old branch at the provider after a merge — local branches survive up to 30 days after the remote branch is deleted.

Git folder limits and sparse checkout▼

A working branch is limited to 1 GB and Databricks recommends keeping the number of assets under 20,000 (verify the exact current limits in the documentation). For a large monorepo use sparse checkout — you clone only the directories you actually need.

12.2

Branching, pull requests, and conflicts

A feature branch isolates work in progress from the main branch. In the Git dialog (the button with the branch name next to the notebook) you choose Create branch, name it, and typically create it from main. Consistent naming pays off:

PatternUse
feature/feature-namenew functionality
bugfix/problem-descriptionbug fixes
users/name/descriptionpersonal experiments
⚠️
Caution: switching branches can delete workspace assets the target branch does not contain — shared or bookmarked notebooks suddenly disappear. Uncommitted changes are carried over to the new branch on switch if they do not conflict; discard beforehand whatever you do not want carried over.

You commit from the Git dialog: the UI highlights the changed files, shows a visual diff, you write a descriptive commit message and hit Commit & Push. A pull request is then created and reviewed in the Git provider's interface — Databricks provides the Git operations, code review lives at the provider. You typically cannot commit directly into a protected main; you go through a feature branch and a PR.

Merge conflicts arise when several people change the same lines. The Git folders UI offers a list of conflicting files and three routes: Keep all current changes, Take all incoming changes, or editing the file by hand with the conflict markers (<<<<<<< HEAD … ======= … >>>>>>>) and Mark As Resolved. Then Continue Merge/Continue Rebase — or Abort if you got it wrong.

Notebook outputs and file formats▼

For notebooks in source formats (.py, .sql, .scala, .r) cell outputs are not included in commits — the repository holds clean code and the diffs are readable. If you do need to version the outputs, use the IPYNB format. For a data engineering pipeline the source format is almost always the better choice.

12.3

Testing strategy: the pyramid, pytest, integration

A good testing strategy follows the testing pyramid: many fast unit tests at the bottom, fewer integration tests in the middle, and a handful of end-to-end tests and UAT scenarios at the top.

Unit tests test individual functions in isolation. The key Databricks recommendation: keep transformation logic in .py modules outside notebooks and import it into the notebooks — it is then easy to test with standard pytest. Name the test files test_*.py or *_test.py:

PYTHON
import pytest
import pandas as pd
from transforms import filter_country_region

@pytest.fixture
def sample_data():
    # synthetic data with the structure of production - no sensitive data
    return pd.DataFrame({
        "iso_code": ["USA", "USA", "CAN", "GBR"],
        "value": [100, 200, 150, 175],
    })

def test_filter_default(sample_data):
    result = filter_country_region(sample_data)
    assert len(result) == 2
    assert all(result.iso_code == "USA")

The @pytest.fixture fixture supplies reusable synthetic data — you test the structure and the logic, not production content. You can also run the tests directly in a notebook:

PYTHON
%pip install pytest

import pytest, sys
sys.dont_write_bytecode = True   # no cache on a read-only filesystem

retcode = pytest.main(["tests/", "-v", "-p", "no:cacheprovider"])
assert retcode == 0, "Tests failed - check the output above"
💡
Tip: design functions with a predictable return type. A function returning "a DataFrame or False" tests terribly — let it always return a DataFrame, even an empty one.
Test typeVerifiesScopeSpeed
Unitindividual functionsa function/class, synthetic datamilliseconds
Integrationcomponents working togetherseveral components, a test catalogseconds
End-to-endthe whole workflowa complete pipelineminutes
UATbusiness requirementsbusiness scenarios, stagingdepends on the scenario

Integration tests run against real Databricks resources — they read a test table, run a transformation, and verify the schema and types of the output. Create a dedicated test catalog/schema for them with a representative sample of data. End-to-end tests simulate a whole daily run (set up inputs → run the pipeline → assert on the output table → clean up); run them in the deployment pipeline or off-peak, not on every commit. UAT then means: acceptance criteria agreed with stakeholders in advance, a staging environment mirroring production, and prepared scenarios (a notebook reconciling monthly revenue against the financial system, say).

⚠️
Caution: never run integration or e2e tests against production tables. An isolated test environment with the structure of production but without sensitive data is a necessary condition — not a nice-to-have.

12.4

Declarative Automation Bundles: configuration and packaging

Declarative Automation Bundles — formerly known as Databricks Asset Bundles (DAB); older materials and slides use the original name — are the infrastructure-as-code approach to deploying Databricks resources. You describe jobs, pipelines, and other resources in YAML files and then deploy the same definition declaratively to dev, staging, and production. From the documentation: "Declarative Automation Bundles (formerly known as Databricks Asset Bundles)".

The foundation is the databricks.yml file in the project root:

YAML
bundle:
  name: order-processing

include:
  - resources/*.yml      # splitting the configuration across several files

variables:
  environment:
    description: Environment name
    default: development

resources:
  jobs:
    etl_pipeline:
      name: ${var.environment}-order-pipeline
      tasks:
        - task_key: extract
          notebook_task:
            notebook_path: ./notebooks/extract.py
        - task_key: transform
          depends_on:
            - task_key: extract
          notebook_task:
            notebook_path: ./notebooks/transform.py

The bundle mapping defines the project identity, resources the objects to deploy (most often jobs with tasks, dependencies through depends_on, and parameters through base_parameters), and include pulls in further YAML files. State paths relative to the bundle root. Variables with ${var.name} substitution replace hardcoded values — they can be filled from a default, a per-target override, the CLI option --var="key=value", or an environment variable prefixed with BUNDLE_VAR_.

Targets represent deployment environments. The modes are essential: mode: development prefixes resource names with [dev user], pauses all schedules, and allows concurrent runs — a dev deployment does not step on production. mode: production, by contrast, validates that the Git branch matches and recommends deploying through a service principal:

YAML
targets:
  dev:
    default: true
    mode: development
    variables:
      environment: development
  staging:
    presets:                       # fine tuning without a full mode
      name_prefix: staging_
      trigger_pause_status: PAUSED
  prod:
    mode: production
    workspace:
      host: https://adb-prod.azuredatabricks.net
    variables:
      environment: production
Bundle configuration in Python (Public Preview)▼

Besides YAML, a bundle can also be defined as Python code — you describe jobs and resources programmatically. At the time of writing this is Public Preview and YAML remains the most common route; verify the current state in the documentation.

12.5

Deploying a bundle through the Databricks CLI

Deployment is driven by the Databricks CLI in four steps: validate, preview, deploy, verify. During a deploy the CLI stores state in the workspace — it knows what it created, and on the next deployment it updates resources, adds new ones, and deletes those that disappeared from the configuration.

BASH
# authenticate against the workspace
databricks auth login --host https://adb-1234567890123456.7.azuredatabricks.net

databricks bundle validate            # check the syntax and configuration
databricks bundle plan                # preview: what will be created / changed / deleted
databricks bundle deploy -t dev       # deploy to the dev target
databricks bundle summary             # overview of deployed resources + URLs
databricks bundle open etl_pipeline   # opens the resource in the browser

# production in CI/CD: without interactive confirmations
databricks bundle deploy -t prod --auto-approve
CommandWhat it does
bundle validatechecks the syntax, prints the bundle identity (name, target, workspace, path)
bundle planshows the planned actions (create/update/delete) without making changes
bundle deployuploads the artifacts and creates/updates the resources in the target (-t)
bundle summarylists the deployed resources with direct links into the UI
bundle run / bundle destroyruns a job from the bundle / removes the deployed resources
⚠️
Caution: the deployment identity = the bundle name + the target + the identity of the deploying user. When every team member deploys into a shared environment under their own identity, conflicting parallel deployments appear. Agree on who (ideally which service principal) deploys into shared targets.

The most common snags: authentication errors (fixed by databricks auth login), a lock conflict after an interrupted deployment (--force-lock), jobs from the bundle running at the moment of deployment (the behavior is governed by --fail-on-active-runs), and warnings about unknown properties — usually an old CLI version against a newer schema.

✓
Summary: the whole lifecycle fits together: the code lives in Git folders (12.1), changes go through a feature branch and a PR (12.2), CI runs the pytest tests (12.3), and after the merge the pipeline deploys the same bundle first to dev and then to prod (12.4–12.5). No manual clicking of job configuration in production — everything is in the repository. Orchestration of the jobs themselves is covered in chapter 11.
