Chapter objectives

  • Design an access control strategy using the privilege model, permission inheritance, and groups from Microsoft Entra ID.

4.1

Query lifecycle: how Unity Catalog evaluates a query

Before we start handing out permissions, we need to understand what actually happens when a user runs a query against a table governed by Unity Catalog. Unity Catalog acts as the control plane for security and governance: every query goes through a permission check, is written to the audit log, and only then does the compute get short-lived access to the data.

Anyone expecting the cluster to "just read files from storage" will be surprised — the compute never receives permanent storage credentials. It only gets a scoped temporary access token valid for specific objects in a specific query.

The whole cycle has eight steps:

1) Query submission — a principal (user, group, or service principal) runs a query from a notebook on an all-purpose cluster, from a job on a job cluster, through a Databricks SQL warehouse, or from a connected BI tool. 2) Validation in Unity Catalog — the compute passes the request to Unity Catalog, which writes it to the audit log and verifies permissions on every object in the query. Denials are logged too. 3) Taking over the cloud credential — for each object Unity Catalog takes over the relevant cloud credential (the metastore storage for managed tables, the storage credential of the given external location for external objects). 4) Issuing scoped tokens — Unity Catalog generates a short-lived token and a secured URL for each object. 5–6) Data access — the compute reads directly from the ADLS Gen2 endpoints (abfss://). 7) Fine-grained filtering — row filters and column masks are evaluated on the compute, so every principal sees only their own subset of the data. 8) Returning the result to the caller.

⚠️
Caution: if the storage account has a firewall or VNet rules enabled, you must explicitly allow access for the access connector / managed identity. Even a valid token will be rejected when the storage account's network rules do not let the identity through.
How a query through the legacy Hive metastore differs▼

A workspace attached to Unity Catalog sees the old Hive metastore as a special catalog named hive_metastore. A query over a Hive table works differently, though: the cluster checks access through table ACLs, gets only the storage path from the metastore, and has to authenticate on its own — through a service principal, credential passthrough, or an instance profile that an administrator must configure in advance (often including mount points and secrets).

There is no central issuing of scoped tokens and no integrated auditing. From the documentation: "Hive metastore table access control is a legacy data governance model." — do not use it for new projects.

4.2

Access control strategy: the privilege model and inheritance

Access control in Unity Catalog rests on four complementary mechanisms:

MechanismApplies toUse
Privileges and ownershipcatalogs, schemas, tablesbasic access — who may do what
ABAC (tags + policies)tagged objects across catalogscentral policies (see chapter 5)
Row filters / column masksindividual tablesfiltering and masking through UDFs
Workspace bindingscatalogs, external locations, storage credentialsrestriction to specific workspaces

The foundation is the privilege model: a grant says who (principal) may perform which action (privilege — SELECT, MODIFY, CREATE TABLE…) on which object (securable). Securables form a hierarchy metastore → catalog → schema → table/view, and permissions are inherited downwards from the higher levels.

The key rule that trips up most beginners: SELECT on a table is not enough on its own. The principal has to make it along the whole path — USE CATALOG on the catalog, USE SCHEMA on the schema, and only then SELECT on the table. If any link is missing, the query fails.

Grants are issued with standard ANSI SQL (DCL), from a notebook, the SQL editor, or through the Permissions tab in Catalog Explorer:

SQL
-- the path to a table: catalog -> schema -> table
GRANT USE CATALOG ON CATALOG sales TO `analysts`;
GRANT USE SCHEMA ON SCHEMA sales.finance TO `analysts`;
GRANT SELECT ON TABLE sales.finance.orders TO `analysts`;

-- the inheritance variant: SELECT at the schema level
GRANT SELECT ON SCHEMA sales.finance TO `analysts`;

-- the right to create tables in the schema
GRANT CREATE TABLE ON SCHEMA sales.finance TO `analysts`;

-- revoking a permission
REVOKE SELECT ON TABLE sales.finance.orders FROM `analysts`;

Check the result with SHOW GRANTS:

SQL
SHOW GRANTS ON TABLE sales.finance.orders;
SHOW GRANTS `analysts` ON SCHEMA sales.finance;
⚠️
Caution: SHOW GRANTS on a table may not show permissions inherited from the schema or the catalog. For the full picture, check grants at every level of the hierarchy.
💡
Tip: grant to groups, not individuals. Identities (users, groups, service principals) are managed in Microsoft Entra ID and synchronized into the Databricks account — Unity Catalog does not support workspace-local groups. The built-in principal account users represents every user in the account.
ℹ️
Note: ALL PRIVILEGES grants every applicable privilege on the object — including privileges Databricks adds in the future. A metastore is bound to a region: a workspace can only be attached to a metastore in the same Azure region, and always to at most one.

4.3

Fine-grained access control: below the table level

The grants from the previous section work on an "all of the table or nothing" basis. In practice, though, you often need to show different groups only some of the rows or masked column values from one canonical table — regional data only to regional teams, PII only to the compliance team. Duplicating tables for each audience is the road to hell: copies go stale, synchronization costs orchestration, and security rules drift apart.

Unity Catalog offers two manual approaches to fine-grained access control:

DimensionRow and column securityDynamic views
Where the logic livesdirectly on the table (UDF)in the view definition
Number of objectsthe table + a couple of functionsa view for each audience
Combining several tablesno — a single table onlyyes, joins across several tables
Writing datareads and writes with the rules applied (on dedicated compute, writes only from DBR 16.3+)the view is read-only
Abstraction from the sourcethe table structure is visiblethe consumer does not see the source table

Row and column security (row filters + column masks) is the preferred modern approach: the rules are attached to the table metadata, apply everywhere the table is used, and no "zoo" of derived views appears. Dynamic views are the older pattern, which still makes sense when you need to combine data from several tables, create an explicit contract between producer and consumer, or shield consumers from the existence of the source tables entirely.

⚠️
Caution: writes into a table with a row filter or a column mask have their own requirements on dedicated compute — they are supported from Databricks Runtime 16.3 up, while on DBR 15.4–16.2 only reads work. On top of that, MERGE does not support tables whose filters or masks contain nested constructs, aggregations, window functions, LIMIT, or non-deterministic functions. And one more practical trap: time travel does not work over a table with a row filter or a column mask — a TIMESTAMP AS OF / VERSION AS OF query fails, even though chapter 6 otherwise recommends time travel. Verify the exact support status in the documentation.
ℹ️
Note: both approaches are manual and per-table. A third option is ABAC — central policies bound to governed tags, applied automatically to every tagged table in a schema or catalog. Databricks recommends it for most scenarios today; we cover it in chapter 5 (section 5.2).
Common mistakes when designing fine-grained security▼

Duplicating tables for each audience — leads to out-of-sync copies and governance chaos. Dozens of nearly identical views instead of one generalized masking function — hard to audit. Business transformations inside masking functions — transformations belong in the pipeline, not in the security layer. Unsecured UDFs — functions are securables like any other; whoever may change them can bypass the entire model. And finally over-masking: mask more than necessary and you block legitimate analytics.

4.4

Row filtering and column masking in practice

The implementation is surprisingly simple: you write a SQL UDF with the decision logic and attach it to the table. To check group membership there is the is_account_group_member() function.

Column mask — the function returns either the real value or a substitute, depending on group membership:

SQL
-- masking function for a phone number
CREATE OR REPLACE FUNCTION phone_mask(c_phone STRING)
  RETURN CASE WHEN is_account_group_member('metastore_admins')
    THEN c_phone
    ELSE 'REDACTED PHONE NUMBER'
  END;

ALTER TABLE customers
  ALTER COLUMN c_phone
  SET MASK phone_mask;

Row filter — the function returns true only for the rows that should be visible:

SQL
-- the admin sees everything, everyone else only nationkey = 21
CREATE OR REPLACE FUNCTION nation_filter(c_nationkey INT)
  RETURN IF(is_account_group_member('admin'), true, c_nationkey = 21);

ALTER TABLE customers
SET ROW FILTER nation_filter ON (c_nationkey);

The same rules expressed in a single view — the source table stays untouched and consumers are granted access only to the view:

SQL
CREATE OR REPLACE VIEW vw_customers AS
SELECT
  c_custkey, c_name, c_nationkey,
  CASE WHEN is_account_group_member('admins') THEN c_phone
       ELSE 'REDACTED PHONE NUMBER' END AS c_phone
FROM customers_new
WHERE CASE WHEN is_account_group_member('admins') THEN TRUE
           ELSE c_nationkey = 21 END;

GRANT SELECT ON VIEW vw_customers TO `account users`;
💡
Tip: only one row filter can be attached to a table and only one mask to a column. So design the "who sees what" decision logic inside a single function rather than by stacking several filters.
✓
Summary: choose table-level controls (filter + mask) for strict enforcement everywhere the table is used; choose dynamic views for flexible, shared abstractions over several tables.
4.5

Secrets through Azure Key Vault: secret scopes

Passwords, API keys, and connection strings never belong in notebook code. Azure Databricks organizes them into secret scopes — named collections of secrets at whose level access is controlled. There are two types:

Databricks-backed scopeAzure Key Vault-backed scope
Secret storagean encrypted DB managed by DatabricksAzure Key Vault (read-only interface)
Secret managementDatabricks CLI / APIAzure portal / CLI — in the Key Vault
WRITE through Databricksyesno — read only
Enterprise integrationlimitednetwork restrictions, central rotation

For production on Azure the standard is a Key Vault-backed scope: secrets live in the Key Vault, fit into the corporate security infrastructure, and once a secret is updated every workspace picks it up automatically. dbutils.secrets.get() reads the current value on every call — so after a secret rotation it is enough to run the code again. You only need a cluster restart for secrets referenced in the cluster's Spark configuration or environment variables: those are expanded at start-up and keep the old value for as long as the cluster runs.

A scope is created through the special URL https://<databricks-instance>#secrets/createScope (the capital "S" is mandatory — the URL is case-sensitive). You will need the DNS Name and the Resource ID of the Key Vault (both in Properties). Databricks sets Get/List permissions on the vault for itself during creation.

⚠️
Caution: the Key Vault must use the Vault access policy permission model — Databricks does not support the RBAC model for secret scopes. Newer Key Vault API versions, however, create vaults with RBAC as the default model, so creating the scope ends with a 403 error. Check the vault's Access configuration before creating the scope; verify the exact support status in the documentation.

In a notebook you then read the secret through dbutils.secrets.get(), and in SQL through the secret() function:

PYTHON
# read the credentials from the "jdbc" scope
username = dbutils.secrets.get(scope="jdbc", key="username")
password = dbutils.secrets.get(scope="jdbc", key="password")

df = (spark.read
  .format("jdbc")
  .option("url", "jdbc:sqlserver://server.database.windows.net:1433")
  .option("dbtable", "customers")
  .option("user", username)
  .option("password", password)
  .load()
)

# list the keys in the scope (without values)
dbutils.secrets.list("jdbc")
SQL
-- secret() in SQL; try_secret() returns NULL instead of an error
SELECT secret('jdbc', 'username') AS db_username;

Notebook output automatically replaces secret values with the text [REDACTED]. That only protects against an accidental leak, though — anyone with the right to run code on the cluster can get to the value programmatically. So control access with ACLs on the scope (levels READ / WRITE / MANAGE) through the Databricks CLI:

BASH
# READ for the data-engineers group on the jdbc scope
databricks secrets put-acl jdbc data-engineers READ
databricks secrets list-acls jdbc
ℹ️
Note: an ACL on a Key Vault-backed scope applies to all secrets in the whole vault. If you need to separate access to individual secrets, create several Key Vaults and a separate scope for each. Restricting MANAGE to the scope creator only requires the Premium plan.
💡
Tip: secrets can also be referenced in the cluster's Spark configuration with the syntax {{secrets/storage/account-key}} or in environment variables. Watch out, though — anyone with CAN ATTACH TO on the cluster can read them, even without rights on the scope.

4.6

Authentication through service principals

A service principal is an identity for applications and automation — "a user account for robots". Jobs and pipelines authenticate with it without personal credentials, consistently across environments. It consists of three components: an Application (client) ID, a Directory (tenant) ID, and a client secret (a password with an expiry date).

In Unity Catalog a service principal is typically hidden behind a storage credential: an administrator registers it once and you simply query tables — Unity Catalog takes over the identity behind the scenes, requests a temporary token from Microsoft Entra ID, and hands it to the compute. No credentials end up in the code and the audit log records who accessed what.

You will meet direct configuration in a notebook with storage that is not registered in Unity Catalog, or with legacy solutions — the OAuth 2.0 client credentials flow through Spark configuration:

PYTHON
# the client secret always from a secret scope, never hardcoded
service_credential = dbutils.secrets.get(scope="storage-secrets", key="sp-client-secret")

spark.conf.set("fs.azure.account.auth.type.<storage-account>.dfs.core.windows.net", "OAuth")
spark.conf.set("fs.azure.account.oauth.provider.type.<storage-account>.dfs.core.windows.net",
               "org.apache.hadoop.fs.azurebfs.oauth2.ClientCredsTokenProvider")
spark.conf.set("fs.azure.account.oauth2.client.id.<storage-account>.dfs.core.windows.net",
               "<application-id>")
spark.conf.set("fs.azure.account.oauth2.client.secret.<storage-account>.dfs.core.windows.net",
               service_credential)
spark.conf.set("fs.azure.account.oauth2.client.endpoint.<storage-account>.dfs.core.windows.net",
               "https://login.microsoftonline.com/<directory-id>/oauth2/token")

df = spark.read.parquet("abfss://<container>@<storage-account>.dfs.core.windows.net/path/to/data")
⚠️
Caution: client secrets expire and have to be rotated. When a pipeline stops reading data on a Monday morning, an expired secret is one of the first suspects. Agree on a rotation plan with your administrators and know who to turn to.
💡
Tip: apply least privilege — give each service principal access only to the storage it genuinely needs. Microsoft nevertheless recommends managed identities for storage credentials whenever possible — no secrets and support for network-protected storage accounts. Details in the next section.

4.7

Managed identities and the access connector

A managed identity is an identity whose lifecycle is managed by Azure — no client secret, no expiry, no rotation. Unity Catalog uses it through the Azure Databricks access connector: a first-party Azure resource acting as a bridge between the managed identity and your Databricks account. The connector can carry either a system-assigned identity (created and destroyed with the connector) or one or more user-assigned identities (which exist independently and can be attached to several connectors).

The deployment steps:

1) In the Azure portal, create an access connector (ideally in the same region as the storage). 2) Assign the managed identity the Storage Blob Data Contributor role on the ADLS Gen2 account; for file event notifications, Storage Queue Data Contributor is useful too. 3) In Catalog Explorer, create a storage credential of type Azure Managed Identity with the connector's resource ID. 4) On top of the credential, define external locations — a combination of the credential and a specific abfss:// path, on which you then grant permissions.

SQL
-- external table over an external location backed by a managed identity
CREATE TABLE sales.bronze.sales_data
USING DELTA
LOCATION 'abfss://data@mystorageaccount.dfs.core.windows.net/sales/';

SELECT * FROM sales.bronze.sales_data WHERE sale_date >= '2026-01-01';

Why is this the preferred route? The documentation sums up the advantages over service principals: "They have the benefit of allowing Unity Catalog to access storage accounts protected by network rules, which isn't possible using service principals, and they remove the need to manage and rotate secrets." In other words — it works behind a storage account firewall and has nothing that can expire.

ℹ️
Note: to create a storage credential you need the CREATE STORAGE CREDENTIAL privilege on the metastore (account and metastore admins have it). As a data engineer you typically do not create credentials — you use existing ones through external locations.
💡
Tip: external locations and storage credentials support workspace binding — tie a production location to the production workspace only and the dev environment will not reach production data even by accident.
