9.1

The layers of data quality defense

Poor-quality data behaves like contamination — once it gets through into the silver and gold layers it spreads into reports, ML models, and decisions. The documentation puts it plainly: invalid data "can derail analytics projects, corrupt business reports, and erode confidence in your data platform". That is why data quality is not guarded in one place but in layers — each layer catches a different kind of problem, and what slips through one is caught by the next.

Azure Databricks offers four built-in mechanisms: schema enforcement (Delta Lake automatically validates structure and types on write), table constraints (rules directly on the table, rejecting the write of an invalid row), pipeline expectations (declarative rules in Lakeflow pipelines with a configurable reaction), and monitoring (quality metrics in the UI and the event log). The combination of all four is referred to in the documentation as "defense in depth".

MechanismWhere it actsReaction to a violationTypical use
Schema enforcementevery write into a Delta tablethe write failsautomatic, always on
NOT NULL / CHECK constrainta write into a specific tablethe transaction failsbatch, hard integrity guarantees
PK / FK constraintUnity Catalog metadatanothing — informationaldocumenting the model, BI tools
Pipeline expectationsa declarative pipelinewarn / drop / fail as chosenstreaming and batch in a pipeline
💡
Tip: constraints and expectations are not competitors but complements. A constraint is the last line of defense on the table (protecting it from every writer, including those outside the pipeline), an expectation is a flexible filter inside the pipeline with metrics. In practice you want both.
9.2

Validation checks: constraints on Delta tables

The simplest validation is a NOT NULL constraint — declared directly in the column definition or added later through ALTER TABLE. Delta Lake then rejects every transaction that would write a NULL into the column.

SQL
-- NOT NULL right in the table definition
CREATE TABLE main.silver.customers (
    customer_id INT NOT NULL,
    email STRING NOT NULL,
    first_name STRING,
    last_name STRING
);

-- adding it later to an existing table
ALTER TABLE main.silver.customers ALTER COLUMN email SET NOT NULL;

More complex business rules — value ranges, formats, combinations of columns — are covered by a CHECK constraint. It is an arbitrary boolean SQL expression evaluated on every INSERT and UPDATE; a violation means the whole transaction fails.

SQL
ALTER TABLE main.silver.employees
  ADD CONSTRAINT valid_age CHECK (age >= 18 AND age <= 120);

ALTER TABLE main.silver.transactions
  ADD CONSTRAINT positive_amount CHECK (amount > 0);
⚠️
Caution: PRIMARY KEY and FOREIGN KEY constraints in Unity Catalog are informational — they are not enforced. Delta Lake will happily let you insert a duplicate primary key value. PK/FK serve as documentation of the data model for people and BI tools (and the optimizer can make use of them), but uniqueness is something you have to watch yourself — through expectations or deduplication in the pipeline, for example.
SQL
-- the PK is metadata only, it does NOT enforce uniqueness
CREATE TABLE main.silver.orders (
    order_id INT NOT NULL,
    customer_id INT,
    order_date DATE,
    CONSTRAINT orders_pk PRIMARY KEY (order_id)
);

-- a real duplicate check can be done with a materialized view
CREATE OR REFRESH MATERIALIZED VIEW order_validation AS
SELECT order_id, COUNT(*) AS occurrence_count
FROM orders
GROUP BY order_id
HAVING COUNT(*) > 1;
What if I add a constraint to a table that already holds invalid data?▼

ALTER TABLE … ADD CONSTRAINT first verifies that all existing data satisfies the rule — if it does not, the statement fails. That is by design: a constraint guarantees the state of the whole table, not just of future writes. In practice that means: clean the data first (or move the invalid rows into a quarantine table), and only then add the constraint. Verify the exact behavior for a specific constraint type in the Delta Lake documentation.

ℹ️
Note: anyone coming from classic databases expects a CHECK constraint to simply "reject" the invalid row and let the rest through. In Delta Lake the whole transaction fails — one bad row brings down the entire batch write. So constraints are useful as a hard safety net, but filter bad rows higher up in the pipeline.

9.3

Data type checks: cast and try_cast

A string where a number should be breaks aggregations and calculations. The first line of defense is again schema enforcement: on write, Delta Lake compares the types of the incoming columns against the schema of the target table. From the documentation: "All inserted columns must exist in the target table" and the types have to match or be safely convertible. Writing the value 'fifty' into an INT column therefore fails on its own.

The bronze layer, however, tends to be full of strings (CSV, JSON) and converting them to the right types is your job. That is what this pair of functions with fundamentally different behavior is for:

FunctionOn successWhen the conversion failsWhen to use it
cast()the converted valuean error, the query failshard validation — I want to know about the problem immediately
try_cast()the converted valuereturns NULLsoft validation — I want to filter out or flag the invalid rows
SQL
-- try_cast: a failed conversion = a NULL I can detect
SELECT
    raw_amount,
    try_cast(raw_amount AS DECIMAL(10,2)) AS validated_amount,
    CASE WHEN try_cast(raw_amount AS DECIMAL(10,2)) IS NULL
         THEN 'Invalid amount format' ELSE 'Valid' END AS validation_status
FROM staging_data;

This pattern is the basis of the practical quarantine pattern: valid rows cast into the silver table, invalid ones into a quarantine table with a timestamp and a reason. Nothing is lost and the data team has something concrete to take back to the source.

SQL
-- valid records into silver
INSERT INTO silver_transactions
SELECT transaction_id,
       cast(amount AS DECIMAL(10,2)) AS amount,
       cast(transaction_date AS DATE) AS transaction_date
FROM bronze_transactions
WHERE try_cast(amount AS DECIMAL(10,2)) IS NOT NULL
  AND try_cast(transaction_date AS DATE) IS NOT NULL;

-- invalid ones into quarantine with a reason
INSERT INTO quarantine_transactions
SELECT transaction_id, amount AS raw_amount, transaction_date AS raw_date,
       current_timestamp() AS quarantined_at,
       'Type validation failed' AS reason
FROM bronze_transactions
WHERE try_cast(amount AS DECIMAL(10,2)) IS NULL
   OR try_cast(transaction_date AS DATE) IS NULL;
💡
Tip: try_cast can also be combined with a CHECK constraint — for example CHECK (try_cast(event_date_str AS DATE) IS NOT NULL) enforces that a string column is always a parsable date, without changing its type.

9.4

Detecting and managing schema drift

Schema drift is a different problem from bad values: the structure of the data itself changes. The source system adds a column, renames a field, changes a type — and a pipeline that does not expect it either fails or, worse, silently loses data. The default Delta Lake behavior is conservative: a write with unknown columns fails. That is safe, but with live sources you need a strategy.

Auto Loader offers five modes through the cloudFiles.schemaEvolutionMode option:

ModeBehavior on a new column
addNewColumnsthe stream stops; after a restart the new columns are added to the schema (the default when no schema is given)
rescuethe stream keeps running; unexpected data is stored in the rescued data column
failOnNewColumnsthe stream stops and waits for manual intervention — the strictest option
nonenew columns are silently ignored
addNewColumnsWithTypeWideninglike addNewColumns + widening of compatible types (INT → LONG)

The most useful compromise for production is the rescue mode: the pipeline never fails because of structure and nothing is lost. Everything that does not match the expected schema lands as JSON in the _rescued_data column, which you can evaluate periodically.

PYTHON
(spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", "/Volumes/main/raw/schema")
    .option("cloudFiles.schemaEvolutionMode", "rescue")
    .option("rescuedDataColumn", "_rescued_data")
    .load("/Volumes/main/raw/claims")
    .writeStream
    .option("checkpointLocation", "/Volumes/main/raw/checkpoint")
    .toTable("main.bronze.claims")
)

For batch writes and MERGE there are counterparts: .option("mergeSchema", "true") on a DataFrame write and the MERGE WITH SCHEMA EVOLUTION INTO syntax in SQL — both add the new columns to the target table automatically.

SQL
MERGE WITH SCHEMA EVOLUTION INTO target_table t
USING source_data s
ON t.customer_id = s.customer_id
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *
⚠️
Caution: the none mode looks tempting ("nothing will fail"), but it silently discards new columns — you never find out the source changed. If you want to survive drift without losing data, production belongs to rescue; if you want to know about drift and decide manually, use failOnNewColumns.
Operational practice: managing drift organizationally▼

The documentation recommends: "Document your expected schemas explicitly. Store schema definitions in version control alongside your pipeline code." Add alerting on the appearance of a non-empty _rescued_data (a simple query in a job is enough) and an agreement with the source teams about announcing changes. Schema drift is 80 % a communication problem and only 20 % a technical one.

9.5

Data quality through pipeline expectations

Expectations in declarative pipelines are quality rules evaluated against every record passing through the pipeline. Each expectation has three parts: a name (identifying the rule in monitoring — use descriptive names such as valid_customer_age), a constraint (a boolean SQL expression over the record), and an action on violation. In the expression you may use literals, column identifiers, and deterministic built-in SQL functions and operators; subqueries, aggregate functions, analytic and ranking window functions, and table-valued generator functions are not allowed.

ℹ️
Note: a materialized view with expectations is always refreshed fully — incremental refresh in combination with expectations is not supported. Take that into account when designing large aggregations; verify the exact current state in the documentation.
ActionPythonSQLFate of the invalid record
Warn (default)@dp.expectEXPECT (…)written, only the metric is affected
Drop@dp.expect_or_dropON VIOLATION DROP ROWremoved before the write
Fail@dp.expect_or_failON VIOLATION FAIL UPDATEthe flow stops, the transaction is rolled back
PYTHON
from pyspark import pipelines as dp

# decorators can be stacked — each rule has its own action
@dp.table
@dp.expect("has_phone", "phone_number IS NOT NULL")
@dp.expect_or_drop("valid_price", "price >= 0 AND price <= 10000")
@dp.expect_or_fail("required_customer_id", "customer_id IS NOT NULL")
def validated_orders():
    return spark.readStream.table("raw.orders")
SQL
CREATE OR REFRESH STREAMING TABLE validated_orders(
    CONSTRAINT has_phone EXPECT (phone_number IS NOT NULL),
    CONSTRAINT valid_price EXPECT (price BETWEEN 0 AND 10000) ON VIOLATION DROP ROW,
    CONSTRAINT required_customer_id EXPECT (customer_id IS NOT NULL) ON VIOLATION FAIL UPDATE
) AS SELECT * FROM STREAM(raw.orders);

You do not have to write the rules for each table separately. The Python API can take a whole dictionary of rules (@dp.expect_all_or_drop(rules)) — and that dictionary can come from a central governance table in Unity Catalog. One set of rules labeled with tags, shared across pipelines:

PYTHON
from pyspark import pipelines as dp
from pyspark.sql.functions import col

def get_rules(tag):
    # loads the rules from the governance table by tag
    df = spark.read.table("governance.data_quality.rules").filter(col("tag") == tag).collect()
    return {row["name"]: row["constraint"] for row in df}

@dp.table
@dp.expect_all_or_drop(get_rules("financial"))
def validated_payments():
    return spark.readStream.table("raw.payments")
ℹ️
Note: what stops when a fail expectation fires depends on the pipeline mode. In a triggered pipeline only that flow stops — the other parallel flows keep running. In a continuous pipeline that flow and every flow depending on it stops, and the pipeline reports the reason for the stop. The error message in the event log even contains a sample of the input data that violated the rule, so diagnosis is quick.

You track the results in the UI: Jobs & Pipelines → select the pipeline → the dataset with expectations → the Data quality tab. The metrics (the number of passed and violated records per rule) can also be queried programmatically from the event log — the basis for your own dashboards and alerts.

✓
Summary: constraints protect the table, expectations govern the flow in the pipeline, try_cast bridges the type chaos of the bronze layer, and the Auto Loader rescue mode survives schema drift without losing data. Together they form a layered defense — none of them is enough on its own.
