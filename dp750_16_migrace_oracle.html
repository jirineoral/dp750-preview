Migrating from Oracle

Approaches to migrating an EDW to the lakehouse, Lakebridge, concept mapping, and resource tips
🗂 Bonus — outside the MOC➕ Custom module outside the official MOC

Chapter objectives

  • Describe the phases of migrating an Oracle DWH to Databricks and decide between lift-and-shift and a redesign.
  • Explain what Databricks Lakebridge (analyzer, converter, reconcile) is for and when to reach for ADF or Lakeflow Connect.
  • Map the key Oracle concepts (PL/SQL, materialized views, sequences, indexes, hints) onto their lakehouse equivalents.
  • List the typical migration traps — from NULL vs. the empty string to transaction semantics.
  • Know where to find the official migration guides and tools.
16.1

Migration strategy: from EDW to lakehouse

Migrating an Oracle data warehouse to Databricks is not one big move but a phased project. Databricks and partner practice agree on the same skeleton: assessment (an inventory of objects, dependencies, and workloads), schema and code conversion, data transfer and synchronization, validation (reconciling results against Oracle), and only at the end cutover — switching the consumers over and shutting the old platform down. The phases are also iterated per domain: you do not migrate "the whole warehouse" but data marts or subject areas one by one, ordered by risk and business value.

The fundamental strategic decision is lift-and-shift vs. redesign. Lift-and-shift (translate the code 1:1, keep the structures) is faster and cheaper as a project, but it carries twenty years of technical debt into the lakehouse — and some Oracle constructs will not translate 1:1 anyway. A redesign (rewriting into a medallion architecture, declarative pipelines, see chapters 7 and 10) gives a better long-term result but costs more analysis. In practice a hybrid wins: core tables and ETL lift-and-shifted with automatic conversion, and the most painful and most valuable parts (staging logic in PL/SQL packages, MV cascades) redesigned.

💡
Tip: do not migrate a corpse. The assessment typically shows that 30–50 % of the objects in the old DWH have not been used by anyone for years. The cheapest migration is the one you do not do — take dead tables and jobs out of scope right at the start.
⚠️
Caution: plan the cutover with a period of parallel running — both platforms live, with the reports compared. Without it you will learn about the differences from your users. And have a rollback plan: as long as the data synchronization from Oracle is running, going back is cheap.
16.2

Lakebridge and the other tools

Lakebridge is a free open-source migration toolkit from Databricks Labs (announced in June 2025; created by combining the BladeBridge acquisition and the internal Remorph project). It covers three migration phases and supports Oracle in all of them:

ComponentPhaseWhat it does for Oracle
Analyzerassessmentgoes through the data dictionary (ALL_OBJECTS, ALL_TAB_COLUMNS…) and the source scripts; computes an inventory, complexity, and an effort estimate
Converter (transpiler)conversiontranslates Oracle SQL and PL/SQL into Databricks SQL / Spark SQL; the BladeBridge engine (mature, the load-bearing one precisely for Oracle and legacy ETL), Morpheus (a deterministic SQL-only transpiler, aimed mainly at Snowflake and Redshift), and Switch (LLM-powered, the so-called agentic converter)
Reconcilevalidationcompares source and target data (row counts, hashes, aggregates) and generates a report of the differences

It installs as a CLI through databricks labs install lakebridge. A realistic expectation of the converter: Databricks quotes automation of up to 80 % of the effort; with Oracle, count on more like 70–80 % depending on the complexity of the PL/SQL — the rest (dynamic SQL, DBMS_* packages, cursor logic) is manual work. Verify the exact support status of the individual engines in the documentation, the project is evolving quickly.

The whole cycle can be driven from the command line:

BASH
# install the CLI and the transpiler (requires the Databricks CLI and a profile)
databricks labs install lakebridge
databricks labs lakebridge install-transpile

# 1) assessment: inventory and complexity of the source -> an Excel report
databricks labs lakebridge analyze \
    --source-directory /migration/oracle/src \
    --report-file /migration/reports/oracle-inventory.xlsx \
    --source-tech oracle

# 2) transpile: convert Oracle SQL and PL/SQL into Databricks SQL
databricks labs lakebridge transpile \
    --input-source /migration/oracle/src \
    --output-folder /migration/databricks/out \
    --source-dialect oracle \
    --error-file-path /migration/reports/errors.log

# 3) reconcile: configure and compare source with target
databricks labs lakebridge configure-reconcile
databricks labs lakebridge reconcile

# verify the exact option names and values with --help,
# the CLI changes between versions
⚠️
Caution: the transpiler output is a proposal, not finished code. Every generated file belongs in code review and in git — otherwise, after a few iterations nobody will be able to tell machine translation from a manual fix.

Lakebridge is not for moving data — that is the job of:

  • Azure Data Factory with the Oracle connector (a self-hosted integration runtime for on-prem) — the classic for both the historical load and scheduled increments. Treat it as an orchestrator and a "landing strip" into the bronze layer, not as a transformation engine (see chapter 7).
  • Lakeflow Connect — managed Oracle connectors: a query-based connector (querying the source through a watermark column) and an integrated CDC connector built on Oracle LogMiner over JDBC (without GoldenGate/XStream). Both variants are in Beta / Public Preview as of August 2026 — verify the availability in your region and the exact status in the documentation before you build a production migration on them.
  • Lakehouse Federation — querying Oracle "in place" without copying; useful during the transition period for comparisons and for tables not yet migrated.
What Lakebridge will not convert▼

Reliably staying manual: dynamic SQL (EXECUTE IMMEDIATE assembled at run time), calls to DBMS_* packages (DBMS_LOB, UTL_FILE), Java stored procedures, cursor and control logic with no set-based equivalent, and everything around performance — hints, partition strategies, statistics. On top of that Lakebridge does not move data, does not migrate permissions (Oracle roles and grants → Unity Catalog privileges), and does not migrate the BI layer (reports, semantic models). Verify the current scope of Oracle support in the project's release notes.

ℹ️
Note: Lakebridge is a Databricks Labs project — with no formal product SLA support. For large migrations Databricks offers a program with partners and professional services; you can, however, use the toolkit for free on your own.
16.3

Mapping Oracle concepts onto Databricks

Before diving into individual objects, it helps to see the mapping layer by layer:

ℹ️
Note: do not map the layers mechanically. Staging → bronze fits almost every time, but one PL/SQL package routinely breaks up into several steps of a silver pipeline and, conversely, three cascading MVs are replaced by a single materialized view over silver.

The biggest mental shift: there are no B-tree indexes, sequences with triggers, or optimizer hints in the lakehouse. Their function is taken over by other mechanisms:

OracleDatabricksNote
PL/SQL procedures, packagesSQL Scripting (BEGIN…END), SQL/Python UDFs, notebooks + Lakeflow JobsSQL Scripting and CREATE PROCEDURE are GA (DBR 17.0+) — the closest replacement for PL/SQL procedures; they have no package structure, though, so replace that with schemas and notebooks
Materialized views (fast refresh)CREATE MATERIALIZED VIEW / streaming tablesthe refresh is driven by a Lakeflow pipeline; incrementality is handled by the engine, not by MV logs
SEQUENCE + triggerGENERATED ALWAYS AS IDENTITYthe values are neither gapless nor necessarily contiguous; MVs do not support identity
NUMBER(p,s)DECIMAL(38,s), BIGINT, DOUBLEboth have a maximum precision of 38 digits, but NUMBER has a floating scale and a wider range (−84 to 127). NUMBER without p/s typically maps through JDBC to DECIMAL(38,10) — for financial columns choose the scale deliberately
DATE, TIMESTAMPTIMESTAMP (or DATE)an Oracle DATE contains a time too! Converting to a plain DATE loses data
VARCHAR2, CLOBSTRINGno length limit; handle length checks with constraints/expectations
B-tree/bitmap indexesliquid clustering, Z-ORDER, data skippingsee section 6.9; predictive optimization tunes the layout by itself
Range/hash partitioningliquid clustering (preferred) / partitioningdo not copy a static partition scheme 1:1 — over-partitioning is the risk
Optimizer hints (/*+ … */)AQE (Adaptive Query Execution)hints are discarded during conversion; AQE handles skew and join strategies at run time
DBMS_SCHEDULERLakeflow Jobssee chapter 11

Two quick examples. A typical "delete and reload the aggregate" PL/SQL procedure simplifies in Databricks to a MERGE or, better still, to a declarative materialized view:

SQL
-- Oracle: a PL/SQL procedure + MV log + fast refresh
-- Databricks: a declarative MV, the engine drives the refresh
CREATE MATERIALIZED VIEW main.gold.sales_daily
AS SELECT order_date, sum(amount) AS total_amount
FROM main.silver.orders
GROUP BY order_date;

And replacing a sequence with a trigger by an identity column:

SQL
-- instead of CREATE SEQUENCE cust_seq + a BEFORE INSERT trigger:
CREATE TABLE silver.customers (
  customer_sk BIGINT GENERATED ALWAYS AS IDENTITY,
  customer_id STRING,
  valid_from  TIMESTAMP
);

And the most common antipattern of the whole migration — a cursor loop that has to be rewritten set-based:

SQL
-- Oracle: row by row, one UPDATE per order
--   FOR r IN (SELECT order_id, amount FROM orders) LOOP
--     UPDATE order_stats SET total = total + r.amount WHERE id = r.order_id;
--   END LOOP;

-- Databricks: one set-based MERGE instead of the loop
MERGE INTO main.gold.order_stats AS t
USING (
  SELECT order_id, sum(amount) AS amount
  FROM main.silver.orders
  GROUP BY order_id
) AS s
ON t.id = s.order_id
WHEN MATCHED THEN UPDATE SET t.total = t.total + s.amount
WHEN NOT MATCHED THEN INSERT (id, total) VALUES (s.order_id, s.amount);
⚠️
Caution: a cursor loop converted 1:1 into a Python for loop over collect() shows up in every careless migration — and a one-minute job becomes an hour-long one. Always look for the set-based rewrite: MERGE, window functions, aggregations.
What about hierarchical queries (CONNECT BY) and the old (+) syntax?▼

CONNECT BY PRIOR has no direct equivalent — it is rewritten as a recursive CTE (WITH RECURSIVE), which Databricks SQL supports (verify the state in the documentation for your DBR version). The old Oracle outer-join syntax (+) has to be rewritten as an ANSI LEFT/RIGHT JOIN — the Lakebridge Converter handles that automatically. ROWNUM is translated to LIMIT or the row_number() window function — careful, the semantics are not identical (ROWNUM is evaluated before ORDER BY in Oracle).

SQL
-- Oracle: SELECT employee_id, manager_id, LEVEL FROM employees
--         START WITH manager_id IS NULL
--         CONNECT BY PRIOR employee_id = manager_id;

-- Databricks: a recursive CTE in ANSI syntax
WITH RECURSIVE org (employee_id, manager_id, lvl) AS (
  SELECT employee_id, manager_id, 1
  FROM main.silver.employees
  WHERE manager_id IS NULL
  UNION ALL
  SELECT e.employee_id, e.manager_id, o.lvl + 1
  FROM main.silver.employees e
  JOIN org o ON e.manager_id = o.employee_id
)
SELECT * FROM org;

Recursive CTEs arrived in Databricks relatively recently (DBSQL 2025.20 / DBR 17.0, in Public Preview at the time of announcement) and have built-in safeguards against infinite recursion — verify both availability and the limits for your runtime version in the documentation. If they are not available to you, the usual substitutes are a precomputed path column in the dimension (flattening the hierarchy at load time) or iterative processing in PySpark with a fixed number of levels.

16.4

Typical migration traps

Automatic conversion rewrites the syntax, but the semantic differences are yours to watch. These are the ones migrations from Oracle get burned by most often:

  • NULL vs. the empty string. Oracle notoriously treats '' as NULL. In Spark SQL an empty string is a regular value distinct from NULL. Every WHERE col IS NULL, concatenation, and join key on text columns can return different results after the migration.
  • Implicit type conversions. Oracle silently converts string ↔ number ↔ date according to the session's NLS settings. Spark has its own (and in ANSI mode stricter) rules — queries relying on an implicit TO_DATE will fail or return NULL. On top of that the TO_CHAR/TO_DATE format masks differ from the date_format() masks.
  • An Oracle DATE has a time. A thoughtless conversion to a Spark DATE truncates the time component — and incremental loads built on comparing "dates" break.
  • Transaction semantics. Delta Lake guarantees ACID at the level of a single table; multi-statement transactions across several tables à la BEGIN…COMMIT in PL/SQL have no direct equivalent. "All or nothing" logic across several tables has to be rebuilt (idempotent steps, with orchestration and any compensations handled by the pipeline). Verify the state of multi-table transactions in the documentation — the area is evolving.
  • MERGE differences. A Delta MERGE fails when several source rows match one target row — Oracle reports ORA-30926 in the same case, so the behavior is essentially the same. The difference is that in Oracle this error was often only hit in production and teams got used to working around it in the ETL; after the migration Delta reveals it again. Deduplicate the source before the MERGE (row_number() = 1).
  • Sorting and case sensitivity. A different default collation, different ordering of NULL values (NULLS FIRST/LAST explicitly!), and case sensitivity of identifiers.

At the level of individual functions the conversion is straightforward — it is the format masks that are treacherous:

SQL
-- Oracle
SELECT NVL(discount, 0)                                AS discount,
       DECODE(status, 'A', 'active',
                      'C', 'closed', 'other')     AS status_txt,
       TO_DATE(order_dt_txt, 'DD.MM.YYYY')          AS order_date
FROM stage.orders;

-- Databricks SQL
SELECT coalesce(discount, 0)                           AS discount,
       CASE status WHEN 'A' THEN 'active'
                   WHEN 'C' THEN 'closed'
                   ELSE 'other' END              AS status_txt,
       to_date(order_dt_txt, 'dd.MM.yyyy')          AS order_date
FROM main.silver.orders;
ℹ️
Note: notice the mask. Oracle's 'DD.MM.YYYY' corresponds to 'dd.MM.yyyy' in Spark — an uppercase D is the day of the year here and an uppercase Y is the week-based year. The transpiler usually handles it, hand-written analyst queries do not.
⚠️
Caution: it is precisely because of these differences that reconciliation is not a "nice to have". Run Lakebridge Reconcile (or your own comparison of row counts + hashes + key aggregates) on every migrated table and resolve the report of differences before the cutover, not after it.
💡
Tip: set up a "semantic regression suite" — a set of 20–50 business-critical queries (the top reports, period-close statements) and their expected results from Oracle. Run it after every conversion iteration. It catches the differences a row-count reconciliation cannot see.
Validating and reconciling data after the migration▼

Lakebridge Reconcile offers four report types: schema (column names and data types), row (a hash of the whole row, no join key needed), data (a value comparison through join columns, with the detail of the mismatches), and all (data + schema). The proven procedure: schema on all tables first — it catches badly mapped NUMBER and DATE — then row on the full volume, and only for tables with mismatches data with a join key.

The most common operational trap is a moving target: if Oracle keeps running in the meantime, compare against a fixed point — a snapshot in the source, a watermark, or time travel in Delta. Otherwise you will spend a week chasing differences that appeared between two reads. The reconcile results are written into a dashboard deployed in the workspace; verify the exact structure and configuration in the documentation.

16.5

Summary and resource tips

Migrating from Oracle is feasible and a well-trodden path: phase it by domain, let Lakebridge do the rough work (assessment, the bulk of the conversion, reconciliation), pull the data through ADF or Lakeflow Connect, and run in parallel before you switch the users over. The biggest risks are not in the syntax but in the semantics — NULLs, types, transactions.

💡
Tip: treat the migration as an opportunity, not just a move. Before you rewrite something 1:1, ask whether anyone still needs it and whether it could be simpler in the lakehouse — a declarative pipeline instead of three hundred lines of PL/SQL.
