10.1

Designing the order of operations in a pipeline

A data pipeline is not one script but a sequence of phases where each builds on the validated output of the previous one. The Learn module distinguishes six phases: ingest → clean & validate → transform → load → serve → monitor. The first four map naturally onto the layers of the medallion architecture you know from earlier chapters — bronze keeps the raw data for possible reprocessing, silver cleans and validates, gold aggregates for consumption.

Three practical rules follow from designing the order of operations. First: ingestion preserves the raw form — transforming during ingestion takes away your ability to replay the processing differently. Second: cleansing comes before transformation — joins and aggregations over invalid data produce invalid results that are far harder to trace. Third: incremental processing from the start — a full reload is comfortable during development but expensive in production.

The load and serve phases deal with getting the data to the consumers: the choice between a full refresh, an incremental append, and the merge pattern, the partitioning of target tables, optimized views, and access control. The last phase — monitoring — is not a "once it is finished" matter: metrics for run duration, volumes, and quality belong in the design from day one.

💡
Tip: when designing, draw the pipeline backwards — from the gold table the consumer needs back to the sources. You will avoid "bronze lakes" that nobody reads, and every task in the DAG will have a justifiable consumer.

10.2

The choice: a notebook, or a declarative pipeline?

Azure Databricks offers two ways to write a pipeline. Notebooks are procedural: step by step you say how something is to be computed, and you have full control over every detail — error handling, caching, the order of operations. Declarative pipelines turn that around: you describe what should exist (tables and their definitions) and the framework derives the dependencies, the execution order, the checkpoints, and the retry logic itself. The basic unit of a declarative pipeline is a flow — it reads from a source, transforms, and writes into a table or a sink.

CriterionNotebookDeclarative pipeline
Execution controlfull control by the developerorchestration handled by the system
Standard ETLverbose codeconcise declarations
Data qualitymanual validationbuilt-in expectations (see chapter 9)
Lineage and monitoringexternal toolsautomatically included
Demands on the teamprogramming skillsmanageable in pure SQL too
Typical scenariocustom logic, ML, explorationproduction, repeatable ETL
ℹ️
Note: this is not an "either–or" choice at company level. The common pattern is a hybrid: a declarative pipeline holds the backbone ETL (ingestion, cleansing, aggregation) and notebooks handle the steps that express badly in declarative form — calls to external APIs, ML scoring, one-off migrations. A single Lakeflow Job then ties both together.

10.3

Designing Lakeflow job logic

A Lakeflow Job is the orchestrator: it assembles tasks (notebooks, SQL, pipelines, scripts…) into a DAG — a directed acyclic graph that determines the execution order and how failures propagate. Independent tasks can run in parallel (faster, but heavier on compute — and the workspace also limits the number of concurrent tasks), dependent ones serially.

When a task runs relative to the results of its predecessors is decided by the Run if condition:

ConditionThe task runs…
All succeededonly when all upstream tasks succeeded (the default)
At least one succeededwhen at least one upstream task succeeded
None failedwhen none failed (skipped ones do not matter)
All doneafter all have finished, regardless of the outcome — typically cleanup
At least one failedwhen at least one failed — typically a failure notification
All failedonly when all of them failed

Alongside Run if conditions there are two special control tasks. The If/else condition task branches the run based on data values — for example the expression {{tasks.quality_check.values.invalid_count}} > 100 sends the run into a remediation branch instead of the gold aggregation. The For each task applies the same logic to every element of an array (a list of regions, files, tables) without copying task definitions; the concurrency of the iterations is configurable.

Parameters make a job reusable: in tasks you reach for them through {{job.parameters.<name>}}, and dynamic references such as {{job.trigger.time.iso_date}} (the scheduled run time) and {{backfill.iso_datetime}} for backfill runs are available too. The typical categories: date parameters (scheduled runs and backfills), environment (dev/staging/prod), and behavior control (batch size, output format).

Choosing compute by task type▼

The Learn module recommends: notebooks and Python scripts → serverless jobs compute; SQL queries and files → a serverless SQL warehouse; declarative pipelines → serverless pipeline compute; JARs → serverless or classic jobs compute; Spark Submit (the legacy JAR variant) → classic jobs compute only. Serverless removes cluster management, classic compute gives detailed control over the configuration. Tasks can share a cluster (faster start) or run in isolation. Verify the availability of the serverless variants in your region in the documentation.

💡
Tip: a task can be temporarily disabled in a job — it is skipped at run time while its configuration and history remain. When debugging, that is considerably safer than deleting the task and clicking it together again.

10.4

Error handling in pipelines and jobs

Responsibility for failures is split: the platform itself handles infrastructure problems (cluster node outages), and what is left for you are data and application errors. At the job level you have four tools: retry policies (the number of attempts and the interval; continuous jobs automatically apply exponential backoff), timeouts (the expected and maximum run duration — preventing tasks from hanging forever; for streaming there are also backlog metric thresholds), notifications (email, Slack, Teams, PagerDuty, webhook), and the conditional dependencies from the previous section (an "At least one failed" branch = notification and cleanup).

In a notebook you add the granular level: try/except over PySparkException can distinguish the error class and react specifically, and a custom retry function covers calls that job-level retry cannot reach:

PYTHON
from pyspark.errors import PySparkException
import time

try:
    df = spark.read.table("source_data")
    df.filter("amount > 0").write.mode("append").saveAsTable("target_data")
except PySparkException as e:
    # getCondition() since PySpark 4.0; getErrorClass() on older runtimes
    if e.getCondition() == "TABLE_OR_VIEW_NOT_FOUND":
        print(f"Source table not found: {e.getMessageParameters()['relationName']}")
    else:
        raise

# custom retry with exponential backoff
def run_with_retry(operation, max_retries=3, base_delay=10):
    for attempt in range(max_retries + 1):
        try:
            return operation()
        except Exception as e:
            if attempt == max_retries:
                raise
            delay = base_delay * (2 ** attempt)
            time.sleep(delay)

The key concept without which every retry is dangerous is idempotence: running the same step again must not produce duplicate data. In practice you achieve that with MERGE instead of a blind INSERT, with streaming checkpoints (exactly-once), or with a "delete & insert" partition pattern. For invalid records that are pointless to retry there is the dead-letter / quarantine table — the same pattern we built in chapter 9 for type errors.

⚠️
Caution: for task notifications, turn on "Mute notifications until the last retry". Otherwise three retry attempts generate three alarms, the team gets used to them — and nobody deals with the fourth, real one. Alert fatigue is a genuine operational risk.
💡
Tip: the documentation recommends "fail fast" when data integrity is compromised, and deliberately testing failures during development — deliberately feed the pipeline a broken file and verify that retry, quarantine, and notifications really work. Error handling that has never run is not error handling.

10.5

A pipeline from notebooks

The most direct route to a pipeline: write each phase as a notebook and assemble them into a job in Jobs & Pipelines. A Notebook task gets the path to the notebook, compute, and parameters; you set the dependencies with the Depends on field — and the DAG draws itself. The typical result is exactly the trio from the lab: ingest_bronze → clean_silver → aggregate_gold.

To make the notebooks reusable, parameterize them with widgets and pass results to the following tasks through task values:

PYTHON
# read a parameter passed from the job
processing_date = dbutils.widgets.get("processing_date")
environment = dbutils.widgets.get("environment")

# pass a value to the following tasks (e.g. for a quality gate)
dbutils.jobs.taskValues.set(key="invalid_count", value=invalid_count)

# signal the outcome back to the job
try:
    records = process_data()
    dbutils.notebook.exit(f"SUCCESS: Processed {records} records")
except Exception as e:
    dbutils.notebook.exit(f"FAILED: {str(e)}")
ℹ️
Note: a notebook has an output limit — 20 MB in total, 8 MB per cell. Production notebooks should log metrics (record counts, times), not print data. Forget about display(df) in a production job.
💡
Tip: define dependencies only where they genuinely exist. Every unnecessary edge in the DAG kills parallelism — if two silver tables do not depend on each other, let them run side by side.
10.6

Declarative pipelines: orchestration and incremental processing

The declarative approach flips the perspective: instead of orchestration, checkpoints, and dependencies you declare tables and the framework takes care of the rest. Three main benefits: automatic orchestration (the system derives the order from the dependencies between tables), incremental processing (streaming tables process every record exactly once, materialized views recompute only the changes), and built-in retry at the level of the Spark task, the flow, and the pipeline.

There are two building blocks. A streaming table is a Delta table for append-only ingestion — ideal for reading from cloud storage (through Auto Loader) or message queues. A materialized view handles transformations — joins, aggregations — and stays synchronized with changes to the upstream tables.

SQL
-- streaming table: incremental ingest from a volume
CREATE OR REFRESH STREAMING TABLE customers_bronze
AS SELECT * FROM STREAM read_files(
  "/Volumes/main/raw_data/customers",
  format => "json"
);

-- materialized view: a join synchronized with upstream changes
CREATE OR REFRESH MATERIALIZED VIEW customer_transactions
AS SELECT c.customer_id, c.customer_name, c.region,
          t.transaction_date, t.amount
FROM customers c
INNER JOIN transactions t ON c.customer_id = t.customer_id;
PYTHON
from pyspark import pipelines as dp

@dp.table
def customers_bronze():
    return (spark.readStream.format("cloudFiles")
        .option("cloudFiles.format", "json")
        .option("cloudFiles.inferColumnTypes", "true")
        .load("/Volumes/main/raw_data/customers"))

@dp.materialized_view
def regional_sales():
    customers = spark.read.table("customers")
    transactions = spark.read.table("transactions")
    return (customers.join(transactions, on="customer_id", how="inner")
        .groupBy("region").agg({"amount": "sum"}))

Data quality in a declarative pipeline is guarded by expectations — covered in full in chapter 9 (section 9.5): EXPECT only records the violation, ON VIOLATION DROP ROW filters, ON VIOLATION FAIL UPDATE stops the flow. Development is supported by the Lakeflow Pipelines Editor with dry-run validation, selective execution, dependency visualization, and data preview; the editor's feature set is evolving, so verify the current state in the documentation.

A common misconception: "a materialized view is just a view"▼

Anyone expecting the behavior of a classic view (a query evaluated on every read) will be surprised: a materialized view in Lakeflow is a precomputed table that the pipeline keeps current with respect to upstream changes — incrementally where possible. Reads are therefore fast even over large joins; the price is that the data is exactly as fresh as the last pipeline run/refresh.

✓
Summary: the order of operations is set by the medallion (ingest → clean → transform → load → serve → monitor). Choose notebooks for procedural logic, declarative pipelines for repeatable ETL — and feel free to use both in one Lakeflow Job. A DAG with Run if conditions, parameters, retries, idempotence, and quarantine turns a pipeline into a production system rather than a script you launch with a prayer.
