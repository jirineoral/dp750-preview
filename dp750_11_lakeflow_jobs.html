11.1

Anatomy of a Lakeflow Job: tasks, code sources, compute

Lakeflow Jobs is the orchestrator built directly into Azure Databricks. A job consists of one or more tasks arranged into a DAG (Directed Acyclic Graph) — the graph determines the order and the parallelism. A minimal job needs three things: a task with the logic, compute for the task to run on, and a unique name.

You create a job in the UI through Jobs & Pipelines → Create → Job. Every task has a type that determines what gets configured and where it runs:

Task typeKey configurationCompute
Notebooknotebook path, parametersserverless, classic jobs, all-purpose
Python script / wheelpath, CLI arguments / entry pointserverless, classic jobs, all-purpose
SQLa query or a fileserverless / pro SQL warehouse
Pipelineselection of an existing pipelinepipeline compute
dbtdbt project, profilesserverless / classic jobs
JARmain class, parametersserverless, classic jobs
Spark Submitthe legacy JAR variantclassic jobs compute only
Run Joba reference to another jobas per the referenced job

On top of that there are the control tasks If/else and For each for branching and iteration within a job. Task code can live in three places: in the workspace (quick start, development), in a Git repository (the job takes a snapshot of a specific commit at run time — all the job's tasks share the same Git reference), or in a volume/cloud storage (for Python scripts through an abfss:// URI).

💡
Tip: use Git as the source for production jobs. The job then runs against a defined commit, not against whatever someone happens to have half-finished in the workspace. "It works in my notebook" stops being an argument.

For compute, the default choice today is serverless compute — Databricks manages the infrastructure, you configure nothing, and it scales automatically. You pick classic jobs compute when you need control over the Spark version, the instance types, or libraries serverless does not support. When several tasks share the same cluster, the cluster lives until all of them finish — you save start-up time between tasks but also pay for any idle periods.

⚠️
Caution: a job runs with the permissions of its run identity — the job owner, or a configured service principal — never with the permissions of the user who started the run. If the run identity lacks the necessary Unity Catalog permissions, the job fails at run time with an authorization error even though the configuration is otherwise valid.
SQL
-- permissions for the service principal the job will run as
GRANT SELECT, MODIFY ON TABLE telconnect.silver.cdr_clean TO `sp-cdr-pipeline`;
GRANT USE SCHEMA ON SCHEMA telconnect.silver TO `sp-cdr-pipeline`;
Job permission levels▼

Job permissions are independent of compute permissions and come in four levels: CAN VIEW (sees the configuration and run history), CAN MANAGE RUN (also starts and cancels runs), IS OWNER (the default identity for Run as), CAN MANAGE (full editing including schedules and permissions). Each level includes the rights of those below it. The job creator and admins automatically have CAN MANAGE. A practical pattern: the pipeline team CAN MANAGE, operators CAN MANAGE RUN, stakeholders CAN VIEW.

11.2

Task dependencies and job parameters

You define dependencies on a task with the Depends on field — that is what creates the DAG. Every edge also carries a Run if condition saying when the downstream task runs at all:

Run if conditionThe task runs when…
All succeededall upstream tasks succeeded (the default)
At least one succeededat least one upstream task succeeded
None failednone failed (some may have been skipped)
All doneall have finished — regardless of the outcome
At least one failedat least one upstream task failed
All failedall of them failed

Anyone assuming the conditions are only for the "happy path" misses the most useful patterns: All done for cleanup tasks that must always run, and At least one failed for an error-handling branch (writing into an incident table, compensating logic).

Job parameters are defined at job level as key-value pairs and are automatically available to every task. Notebooks read them through widgets, Python scripts receive them as command-line arguments. In parameter values you can use dynamic value references — values filled in only at run time:

PYTHON
# the notebook reads a job parameter through a widget
processing_date = dbutils.widgets.get("processing_date")

# a parameter value in the job configuration can be dynamic:
#   {{job.trigger.time.iso_date}}                          -> the run date
#   {{job.trigger.table_update.updated_tables}}            -> which tables changed
#   {{job.trigger.table_update.<cat.sch.tbl>.version}}     -> the Delta table version
ℹ️
Note: tags (labels or key-value pairs) help filter jobs by team, project, or environment and propagate to job clusters as well — useful for cost attribution.
11.3

Triggers: scheduled, file arrival, table update, continuous

The trigger determines when a job runs. Besides a time schedule (see section 11.4), Lakeflow Jobs offers event-based triggers that react to data rather than to the clock. You add a trigger in Job details → Schedules & Triggers → Add trigger.

A file arrival trigger watches a path in a Unity Catalog external location or volume (including subdirectories, recursively) and starts the job when a new file appears. The check runs best-effort roughly every minute. Overwriting an existing file with the same name does not trigger a run — so design your file deliveries with unique names.

A table update trigger watches one or more Unity Catalog tables (managed Delta/Iceberg, external Delta, streaming tables, materialized views, and views over them) and reacts to inserts, updates, merges, and deletes. With several tables you choose between Any table is updated (a quick reaction) and All tables are updated (waiting until all the sources are current).

Both types share two handy options against "trigger storms": Minimum time between triggers (a protective pause after a run finishes) and Wait after last change (a delay that resets with every further change — batching a quick series of updates into one run).

A continuous trigger keeps the job in an endless loop: as soon as a run finishes (even by failing), the next one starts immediately. It suits near real-time processing; do count on continuous compute consumption, though.

⚠️
Caution: continuous jobs on serverless compute support only bounded streaming triggers of the Trigger.AvailableNow kind. The time-based ProcessingTime and Continuous triggers do not work on serverless — for those use classic jobs compute, or Lakeflow Spark Declarative Pipelines in continuous mode.
Limits of file arrival triggers and file events▼

Without file events enabled on the external location, a limit of 50 jobs with a file arrival trigger per workspace and a maximum of 10,000 files in the watched location applies. With file events enabled (a one-off setup using cloud change notifications) these restrictions fall away and table update triggers work more efficiently too. Verify the exact current limits in the documentation.

Before creating a file arrival trigger you need a workspace with Unity Catalog, READ on the storage location, and CAN MANAGE on the job.

💡
Tip: triggers can be paused (Pause) and resumed at any time without losing the configuration — practical during maintenance windows. An active run is allowed to finish, only new ones do not start.

11.4

Scheduling: cron, time zones, concurrent runs

A scheduled trigger comes in two forms. A simple schedule is entered as an interval ("every 12 hours") — the scheduler picks the first run itself when you save. An advanced schedule uses a cron expression with six or seven fields: seconds, minutes, hours, day of month, month, day of week, and optionally year. The minimum interval between runs is 10 seconds.

Cron expressionMeaning
0 0 12 * * ?every day at noon
0 15 10 ? * MON-FRIweekdays at 10:15
0 0 8 1 * ?the first day of the month at 8:00
0 30 6 ? * 6Lthe last Friday of the month at 6:30
0 0 */2 * * ?every 2 hours
Special characters in cron expressions▼

* = all values · ? = "no specific value" (use it in the day-of-month or day-of-week field when you specify the other one) · - = a range (10-12) · , = a list (MON,WED,FRI) · / = a step (0/15 = every 15 minutes) · L = last (day of the month, 6L = the last Friday) · # = the n-th occurrence (6#3 = the third Friday).

The time zone is not a detail. Zones with daylight saving time (DST) mean that an hourly job either skips a run or shifts by an hour once a year at the changeover. The rule from practice: schedule reports for people in their local time zone (and accept the DST shifts), and schedule technical pipelines tied to UTC timestamps or exact intervals in UTC.

What if a run takes longer than the interval? That is governed by Maximum concurrent runs — set it to 1 for jobs writing into the same tables — and by the behavior when the limit is exceeded:

BehaviorWhat happens to the new runWhen to use it
Queuewaits in a queue and starts when a slot frees upno trigger may be lost (the default choice for pipelines)
Cancelcancelled immediatelya stale trigger has no value
Skipdoes not happenan occasional missed run does not matter

The documentation on queueing: "Queued runs consume no compute resources while waiting." So the queue is free — you pay only for the run itself.

ℹ️
Note: the scheduler is not a low-latency system — a job start can be delayed by minutes because of the network or a cloud service. Do not schedule business logic to sub-minute precision and leave a time cushion between dependent pipelines.
11.5

Alerts and notifications

Notifications are configured at job level (Job notifications) as well as per task. Five event types are available:

EventWhen it is sentTypical use
Startthe run startedconfirmation that a scheduled job took off
Successthe run finished successfullya signal for downstream processes
Failurethe run failedincident response
Duration warningthe run exceeded a thresholddetecting performance degradation
Streaming backlogthe backlog stays above a threshold for 10 minutesthe health of streaming jobs

The target can be email or a system destination: Slack, Microsoft Teams, PagerDuty, and a generic HTTP webhook. System destinations must first be created by a workspace admin in Admin Settings → Notifications; a maximum of three destinations per event type can be attached to a job/task.

JSON
{
  "event_type": "jobs.on_failure",
  "workspace_id": "your_workspace_id",
  "run": { "run_id": "run_id" },
  "job": { "job_id": "job_id", "name": "job_name" }
}
⚠️
Caution: the Succeeded with failures state (the job finished, but some tasks failed) counts as a success. If you need to see partial failures too, add task-level notifications. And note: job-level notifications are not sent for the failure and retry of individual tasks.

The biggest enemy of alerting is alert fatigue — a team buried in notifications stops reading them, including the critical ones. Proven principles: mute notifications for skipped and cancelled runs (Mute notifications for skipped/canceled runs — job-level only, tasks have to be set separately), set duration warnings from the run history (warn at 45 minutes for a job that typically runs 30, not at 35), and for tasks with retries enable Mute notifications until the last retry. And document why each alert exists and what the recipient is supposed to do.

💡
Tip: if the jobs are orchestrated by Azure Data Factory, combine the layers: Databricks notifications for job-level events, ADF alerts (Monitor → Alerts & metrics) for orchestration metrics — pipeline run status, activity counts, Integration Runtime utilization.

11.6

Automatic restarts and retry policy

Network outages and transient cloud service errors are a normal operating state in distributed systems. A retry policy makes sure a job recovers from such a failure on its own. The default behavior is surprising, though: most jobs do not retry without explicit configuration. There are two exceptions — serverless jobs have auto-optimized retries by default and continuous jobs always restart, using an exponential backoff algorithm.

Retries are configured at task level: the number of attempts and the interval between them. The interval is counted from the start of the failed run — with a 60 s interval and a task that failed after 30 s, the retry starts 30 s after the failure. The timeout applies to each attempt separately; a timeout expiring counts as a failure and consumes an attempt.

For continuous jobs the exponential backoff works like this: once a threshold of consecutive failures is exceeded the job waits, every further failure extends the wait up to a system maximum, and a successful run (or a run without failures for the threshold period) resets the sequence. The Task retry mode option (On failure / Never) controls whether failed tasks are retried within the run. Continuous jobs support neither classic task-level retry policies nor task dependencies.

Against "zombie" tasks, deploy Metric thresholds → Run duration: the Warning value sends a notification, the Timeout value ends the task with the Timed Out state and hands it to the retry logic.

⚠️
Caution: retry is safe only for idempotent operations. A job that duplicates writes when run again will not be fixed by a retry policy — quite the opposite. For non-idempotent serverless jobs, turn the retry auto-optimization off.
💡
Tip: a sensible standard: 1–3 retries with an interval of 30 s to 5 minutes. Never unlimited retries — they will not solve a permanent failure, they will just burn compute. And watch the trend: a growing share of runs saved by a retry is usually the first signal of an infrastructure or data problem.
✓
Summary: restarts handle transient failures, alerts the permanent ones. The combination: retries with muting until the last attempt + a failure notification once the attempts are exhausted + a duration warning. That way you learn about a problem exactly once — and at the moment when getting up is actually worth it.
