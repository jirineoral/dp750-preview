6.1

Designing ingestion logic and configuring data sources

Before you reach for any tool, you have to decide how the data will be obtained from the source in the first place. This is called the extraction type and it is the decision that determines data freshness, compute consumption, and pipeline complexity. Databricks distinguishes three basic patterns — full, incremental, and streaming — plus the specialized change data capture (CDC) pattern.

The key difference between incremental extraction and CDC: incremental extraction sees only the "new state of the rows", whereas CDC preserves the operation type — so it also detects deletes and changes to key columns. CDC does, however, require sequencing information (a timestamp or an ordinal number) so that events arriving out of order can be processed correctly.

The second part of the design is configuring the source. With cloud storage (ADLS, S3, GCS) you control access through Unity Catalog external locations (see chapter 3) and the folder structure matters a great deal: Hive-style partitioning (key=value) allows partition values to be extracted automatically, while flat directories with thousands of files slow down listing. With databases you deal with networking, secrets, and the impact of extraction on the source system; with SaaS APIs it is rate limits, pagination, and OAuth; with message buses it is consumer groups and offset management.

RequirementChoose
Small volume (< 100k rows), no change trackingFull extraction
Large volume, reliable timestamp/sequence, hourly/daily freshness is enoughIncremental extraction
Freshness in seconds/minutes, the source publishes eventsStreaming extraction
Deletes and the operation type must be captured, audit trailCDC extraction
💡
Tip: follow the framework from the documentation: requirements first (volume, latency, source capabilities, quality, networking, cost), then the mapping onto an extraction type, then the format, and finally validation of the design. And document the decision — in a year's time nobody will know why you did not choose streaming unless you write it down somewhere.
⚠️
Caution: anyone expecting streaming to always be "better" because it is faster is confusing latency with value. If reporting needs hourly freshness, always-on streaming infrastructure just burns money — in its sample e-commerce scenario the documentation chooses exactly the hourly incremental batch.

6.2

Choosing an ingestion tool

Azure Databricks offers a spectrum of ingestion tools from fully managed to fully custom code. At one end stands Lakeflow Connect with ready-made connectors, at the other Spark Structured Streaming, where you write everything yourself. In between lie Auto Loader for files in cloud storage, COPY INTO for SQL batches, and notebooks with JDBC/ODBC. Azure Data Factory plays the role of orchestrator and "landing strip" for data from the Azure ecosystem — not of a transformation engine.

Lakeflow Connect has three categories of managed connectors (in detail in section 7.1): SaaS connectors (Salesforce, HubSpot, Jira, Workday…), which handle authentication, incremental reads, rate limits, and schema evolution and run on serverless compute; database connectors (CDC) (SQL Server, MySQL, PostgreSQL) built on reading the transaction log, which require an ingestion gateway in your network plus a staging volume; and query-based connectors for databases without CDC (Oracle, Teradata, and others), which query on a schedule through a cursor column and need no gateway. On top of that there are community connectors maintained by the community. Add standard connectors for cloud storage (Auto Loader under the hood) and message buses (Kafka, Pub/Sub, Pulsar), typically used within Lakeflow Spark Declarative Pipelines. The list of connectors is growing quickly — verify the current state in the documentation.

CDC connector vs. query-based connector — which one when?▼

Query-based connectors are the lighter alternative to CDC connectors: instead of reading the transaction log they query the source table directly through a cursor column (a monotonically increasing timestamp or integer) and load the rows above the high-water mark from the previous run. They need neither an ingestion gateway nor staging storage and support, among others, Oracle, Teradata, SQL Server, MySQL, PostgreSQL, and Lakehouse Federation sources. They can maintain target tables as SCD Type 1, SCD Type 2, or append-only.

Choose them when CDC infrastructure is not available but a reliable cursor column exists. You need a CDC connector, on the other hand, when you must capture every intermediate state of a row between runs or reliably track deletes. The price of simplicity: a query-based connector puts load on the source table with direct queries.

Auto Loader keeps the state of processed files in a checkpoint and discovers new files either by directory listing or through file notification events — it handles exactly-once processing even with billions of files, plus schema inference and evolution. COPY INTO is its batch sibling: an idempotent SQL statement that records the processed files in the Delta table's transaction log, so re-running it does not duplicate data.

SQL
-- idempotent batch load from the landing zone
COPY INTO bank.bronze.transactions
FROM 'abfss://landing@datalake.dfs.core.windows.net/transactions/'
FILEFORMAT = PARQUET
COPY_OPTIONS ('mergeSchema' = 'true');
💡
Tip: from the documentation: "Start with the most managed option that meets your requirements." Descend to custom code (Structured Streaming, JDBC notebooks) only when the managed layer does not meet your requirements — every line of custom code is a line you will maintain.
⚠️
Caution: use ADF for orchestration and landing data, not for ETL transformations "through" Databricks — transformation logic belongs in Databricks. For on-premises databases count on ExpressRoute/VPN, or on the ADF Self-Hosted Integration Runtime, which lands the data in cloud storage first. Besides ADF there are also partner ETL tools (through Partner Connect, e.g. Fivetran) — check the offering in the documentation.
6.3

Choosing a table format: Delta, Iceberg, Parquet

First the terms: a file format (Parquet, CSV, JSON) determines the physical storage of data on disk, while a table format (Delta Lake, Apache Iceberg) adds a metadata layer on top of it — transactions, a record of files, and schema versions. Delta and Iceberg both use Parquet under the hood; what differs is exactly that metadata layer.

Parquet stores data columnar in row groups with min/max statistics — hence column pruning (only the needed columns are read) and predicate pushdown (row groups outside the filter range are skipped). Delta Lake adds a transaction log on top: ACID transactions, time travel, schema enforcement/evolution, and a unified batch + streaming approach. In Azure Databricks, Delta is the default format — if you do not state a format, you get a Delta table.

Choose Apache Iceberg primarily for interoperability: it is read and written by Snowflake, Trino, Athena, Flink, and others. Unity Catalog can manage managed Iceberg tables and act as an Iceberg catalog for external engines; foreign Iceberg tables (AWS Glue, Snowflake Horizon) can be attached as foreign tables. There is also UniForm — a Delta table that generates Iceberg metadata alongside it, so external Iceberg clients can read it without copying data; verify the exact capabilities and limits in the documentation. Watch out for one asymmetry: liquid clustering and predictive optimization work for Delta as well as managed Iceberg, but Change Data Feed is a Delta Lake speciality — it rests on its transaction log.

6.4

Partitioning

Partitioning splits a table into segments by the values of a column; queries filtered on the partition key then read only the relevant portion of the data (partition pruning). It sounds like a universal good — but the documentation is unexpectedly reserved: "Databricks recommends that you do not partition tables that contain less than a terabyte of data." Below 1 TB the overhead of managing partition metadata and the risk of small files outweigh the benefits; unpartitioned Delta tables also benefit automatically from ingestion time clustering.

If you do partition, respect two numbers: a table over 1 TB and at least 1 GB of data per partition. A good partition key has low cardinality (date, region, category), matches the most frequent query filters, and scales as the data grows. Keys such as customer_id or a timestamp down to seconds produce millions of mini-partitions and destroy performance.

SQL
-- partition by a date derived from a timestamp (generated column)
CREATE TABLE bank.silver.transactions (
    transaction_id STRING,
    customer_id    STRING,
    amount         DECIMAL(12,2),
    transaction_ts TIMESTAMP,
    transaction_date DATE GENERATED ALWAYS AS (CAST(transaction_ts AS DATE))
)
PARTITIONED BY (transaction_date);

The generated column trick is worth remembering: Delta Lake can then derive partition filters even from queries that filter on the original transaction_ts — analysts do not have to know the table is partitioned by a derived date.

Common partitioning mistakes▼
  • Over-partitioning: many partitions with little data → the small files problem, slow listings, and long optimizations. The symptom: pruning "works", but queries are still slow.
  • A high-cardinality key: partitioning by customer or transaction ID never ends well — that is what clustering techniques are for (see section 6.9).
  • Changing the strategy = rewriting the table: partition columns are part of the table structure; changing them requires a complete rewrite into a new location. Think the key through before you pour in terabytes.
  • An undocumented decision: write down the key, the expected partition sizes, and the query patterns the scheme favors.
ℹ️
Note: for new tables the recommended alternative today is liquid clustering — it solves exactly the situations where partitioning fails (high cardinality, uncertain query patterns), and the keys can be changed without rewriting the data. Liquid clustering and partitioning are mutually exclusive on one table. In detail in section 6.9.

6.5

Choosing an SCD type and implementing SCD Type 2

Dimension attributes (customer, product, branch) change over time and slowly changing dimensions (SCD) define what to do about it. When a customer moves from Seattle to Portland you have three options: overwrite the value (and lose the history), preserve the old version and create a new one, or track just the previous value in a separate column.

CriterionType 0Type 1Type 2Type 3
History preservedthe original value onlynonecompletelimited (the previous value)
Storage impactminimalminimalhighmedium
Query complexitysimplesimplehighermedium
Typical useconstants, auditing the original valueerror corrections, contact detailssales attribution, territoriesbefore/after comparison
Reference from factsnatural keynatural keysurrogate keynatural key

In practice dimensions combine the types: registration date as Type 0, email and phone as Type 1, assigned region as Type 2. Save Type 2 for attributes where the historical perspective affects business decisions — versioning because of a changed phone number is pointless overhead. Type 3 is the least common; most scenarios that seem to call for it are better served by Type 2.

The implementation in Delta Lake: the surrogate key is generated by GENERATED ALWAYS AS IDENTITY, and version validity is held by the valid_from/valid_to columns plus the is_current flag:

SQL
CREATE TABLE bank.gold.dim_customer (
    customer_sk   BIGINT GENERATED ALWAYS AS IDENTITY,
    customer_id   STRING NOT NULL,   -- natural / business key
    customer_name STRING,
    city          STRING,
    region        STRING,
    valid_from    TIMESTAMP NOT NULL,
    valid_to      TIMESTAMP NOT NULL,
    is_current    BOOLEAN
)
USING DELTA
TBLPROPERTIES ('delta.enableChangeDataFeed' = 'true');

Processing the changes itself has two phases: MERGE first closes the current versions of the changed records and inserts brand-new customers, and the second step then inserts new versions for the records whose old version has just been closed. Both phases must work with the same point in time — otherwise a micro-gap appears between the valid_to of the old version and the valid_from of the new one, and a point-in-time query landing in it comes back empty. So store the timestamp in a variable:

SQL
-- one point in time for both phases: the intervals then meet with no gap
DECLARE OR REPLACE VARIABLE change_ts TIMESTAMP DEFAULT current_timestamp();

-- step 1: close old versions + insert new customers
MERGE INTO bank.gold.dim_customer AS t
USING bank.staging.customers AS s
ON t.customer_id = s.customer_id AND t.is_current = true
WHEN MATCHED AND (t.city <> s.city OR t.region <> s.region
                  OR t.customer_name <> s.customer_name)
THEN UPDATE SET t.valid_to = change_ts, t.is_current = false
WHEN NOT MATCHED THEN INSERT
    (customer_id, customer_name, city, region, valid_from, valid_to, is_current)
VALUES (s.customer_id, s.customer_name, s.city, s.region,
        change_ts, CAST('9999-12-31' AS TIMESTAMP), true);

-- step 2: insert new versions for the records just closed
-- EXISTS instead of JOIN: otherwise a customer with N closed versions would get N copies
INSERT INTO bank.gold.dim_customer
    (customer_id, customer_name, city, region, valid_from, valid_to, is_current)
SELECT s.customer_id, s.customer_name, s.city, s.region,
       change_ts, CAST('9999-12-31' AS TIMESTAMP), true
FROM bank.staging.customers s
WHERE EXISTS (SELECT 1 FROM bank.gold.dim_customer h
              WHERE h.customer_id = s.customer_id AND h.valid_to = change_ts)
  AND NOT EXISTS (SELECT 1 FROM bank.gold.dim_customer c
                  WHERE c.customer_id = s.customer_id AND c.is_current = true);

A query for the state "as of a date" then filters on the validity interval — returning exactly one version per customer:

SQL
-- the state of the dimension as of 15 June 2023 (point-in-time)
SELECT customer_id, customer_name, city
FROM bank.gold.dim_customer
WHERE valid_from <= '2023-06-15 12:00:00'
  AND valid_to   >  '2023-06-15 12:00:00';
⚠️
Caution: two classic traps in the second step. The first is fan-out: write a JOIN against the historical rows (h.is_current = false) instead of EXISTS and a customer with N closed versions gets N copies of the new version — and the dimension quietly swells with duplicates. The second is calling current_timestamp() separately in each step: a micro-gap is then left between the valid_to of the old version and the valid_from of the new one, and a point-in-time query landing exactly in it returns no version at all. A single variable with a shared timestamp plus EXISTS instead of a join solves both.
💡
Tip: a hand-written MERGE is great for understanding the mechanism, but in production consider a declarative pipeline with the AUTO CDC API — it maintains the SCD Type 2 table automatically, including handling out-of-order records (see chapter 7).
⚠️
Caution: anyone expecting SCD Type 2 to be replaced by Delta time travel will run into retention: time travel is available for 7 days by default. Business history belongs in explicit valid_from/valid_to columns; time travel is a tool for operational forensics (see section 6.6).

6.6

Temporal (history) tables and Change Data Feed

SCD Type 2 tracks business history for analytics. Temporal (history) tables solve something else: technical history for auditing, debugging, and reproducibility — "what exactly was in the table on Tuesday at 14:30 and who changed it". In Delta Lake this is built on two mechanisms: Change Data Feed (CDF) and time travel.

Once enabled, CDF records every row-level change with metadata: _change_type (insert, update_preimage, update_postimage, delete), _commit_version, and _commit_timestamp. By default it is disabled and captures only changes made after it is enabled — so turn it on before you pour production data into the table.

SQL
-- enabling CDF on an existing table
ALTER TABLE bank.silver.transactions
SET TBLPROPERTIES ('delta.enableChangeDataFeed' = 'true');

-- who changed what and when in January (audit query)
SELECT transaction_id, amount, _change_type, _commit_version, _commit_timestamp
FROM table_changes('bank.silver.transactions', '2026-01-01', '2026-01-31')
WHERE _change_type IN ('insert', 'update_postimage')
ORDER BY _commit_timestamp;

Time travel complements CDF with queries against the whole state of the table in the past — through TIMESTAMP AS OF or VERSION AS OF; DESCRIBE HISTORY gives an overview of the operations. How far back the history reaches is governed by retention: by default data files are kept for 7 days and the log for 30 days. For compliance scenarios extend the retention — set both properties together:

SQL
SELECT * FROM bank.silver.transactions TIMESTAMP AS OF '2026-01-15 14:30:00';
SELECT * FROM bank.silver.transactions VERSION AS OF 42;
DESCRIBE HISTORY bank.silver.transactions;

-- extending retention for auditing (both properties together)
ALTER TABLE bank.silver.transactions SET TBLPROPERTIES (
    'delta.logRetentionDuration' = 'interval 90 days',
    'delta.deletedFileRetentionDuration' = 'interval 90 days');
A permanent audit trail: persisting CDF into a history table▼

Because both time travel and CDF are subject to retention, long-term auditing requires persisting the changes into a separate history table. An elegant pattern is Structured Streaming reading the change feed with trigger(availableNow=True) — it starts after every load, processes everything new as a batch, and finishes:

PYTHON
(spark.readStream
    .option("readChangeFeed", "true")   # deletes arrive as _change_type = 'delete'
    .table("bank.silver.transactions")
    .writeStream
    .option("checkpointLocation", "/Volumes/bank/audit/checkpoints/transactions_history")
    .trigger(availableNow=True)
    .toTable("bank.audit.transactions_history"))

The history table then contains every change over the entire life of the data — regardless of the source table's retention window.

ℹ️
Note: longer retention = higher storage cost (old files must not be deleted by VACUUM). For regulated data this is a deliberate and documented trade: you pay for storage and buy provability.
6.7

Granularity of columns and tables

Granularity (the "grain") states what a single row of a table represents. It is the hardest reversible decision in modeling: once data is aggregated you can never un-aggregate it. If a per-minute aggregate says "average sensor temperature 75 °C", you will never learn from it in which millisecond the spike arrived.

The grain of a fact table is determined by the combination of dimension keys: "one row per product, customer, store, and day". Add an hour and you multiply the row count. The documentation recommends declaring the grain explicitly as a contract ("this table contains one row per order line") before you add the first column. The choice is then between atomic grain (the finest detail from the source — maximum flexibility) and aggregate grain (presummarized data — faster queries, fewer possible questions). A common answer: keep both and maintain the aggregates as materialized views over the atomic data.

For dimensions, granularity means the way of versioning: one row per customer (Type 1), per customer version (Type 2), or per customer and period (periodic snapshots). The grain of the dimension must match the grain of the facts — a transaction referencing version 5 of a customer must be able to find that version in the dimension.

The decision is shaped by four forces: business questions (the most detailed analysis required is the lower bound), query patterns (data that is too fine makes ordinary aggregations more expensive), cost (finer grain = more rows = more storage and compute; aggregating sensor data to seconds or minutes can cut row counts by 99 %), and compliance — financial institutions often have to keep transaction-level detail regardless of the price.

💡
Tip: when in doubt, choose the finer granularity — you can build aggregates any time later, but lost detail never comes back. The condition is a storage budget; so always back this argument with a volume estimate.

6.8

Managed vs. external (unmanaged) tables

For managed tables, Unity Catalog manages the metadata and the data files — the data sits in the managed storage location of the schema, catalog, or metastore. For external tables, Unity Catalog manages only the metadata; the files sit in a location you specify with the LOCATION clause over a registered external location, and their lifecycle is your responsibility.

Anyone thinking "managed" merely means "Databricks picked the path for me" underestimates what they are getting. Full control over the files enables exclusive Unity Catalog features: predictive optimization (automatic compaction and vacuum), automatic liquid clustering (choosing clustering keys based on queries), metadata caching, and automatic cleanup of files after a drop. A dropped managed table can be brought back with UNDROP TABLE — the default window is 7 days and is configurable in the range 7–30 days. Only after that window does Databricks delete the data files, typically within 48 hours. Verify the exact values in the documentation.

CharacteristicManaged tableExternal table
Data files managed byUnity Catalogthe user
FormatsDelta Lake, Apache IcebergDelta, Parquet, CSV, JSON, Avro, ORC, text
Predictive optimizationyesno
DROP TABLEUNDROP possible for the default 7 days (7–30 configurable), then the files are deletedthe files stay in storage
Typical usethe default choice for most tablessharing files with external systems, migration from the Hive metastore, non-Delta formats

External tables have legitimate use cases: the data has to survive independently of the workspace, tools outside Databricks read or write it, you are migrating from the Hive metastore without moving files, or you need formats other than Delta/Iceberg. Do count on the fact, though, that direct access to storage bypasses Unity Catalog's access controls and auditing — for controlled sharing, Delta Sharing is better (see section 5.6). And do not register the same external table in several metastores; changes do not propagate between them.

✓
Summary: from the documentation: "Databricks recommends managed tables for most use cases." Deploy external tables deliberately, keep writes going through Databricks where possible, and plan their conversion to managed as soon as the original reason goes away.
6.9

Liquid clustering vs. partitioning vs. Z-ORDER

All three techniques rest on the same foundation: data skipping. Delta Lake keeps statistics for each file (min/max, null counts) and a query with a filter skips the files that cannot possibly contain the values sought. Skipping only works, however, when related records are physically together — and that is exactly what clustering techniques arrange.

Liquid clustering is the recommended approach for new tables (and in Public Preview for managed Iceberg tables as well — verify the state in the documentation). Unlike partitioning it can change the strategy without rewriting the data: you define the keys with CLUSTER BY (up to 4 columns), the physical organization is done by an incremental OPTIMIZE, and when the query patterns change you simply switch the keys with ALTER TABLE.

SQL
-- fact table with liquid clustering (up to 4 keys)
CREATE TABLE bank.gold.fact_transactions (
    transaction_id STRING,
    customer_sk    BIGINT,
    branch_id      STRING,
    transaction_date DATE,
    amount         DECIMAL(12,2)
)
CLUSTER BY (transaction_date, customer_sk);

OPTIMIZE bank.gold.fact_transactions;          -- incremental clustering

-- query patterns changed? no table rewrite needed:
ALTER TABLE bank.gold.fact_transactions CLUSTER BY (branch_id, transaction_date);
OPTIMIZE bank.gold.fact_transactions FULL;     -- reorganize the old data too

-- or leave the key selection to the platform (requires predictive optimization)
-- CREATE TABLE needs a column definition or AS SELECT
CREATE TABLE bank.gold.orders (
    order_id     STRING,
    customer_sk  BIGINT,
    order_date   DATE,
    amount       DECIMAL(12,2)
)
CLUSTER BY AUTO;

-- the automation can be enabled on an existing table as well
ALTER TABLE bank.gold.orders CLUSTER BY AUTO;

Z-ORDER is the predecessor of liquid clustering: OPTIMIZE … ZORDER BY (…) co-locates related data into the same files, but it is applied only during OPTIMIZE, changing the keys means a full rewrite, and it offers only transaction-level concurrency (liquid clustering supports row-level). You will meet it on inherited tables; migration is straightforward — ALTER TABLE … CLUSTER BY (…) on an unpartitioned table followed by OPTIMIZE … FULL.

Deletion vectors — the third piece of the puzzle▼

Without deletion vectors, updating or deleting a single row means rewriting the whole Parquet file. With them, Delta only marks the rows as deleted in a small metadata file and reads apply that on the fly; the files are physically rewritten only during OPTIMIZE, auto-compaction, or REORG TABLE … APPLY (PURGE). A side benefit: row-level concurrency — concurrent transactions can change different rows of the same table without conflict. For new tables they have been enabled by default since Databricks Runtime 14.1. A caveat for compliance: "deleted" does not mean "physically gone" — that requires REORG … APPLY (PURGE) + VACUUM.

💡
Tip: for tables with frequent writes, schedule OPTIMIZE every hour or two — or, on managed tables, enable predictive optimization and leave it to the platform. CLUSTER BY AUTO then takes the automation one step further: the platform picks and changes the keys itself based on the actual queries.
⚠️
Caution: liquid clustering cannot be combined with partitioning on the same table. On managed Iceberg tables in Unity Catalog the PARTITIONED BY clause is even interpreted as liquid clustering keys — no Hive-style partitions are created.
