8.1

Profiling data: understand it first, clean it second

The journey from the bronze to the silver layer is not one statement but a sequence of steps — and the first of them is profiling: finding out what is actually in the data before you start changing anything. How many NULLs there are, what the value ranges are, where the duplicates hide. Without that you are cleaning blind.

The fastest tools are right there in SQL and the DataFrame API. ANALYZE TABLE computes statistics (row counts, min/max, NULL counts, distinct counts) — the very same statistics, incidentally, that the query optimizer uses for planning:

SQL
-- statistics for all columns
ANALYZE TABLE sales.transactions COMPUTE STATISTICS FOR ALL COLUMNS;

-- detail of a single column: min, max, NULL count, distinct count
DESC EXTENDED sales.transactions amount;
PYTHON
df = spark.table("sales.transactions")

# count, mean, stddev, min, max for numeric columns
df.describe().show()

# interactive profile of all columns including histograms
dbutils.data.summarize(df)

The dbutils.data.summarize utility renders an interactive overview of distributions, missing values, and frequent values for the whole DataFrame — for ad-hoc exploration in a notebook it is the fastest start.

Beyond these statements, Unity Catalog offers data quality monitoring with two branches: anomaly detection (enabled at the schema level, automatically watching the freshness and completeness of all tables) and data profiling (an in-depth per-table analysis of distributions, NULL percentages, and drift, configured per table through the Quality tab in Catalog Explorer or through the SDK). The profile generates two metric tables — profile metrics and drift metrics (a KS test for numeric columns, chi-square for categorical ones).

💡
Tip: a practical division of labor — anomaly detection as a blanket early-warning system across the whole schema, data profiling only for the critical tables where you need historical trends. On Unity Catalog managed tables the statistics are also kept up to date continuously by predictive optimization.

What to look for in a profile: high NULL percentages in columns that are supposed to be mandatory; "unique" identifiers that are not unique; values outside the expected bounds (negative prices); and changes in distributions over time (data drift).

8.2

Choosing column data types

The wrong type means lost precision, wasted storage, or blocked operations. The bronze layer often keeps everything as string — silver is the time to straighten the types out.

For integers, choose by the range of values: TINYINT (1 B, up to 127) for status codes, INT (4 B) for ordinary identifiers, BIGINT (8 B) for large IDs. For decimal numbers the decision matters more:

TypeCharacterUse
DECIMAL(p,s)exact precision (p digits in total, s after the point)financial data, prices
DOUBLE / FLOATapproximation in a binary representationscientific computation, sensors
⚠️
Caution: never put prices in a DOUBLE. Floating point stores values in binary and introduces rounding errors for decimal numbers such as 0.1 — and then the accounting does not add up. DECIMAL(10,2) covers amounts up to 99,999,999.99 exactly.

For temporal values the deciding question is whether you need a time zone: DATE for calendar dates without a time, TIMESTAMP for events across zones (internally normalized to UTC and rendered with the session time zone on read), and TIMESTAMP_NTZ when the time should stay exactly as it was entered (the local time of a meeting, say). Anyone expecting TIMESTAMP to return exactly what they stored may be surprised — with a different session time zone they will see a different value for the same moment.

For nested data there are the complex types: ARRAY<STRING> (a list of values of the same type — product tags), MAP<STRING, STRING> (dynamic key–value pairs), and STRUCT (a fixed set of named fields — an address). They save joins but complicate some operations; decide by your query patterns.

SQL
-- explicit CAST right at load time: errors show up early, not in reports
INSERT INTO silver.listings
SELECT
    CAST(raw_id AS INT) AS id,
    CAST(raw_price AS DECIMAL(12,2)) AS price,
    CAST(raw_listed_at AS TIMESTAMP) AS listed_at
FROM bronze.listings;
💡
Tip: cast explicitly and as early in the pipeline as you can. Implicit conversions can pass silently even where data is being lost. An explicit CAST is also documentation of intent — and a type error at load time is cheaper than a wrong number in a dashboard.

8.3

Resolving duplicates and NULL values

Duplicates arise from repeated ingestion, integration errors, or concurrent writes. Find them first — classically with GROUP BY ... HAVING COUNT(*) > 1, more elegantly with QUALIFY and a window function, which returns the whole duplicate rows straight away:

SQL
-- find duplicate rows (with all columns)
SELECT * FROM sales.customers
QUALIFY COUNT(*) OVER (PARTITION BY customer_id, email) > 1;

-- keep only the newest version of each customer
SELECT * FROM sales.customers
QUALIFY ROW_NUMBER() OVER (
    PARTITION BY customer_id ORDER BY updated_at DESC
) = 1;
PYTHON
# remove duplicates by key columns (keeps the first occurrence)
df_clean = df.dropDuplicates(["customer_id", "email"])

# full deduplication across all columns
df_unique = df.distinct()

# show only the surplus duplicates: original minus the deduplicated version
df_duplicates = df.exceptAll(df.dropDuplicates(["customer_id", "email"]))
⚠️
Caution: dropDuplicates() keeps the "first" occurrence — but which one that is, is not deterministic. When it matters which version survives (typically the newest), use the pattern with ROW_NUMBER() ... ORDER BY updated_at DESC. That is exactly the difference between "we deleted the duplicates" and "we kept the right one".

NULL values represent missing data and the strategy depends on the context: NULLs in mandatory fields (identifiers) → drop the row; NULLs in numeric fields used for aggregations → fill with zero or the average; NULLs in optional categories → an "Unknown" placeholder.

PYTHON
# drop rows with NULL in key columns
df_clean = df.dropna(subset=["customer_id", "amount"])

# fill different defaults for different columns
df_filled = df.fillna({
    "amount": 0,
    "status": "Unknown",
    "quantity": 1
})

In SQL the same job is done by COALESCE(amount, 0). And one more trap: in Python, do not filter NULLs with != None — a NULL comparison in SQL semantics does not return true/false but NULL again. Always isNull() / isNotNull(), and IS [NOT] NULL in SQL.

exceptAll vs. except — what is the difference▼

exceptAll() is a set difference that preserves multiplicity: if a record appears three times in the original and once in the deduplicated version, it returns exactly the two surplus occurrences. A plain except() would return a distinct result — and you would lose the duplicate counts. That is why exceptAll is the right tool for auditing duplicates ("how many rows will deduplication actually remove?").

Document what you did with NULLs and duplicates — a future analyst has to know why they are seeing "Unknown" in the data and where the rows went.

8.4

Transformation with filters and aggregations

Filtering, grouping, and aggregation are the basic trio for shaping data. In PySpark, filter() and where() are identical methods; conditions are combined with the & and | operators — each condition in parentheses:

PYTHON
from pyspark.sql.functions import col, count, sum, avg, max

# chaining: filter, group, aggregate, sort in one pipeline
df_result = (
    df_order
    .filter((col("o_orderstatus") == "F") & (col("o_totalprice") > 50000))
    .groupBy("o_orderpriority")
    .agg(
        count("o_orderkey").alias("n_orders"),
        sum("o_totalprice").alias("total_revenue"),
        avg("o_totalprice").alias("avg_order_value")
    )
    .sort(col("n_orders").desc())
)
display(df_result)

Thanks to lazy evaluation the whole chain is evaluated only on an action (display(), show()), and Spark optimizes the entire sequence before that. The SQL equivalent is the classic — WHERE for rows, GROUP BY for groups, HAVING for filtering after aggregation:

SQL
SELECT id, SUM(quantity) AS total_quantity
FROM dealer
GROUP BY id
HAVING SUM(quantity) > 20
ORDER BY total_quantity DESC;

The GROUP BY rule: every column in SELECT must be either in GROUP BY or wrapped in an aggregate function. The common aggregates: count(), sum(), avg(), min(), max().

💡
Tip: put filters as early in the chain as possible — every subsequent operation then processes less data. Spark reorders a fair amount on its own (predicate pushdown), but you help both readability and performance when the pipeline logically flows from reduction to aggregation.
8.5

Joins and set operators

Two families of combining datasets: joins connect tables horizontally (adding columns by key), set operators vertically (stacking the rows of queries with the same schema).

JoinReturnsTypical case
INNERonly the matching rows of both tablesorders with a valid customer
LEFTthe whole left side; NULL where there is no matchall customers, even without orders
FULLeverything from both; NULL on either sidehunting for gaps on both sides
SEMIleft rows with a match (without the right columns)customers who have ordered
ANTIleft rows without a matchcustomers who have never ordered
CROSSthe Cartesian productgenerating all combinations
PYTHON
# left join; a shared key name as a string = no duplicate column
df_left = df_employee.join(df_department, on="deptno", how="left")

# anti join: employees with no existing department (data quality check)
df_anti = df_employee.join(df_department, on="deptno", how="anti")

Set operators: UNION removes duplicates by default, UNION ALL keeps them (and is faster — it skips deduplication). INTERSECT returns the common rows, EXCEPT (a synonym for MINUS) the rows of the first query minus the second.

⚠️
Caution: the PySpark union() method behaves like SQL UNION ALL — it keeps duplicates. Anyone expecting SQL semantics has to add .distinct(). And when chaining set operations, INTERSECT has higher precedence than UNION and EXCEPT — parentheses are not decoration.
8.6

Denormalization and pivots

Denormalization flattens normalized tables into wider units: dimensions are pre-joined into the fact table, so queries against it need no joins at all. It is typically done when building the gold layer and data marts — the price is more storage and the need to refresh when the sources change.

💡
Tip: denormalize in the gold layer, where query speed rules; keep normalized structures in bronze and silver for flexibility. See the medallion architecture in the opening chapters.

PIVOT rotates the unique values of a column into separate columns ("long" → "wide") — ideal for cross-tab reports. It requires an aggregate function, because several source rows may land in the same cell:

SQL
-- quarters from rows into columns
SELECT year, region, Q1, Q2, Q3, Q4
FROM quarterly_sales
PIVOT (
  SUM(revenue)
  FOR quarter IN (1 AS Q1, 2 AS Q2, 3 AS Q3, 4 AS Q4)
);

The result: every region has its quarterly revenue side by side in a single row. A single pivot can also use several aggregates at once (SUM(revenue) AS total, AVG(revenue) AS avg) — producing the columns Q1_total, Q1_avg, and so on.

UNPIVOT is the opposite direction ("wide" → "long"): monthly columns are rotated into name–value pairs, a format suitable for aggregations and ML pipelines:

SQL
SELECT * FROM regional_targets
UNPIVOT (
  target_amount FOR month IN (jan, feb, mar, apr)
);

Each monthly column becomes a row with the value in target_amount and the month name in the month column. NULL values are omitted by default — if you want them, add UNPIVOT INCLUDE NULLS. Columns can be given aliases (jan AS `January`).

Which data shape when▼

The long format is friendly to aggregations, window functions, and machine learning — one fact per row. The wide format is friendly to people — a side-by-side comparison in a report. In practice a pipeline often unpivots source "spreadsheet" data into the long format, transforms it, and pivots the result at the end for presentation. The UNPIVOT clause requires Databricks Runtime 12.2 LTS+ — not a limitation on current runtimes, but worth checking on old clusters.

8.7

Load: INSERT, append, and MERGE

The last step of the pipeline: getting the cleansed data into the target table. The choice of strategy depends on how the new data relates to the existing data:

ScenarioOperation
new records only (daily logs, event streams)INSERT INTO / mode("append")
full refresh (lookup tables, aggregations)INSERT OVERWRITE / mode("overwrite")
a mix of updates and inserts (CDC, dimensions)MERGE INTO
selective replacement by a conditionREPLACE WHERE / REPLACE USING

MERGE INTO is the most universal: it matches source rows against target rows by the key in ON and defines an action for each branch (matched / not matched) — which is why it is called an upsert:

SQL
MERGE INTO customers AS target
USING customer_updates AS source
ON target.customer_id = source.customer_id
WHEN MATCHED AND source.price <> target.price THEN
    UPDATE SET target.price = source.price,
               target.updated_at = current_timestamp()
WHEN MATCHED AND source.discontinued = true THEN
    DELETE
WHEN NOT MATCHED THEN
    INSERT *;

In PySpark the same is provided by the Delta Lake API — DeltaTable.forName(...).merge(...) with the methods whenMatchedUpdateAll() and whenNotMatchedInsertAll() for the case of matching schemas.

⚠️
Caution: MERGE requires a unique match — if several source rows point at one target row, the operation fails. So deduplicate the source before the merge (section 8.3). And likewise: INSERT INTO does not check for duplicates — the same batch loaded twice means twice the rows.
Selective overwrite: REPLACE WHERE and REPLACE USING▼

Between "append" and "overwrite everything" there is a middle path. INSERT INTO ... REPLACE WHERE condition atomically deletes the rows matching the condition and inserts the new ones — ideal for fixing a specific time window. The newer REPLACE USING (columns) replaces only those "partition" values the incoming data touches and, according to the documentation, works on all compute types including SQL warehouses and serverless; the documentation recommends it over the classic INSERT OVERWRITE PARTITION with partitionOverwriteMode=dynamic, which is limited to classic compute. The REPLACE ON variants and the exact runtime version requirements are evolving — verify the current state in the documentation.

✓
Summary: profiling → types → dedup/NULL → transformation → load. Append for new records, overwrite for a full refresh, MERGE for upserts, REPLACE WHERE/USING for surgical interventions. This chain is the core of every bronze→silver pipeline — in declarative pipelines you simply wrap it in a managed framework (see chapter 7).
