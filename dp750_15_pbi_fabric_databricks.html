Chapter objectives

15.1

A map of the integration routes: four ways to get data into a report

Databricks and Fabric are not competitors to the death today — Microsoft sells both platforms and since 2025 has been systematically adding interoperability between them under the "better together" banner. For a data engineer that means a pleasant problem: several routes lead from data in Unity Catalog into Power BI, and each has different properties. Anyone who only knows "the warehouse connector" pays needlessly for compute; anyone who blindly deploys mirroring may run into the limits of what actually gets mirrored.

The four main routes we will cover in this chapter:

  • The Power BI connector to a Databricks SQL Warehouse — the classic: Import or DirectQuery, with the queries paid for by Databricks compute.
  • Mirroring Unity Catalog into Fabric — catalog (metadata) mirroring, the data stays put, and Fabric reads it through shortcuts. Direct Lake works on top of it.
  • OneLake shortcuts / OneLake as storage — Fabric points at Delta files in ADLS Gen2, or Databricks reads and writes into OneLake directly.
  • Delta Sharing — an open protocol for sharing between organizations and platforms, including a Power BI connector.
ℹ️
Note: this chapter is an addition outside the official DP-750 agenda — you do not need it for the exam. In practice, though, "how do I get from Databricks into Power BI" is one of the most frequent questions you will get as a data engineer.
15.2

The Power BI connector: Import vs DirectQuery

The native Azure Databricks connector in Power BI Desktop connects to a SQL Warehouse (recommended for BI workloads, ideally serverless — see chapter 2) through ODBC/HTTP; newer versions can switch to the ADBC (Arrow) driver, which speeds up the transfer of large results — verify the exact state and the plan to make ADBC the default in the documentation, because it will affect your gateway versions too. Authentication goes through Microsoft Entra ID for interactive work and through an OAuth service principal (M2M) for scheduled refreshes in the service. The connection can also be set up with Partner Connect straight from the Databricks UI.

The crucial choice is the dataset's storage mode:

  • Import — on refresh, Power BI copies the data into its in-memory VertiPaq engine. Visuals then run from memory, typically in under a second, and the SQL Warehouse is only touched by the refresh. The price is duplicated data, a model size limit, and lag (the data is as old as the last refresh).
  • DirectQuery — every interaction with a visual generates DAX, which is translated into SQL and flies off to the SQL Warehouse. The data is always fresh and the model has no size limit, but report latency depends on the warehouse and every click costs compute. Note: Databricks.Query (a native query) has limitations in combination with DirectQuery — verify the behavior in the connector documentation.

⚠️
Caution: DirectQuery over a stopped warehouse means the first user waits for the start-up. A serverless SQL Warehouse starts in seconds, a classic one in minutes — for DirectQuery, serverless is practically mandatory. And count on 50 users clicking around a report being a very "chatty" workload for the warehouse.
💡
Tip: Databricks can do the opposite direction too: from Catalog Explorer a schema can be published directly into a Power BI workspace as a semantic model (Publish to Power BI) and the refresh orchestrated as a Power BI task in Jobs — the Import model refresh then follows immediately after the pipeline finishes, rather than a blind schedule.
Metric views and Power BI — a frequent question from practice▼

Unity Catalog metric views — a semantic layer with metric definitions over tables — long reached Power BI through the "Metric View BI Compatibility Mode" option in the connector. Microsoft removed that option from the connector — reports built on it stopped working. The current route is a native query with the MEASURE() function in DirectQuery mode, or Databricks AI/BI dashboards, which work with metric views natively. The state is evolving, so verify in the documentation.

15.3

Optimization: so DirectQuery does not hurt and Import does not bloat

Most "Power BI over Databricks is slow" stories have the same roots: the report sits directly on wide bronze/silver tables, the warehouse is undersized, or statistics are missing. The principles that work:

On the Databricks side: connect reports exclusively to the gold layer — a star schema, not wide flat tables. Maintain the tables with OPTIMIZE plus liquid clustering on the filtering columns and collect statistics so the optimizer generates sensible plans. Precompute the most expensive aggregations as materialized views (see chapter 3, or section 10.6) — the warehouse then serves ready-made results:

SQL
-- statistics for the optimizer
ANALYZE TABLE main.gold.sales_fact COMPUTE STATISTICS FOR ALL COLUMNS;

-- a precomputed aggregation for the most frequent visual
CREATE MATERIALIZED VIEW main.gold.sales_by_month_mv AS
SELECT date_trunc('month', order_date) AS month,
       region,
       sum(amount) AS revenue
FROM main.gold.sales_fact
GROUP BY ALL;

Size a SQL Warehouse for BI workloads towards more clusters (autoscaling) rather than a bigger size — BI generates many small concurrent queries, not one big one. Photon helps (always on for SQL Warehouses), as do the caching layers: the result cache returns repeated queries instantly (typically slicers and shared dashboards), and the disk cache keeps hot data local.

On the Power BI side:

  • A composite model — facts in DirectQuery, dimensions in Dual/Import mode. Slicers then do not go to the warehouse at all.
  • User-defined aggregations — a small Import table with aggregates "catches" most queries, and DirectQuery reaches for the detail only on drill-down.
  • Incremental refresh in Import mode — only the last partition is refreshed, not the whole history; with the Databricks connector it works thanks to query folding through RangeStart/RangeEnd.
  • Assume referential integrity on relationships — it generates an INNER JOIN instead of an OUTER one, which is cheaper for the warehouse (only if FK integrity really holds!).
  • Fewer visuals per page — every visual in DirectQuery is at least one SQL query.
💡
Tip: the behavior in practice is easy to measure: Performance Analyzer in Power BI Desktop shows the DAX times, and Query History on the SQL Warehouse shows what SQL actually comes out of the report and where it spends its time. These two views side by side reveal the culprit within minutes.
⚠️
Caution: DirectQuery is not a substitute for data modeling. If a report needs to aggregate billions of rows on every click, no amount of sizing will save it — what you are missing is an aggregation layer in gold, not a bigger warehouse.
15.4

Mirroring Azure Databricks Unity Catalog into Fabric

A mirrored Azure Databricks catalog is, from Fabric's point of view, an item that mirrors the structure of Unity Catalog. The key word is structure: unlike database mirroring (SQL, Cosmos…), no data is copied here. Fabric pulls in the catalog metadata (schemas, tables) and accesses the Delta files themselves through internal shortcuts into ADLS Gen2. From the documentation: "When you use Fabric to read data that is registered in Unity Catalog, there is no data movement or data replication." The feature is GA (generally available since mid-2025).

What you get once the mirrored catalog is created:

  • a Mirrored Azure Databricks item in the workspace with the selected schemas/tables,
  • an automatically generated SQL analytics endpoint — read-only T-SQL querying over the Databricks tables from Fabric,
  • the ability to build a Direct Lake semantic model for Power BI on top of it (see section 15.7).

Metadata is synchronized automatically: adding or removing a schema or table in UC propagates into Fabric. Data changes show up with a small delay (seconds to minutes — it is the same discovery mechanism as the SQL analytics endpoint over a lakehouse). Governance stays on two tracks: Unity Catalog controls access on the Databricks side, while Fabric permissions apply to the mirrored item in Fabric — count on that in a security review.

⚠️
Mind the exclusions: materialized views, streaming tables, and external tables in formats other than Delta do not make it into a mirrored catalog. If your gold layer rests on the MVs from section 15.3, you will have to materialize it into ordinary Delta tables for mirroring. Verify the current list of limitations in the documentation.
💡
Tip: mirroring requires a Fabric capacity, but reading the metadata itself is cheap — you pay dearly only for what you then run over the data (T-SQL queries, Direct Lake). Databricks compute is not used at all when reading from Fabric, which is the fundamental difference from the connector in 15.2.
Common misconceptions about mirroring▼

"Mirroring makes a copy of my data, I will pay for storage twice." No — with the Azure Databricks variant only the catalog is mirrored, the data stays in ADLS Gen2 and is read through shortcuts.

"Through a mirrored catalog I can also write into Databricks." No, the SQL analytics endpoint is read-only. Writing belongs in Databricks (or into OneLake, see 15.6).

"RLS from Unity Catalog propagates into Power BI." It does not — UC row filters and column masks apply to queries through Databricks compute. The documentation is unambiguous: "Unity Catalog policies and permission aren't mirrored in Fabric." In Fabric you have to solve the security again (Fabric permissions, RLS in the semantic model).

⚠️
Mind the governance hole: if ADLS Gen2 is behind a firewall and you use trusted workspace access with a connection straight to the storage account, Unity Catalog policies (RLS, column masks, ABAC) are not enforced — the documentation states they are not enforced at the storage level. Access then stands or falls on the Fabric workspace identity and the roles on the storage account, so restrict the permissions to a specific folder in the container.
15.5

Delta Sharing: sharing across organizational boundaries

Delta Sharing (see chapter 5, section 5.6) is an open protocol for sharing Delta tables with anyone — another organization, another tenant, another platform. In the context of Power BI and Fabric it takes two forms:

  • The Power BI Delta Sharing connector — the recipient gets a credential file (endpoint URL + bearer token, and more recently OIDC federation without tokens) and connects from Power BI Desktop with the "Delta Sharing" connector. Data is loaded in Import mode; the Advanced options include a row limit (1 million by default, can be raised). It costs the provider no compute — the recipient reads the Parquet files directly through the sharing server.
  • Fabric as the recipient — data from a Delta Share can be brought into OneLake (through shortcuts or a dataflow, for example) and worked with further in Fabric; the options and the state of this integration are evolving, so check the current documentation.
SQL
-- provider: a share + a recipient (open sharing)
CREATE SHARE gold_reporting;
ALTER SHARE gold_reporting ADD TABLE main.gold.sales_by_month;
CREATE RECIPIENT partner_bi;  -- generates an activation link with a token
GRANT SELECT ON SHARE gold_reporting TO RECIPIENT partner_bi;

Delta Sharing is the right choice when the recipient is not in your tenant or does not have Databricks: a supply chain, clients, subsidiaries. Inside one organization with a Fabric capacity, mirroring (15.4) tends to be more convenient — Delta Sharing there adds token management and connector limits on top.

ℹ️
Note: the Power BI connector for Delta Sharing works in Import mode — for large shared tables, keep the row limit in mind and remember that the refresh pulls the data over the internet. For large volumes it is better to process the shared data in Databricks/Fabric and let only an aggregate through into Power BI.
15.6

OneLake as storage for Databricks

OneLake is Fabric's logical data lake — technically an ADLS-compatible endpoint (onelake.dfs.fabric.microsoft.com), so Databricks can work with it like ordinary ABFS storage. The relationship works in both directions:

Fabric points at Databricks data — OneLake shortcuts. A shortcut in a lakehouse is a virtual reference to external storage: you create an ADLS Gen2 shortcut to the folder with the Delta tables Databricks produces, and the tables appear in the lakehouse as local — with no copying and no pipeline. It works well for external tables whose path you know; for UC managed tables the cleaner route is the mirroring from 15.4, which handles the paths for you.

Databricks reads and writes OneLake — the ABFS path. On a standard cluster an OAuth configuration with a service principal (Contributor on the Fabric workspace) is enough:

PYTHON
# OAuth through a service principal (secrets, never hardcoded!)
spark.conf.set("fs.azure.account.auth.type", "OAuth")
spark.conf.set("fs.azure.account.oauth.provider.type",
    "org.apache.hadoop.fs.azurebfs.oauth2.ClientCredsTokenProvider")
spark.conf.set("fs.azure.account.oauth2.client.id", client_id)
spark.conf.set("fs.azure.account.oauth2.client.secret", client_secret)
spark.conf.set("fs.azure.account.oauth2.client.endpoint",
    f"https://login.microsoftonline.com/{tenant_id}/oauth2/token")

# reading and writing through the OneLake ABFS endpoint
path = "abfss://BIWorkspace@onelake.dfs.fabric.microsoft.com/Sales.lakehouse/Tables/dim_customer"
df = spark.read.format("delta").load(path)
df.write.format("delta").mode("overwrite").save(path)

This lets a Databricks pipeline write gold tables straight into a Fabric lakehouse — and Power BI has them immediately available for Direct Lake, without any mirroring. The price is that tables written this way live outside Unity Catalog governance (it is a direct write to storage).

Newer developments are closing that gap — the state as of August 2026, so verify in the documentation:

  • OneLake catalog federation — through CREATE CONNECTION … TYPE onelake and a foreign catalog, Unity Catalog can read a Fabric Lakehouse and Warehouse without a copy directly from Databricks (zero-copy in the opposite direction). Access is read-only, requires DBR 18.0+ in standard access mode (SQL warehouse 2025.40+), and does not support views, materialized views, or complex data types.
  • UC managed tables in OneLake — a Unity Catalog external location mapped to a OneLake path, so even managed UC tables can physically sit in OneLake. In Beta as of mid-2026.
⚠️
Caution: serverless compute in Databricks does not allow setting fs.azure.* Spark configuration — writing directly into OneLake from serverless goes through an MSAL token and the deltalake library (Python, outside Spark). And when writing into the same path from several engines, stick to the rule of one writer per table, or you are asking for transaction log conflicts.
💡
Tip: if the storage account is behind a firewall, shortcuts to ADLS Gen2 are handled by trusted workspace access and direct Databricks access into OneLake by resource instance rules for the access connector — prepare the networking in advance, it is the most common place where a demo integration freezes.
15.7

Direct Lake: the speed of Import without the refresh

Direct Lake is Power BI's third storage mode, available only on a Fabric capacity (F SKU). The trick: the VertiPaq engine loads columns directly from the Delta/Parquet files in OneLake into memory (so-called transcoding) — only at the moment a query needs them. A model "refresh" is just framing: updating the metadata to a new version of the Delta table, an operation of seconds. The result: queries as fast as Import, data freshness close to DirectQuery, without copying the whole dataset.

Direct Lake exists in two variants — and the difference matters in Databricks scenarios:

Direct Lake on OneLakeDirect Lake on SQL (endpoint)
SourceDelta tables from several Fabric sourcesone lakehouse/warehouse
Fallback to DirectQueryno — beyond the limits the query/refresh failsyes (views, SQL RLS, guardrails)
Composite with Import tablesyesno (only as a layer on top)
SQL views as a sourcenoyes, but = DirectQuery
Statusthe newer variant, GAthe original variant, GA

With the older "on SQL" variant the key word is fallback: when the engine cannot read the Delta files directly (the source is a SQL view, RLS is defined on the endpoint, the table exceeds the capacity guardrails), the query quietly switches to DirectQuery — and the report suddenly runs 5× slower without anyone changing anything. Fallback can be disabled in the model settings (Direct Lake behavior), in which case you get an error instead of a slowdown — often better in production, because you see the problem immediately.

Guardrails depend on the SKU — roughly: an F64 handles 1.5 billion rows, 5,000 Parquet files, and 25 GB of model memory per table; smaller SKUs proportionally less. Verify the exact figures in the documentation. In practice that means: keep Delta tables for Direct Lake compact (OPTIMIZE, a sensible number of files and row groups) — the V-Order Parquet optimization speeds VertiPaq reads up further and Databricks does not produce it on write. Do not assume tables written by Fabric have it, though — since spring 2025 V-Order has been disabled by default even for newly created Fabric workspaces (the documentation: "V-order is disabled by default for all newly created workspaces"), because it slows writes down. For read-heavy tables under Direct Lake, enable it explicitly.

What matters for our integration: Direct Lake also works over mirrored Databricks tables (15.4) and over shortcuts (15.6). The combination "Databricks writes gold → mirroring → Direct Lake" is, as of August 2026, architecturally the cleanest route to fast Power BI over Databricks data without paying for a SQL Warehouse on every click.

✓
Summary: Direct Lake = the performance of Import + the freshness of DirectQuery, in exchange for a Fabric capacity and discipline in maintaining the Delta tables. Over Databricks data it is unlocked by mirroring or a shortcut — with no copy of the data.
How to tell the model has fallen back to DirectQuery▼

Performance Analyzer in Power BI Desktop shows a "Direct query" item on the visual instead of pure DAX time; DAX Studio / server timings reveal DirectQuery events. In Fabric, Analyze query processing for Direct Lake semantic models (Learn) helps — it describes how to analyze queries systematically. The most common causes: the source is a view, SQL RLS on the endpoint, exceeded guardrails, or a first refresh that was never run after an XMLA deployment.

15.8

Which route when — and a summary

The decision in practice is well captured by a simple tree: first the question of who you are giving the data to, then whether you have a Fabric capacity, and finally how fresh and how large the data needs to be.

ScenarioRecommended routeWhy
Smaller gold data, periodic reportingConnector + Importsimplest, fastest visuals, the warehouse only during the refresh
Live data / huge facts, no FabricConnector + DirectQuerylive queries; optimization required (15.3)
A Fabric capacity in the organizationUC mirroring + Direct Lakezero-copy, the speed of Import, no SQL Warehouse cost per click
Databricks should write straight "into Fabric"OneLake shortcuts / ABFS writesone storage for both worlds
Data for a partner outside the tenantDelta Sharingan open protocol, no shared tenant and no shared compute
✓
Chapter summary: 1) The connector to a SQL Warehouse is the quickest start — Import for speed, DirectQuery for freshness, and both can be optimized considerably (a gold layer, materialized views, composite models, a serverless warehouse). 2) Mirroring Unity Catalog into Fabric (GA) is metadata-only and zero-copy; it opens a T-SQL endpoint and Direct Lake. 3) Direct Lake combines the performance of Import with the freshness of DirectQuery — mind the fallback and the guardrails. 4) OneLake and Databricks are converging in both directions (shortcuts, ABFS writes, catalog federation, UC managed tables in OneLake — parts of it in preview/beta). 5) Delta Sharing handles sharing across organizational boundaries.
