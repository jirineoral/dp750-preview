13.1

Monitoring and managing cluster consumption

Running a lakehouse in production is not only about the pipeline finishing. It is about it finishing for reasonable money and about you learning of a problem before the finance department does. A single forgotten interactive cluster running over the weekend can generate a surprisingly high bill — and an undersized cluster, conversely, means slow jobs and missed SLAs. The goal of monitoring is not to minimize cost at any price, but to fit the resources exactly to the workload.

Azure Databricks offers three complementary layers of observability: immediate metrics in the workspace, historical data in system tables, and centralized logs in Azure Log Analytics.

Cluster and SQL warehouse metrics

You will find the native metrics interface on every all-purpose and job cluster: Compute → the chosen cluster → the Metrics tab. It shows three categories: hardware metrics (CPU, memory, network throughput), Spark metrics (active/failed/completed tasks, shuffle read and write), and GPU metrics on the ML runtime. The data can be filtered up to 30 days back and you can switch between the aggregated view and individual nodes — handy when you suspect one particular worker.

SQL warehouses have their own Monitoring tab: live statistics (running and queued queries, cluster count), a peak query count chart, and query history with a filter for long-running queries. If the running-clusters chart sits at the autoscaling maximum for long periods, the warehouse is not keeping up.

ℹ️
Note: serverless compute for notebooks and jobs has no Metrics tab — query insights are used instead. The goal is the same, the route is different.

Auto-termination and autoscaling

Monitoring reveals the patterns, configuration reacts to them. Auto-termination shuts a cluster down after a given period of inactivity — 30–60 minutes is usual for development environments. A cluster is "inactive" only once all commands have finished, including Spark jobs, Structured Streaming, and JDBC calls. Autoscaling dynamically adds and removes workers between the configured minimum and maximum; according to the Learn module this can save roughly 20–40 % of cost compared with a fixed size (the real saving depends on the workload profile).

⚠️
Caution: auto-termination does not track the activity of legacy DStreams. If you still run such a workload, either turn auto-termination off or (better) migrate to Structured Streaming.

Budgets and system tables for cost

Track the real spend through budgets in the account console (financial targets + email notifications on overrun, filterable per team/project/workspace) and above all through the system.billing.usage system table, which can be queried directly with SQL. Anyone expecting to "somehow work the cost out from the invoice" will be surprised — without tags and system tables, attributing costs retrospectively is very hard.

SQL
-- daily DBU consumption trend
SELECT usage_date, sum(usage_quantity) AS dbus_consumed
FROM system.billing.usage
WHERE sku_name = "STANDARD_ALL_PURPOSE_COMPUTE"
GROUP BY usage_date
ORDER BY usage_date ASC
SQL
-- which jobs consumed the most DBUs (candidates for optimization)
SELECT usage_metadata.job_id AS job_id,
       sum(usage_quantity) AS total_dbus
FROM system.billing.usage
WHERE usage_metadata.job_id IS NOT NULL
GROUP BY job_id
ORDER BY total_dbus DESC

Joining system.compute.clusters tells you whose clusters burn the most DBUs (owned_by), and custom_tags lets you split costs across projects. Tags propagate from clusters and the workspace into the billing records — but only from the moment you set them. You cannot tag history retrospectively.

💡
Tip: introduce a tagging convention (business unit, project, environment) at the very start of a project and enforce it with a cluster policy. A monthly review of the cost report then takes minutes, not days.
Serverless and billing — what to watch out for▼

Serverless compute has a different billing model. In system.billing.usage you isolate it with the filter product_features.is_serverless = true; the identity_metadata.run_as column says which identity the workload ran under. Because of the distributed architecture, one serverless run can generate several billing records — always aggregate with SUM(), never rely on "one row = one run". For budgets you need account admin permissions; a workspace admin typically only sees them.

13.2

Troubleshooting and repairing Lakeflow Jobs

When an orchestrated job fails, the first question is not "why" but "where". Azure Databricks derives the state of the whole run from the leaf tasks — the tasks with no downstream dependencies. That is where the seemingly odd "Succeeded with failures" state comes from: a task in the middle of the DAG failed, but all the leaf tasks finished.

Run stateMeaning
FailedOne or more leaf tasks did not finish successfully.
Succeeded with failuresSome tasks failed, but all leaf tasks succeeded.
SkippedThe run did not start — the concurrent run limit (job/workspace) was exceeded.
Timed OutThe run exceeded the configured maximum duration.
CanceledThe run was stopped by a user or by automation.

Individual tasks can additionally be Disabled — either you turn them off by hand, or Lakeflow Jobs turns them off automatically because an upstream task is disabled. In the DAG view you recognize them by the crossed-out circle icon.

Where it broke: the matrix view

Diagnosis starts in Jobs & Pipelines → the job detail → the Runs tab. The matrix view shows the run history as a grid where every cell is the state of one task in one run:

  1. Hover over a red (failed) task — you will see the metadata including the error message.
  2. Click the task and open Task run details with the complete output and logs.
  3. Look for a pattern: the same task failing repeatedly → a problem in the task's code or configuration. Failures "jumping" randomly between different tasks → more likely a cluster or resource problem.
💡
Tip: the Diagnose Error button in the Jobs UI has the error message analyzed by the assistant (Genie) and suggests solutions for common problems. A good first step, not a substitute for understanding.

Repair run: fixing without repeating the whole job

The most valuable tool in this section: repair run re-runs only the failed tasks and their descendants, not the whole job. For a pipeline where a three-hour transformation succeeded and only the final export failed, that is the difference between three hours and three minutes of compute time.

  1. Open the failed run (the Start time column or the matrix view).
  2. Choose Repair run — the dialog shows the list of tasks that will be re-run.
  3. Optionally adjust the task parameters — the override applies to this repair run only.
  4. Confirm; once finished, the matrix view adds a new column with the repair results.
ℹ️
Note: repair is available only for jobs with two or more tasks. If the tasks share a job cluster, the repair creates a new cluster instance (e.g. my_job_cluster_v1). A disabled task is normally skipped during a repair — you force it by including it explicitly in the repair request.

Stopping, restarting, and proactive monitoring

You stop an active run with the stop button in the Runs tab (in bulk through Cancel runs / Cancel all queued runs). Continuous jobs that fail repeatedly go into exponential backoff — Databricks waits longer and longer between attempts. Once the cause is fixed, use Restart run: it cancels the active run, resets the waiting interval, and starts a new run immediately.

Complement reactive firefighting with prevention: notifications (email, Slack, webhook) on job failure, a regular review of the matrix view, and queries against the system.lakeflow schema, where you will find the history of jobs and runs across the account — trends in run duration reveal degradation before it becomes an incident.

13.3

Troubleshooting Spark jobs and notebooks

The Jobs UI tells you which task failed. But when you need to find out why it is slow, you have to go a layer down — into the Spark UI. For that you need to understand how Spark structures the work.

Three categories of failure

The causes of Spark job failures fall into three families: code errors (syntax, wrong transformations, schema mismatch — the error message usually points straight at the problem), lack of resources (out-of-memory, slow shuffle, repeatedly failing tasks), and environment problems (a cluster that did not start because of subscription limits, spot instance reclaim, an unavailable external source). The first category is fixed in code, the second by a combination of cluster configuration and optimization, the third often outside Databricks.

How to work through the Spark UI

You open the Spark UI from the cluster page (the Spark UI tab). Start the investigation on the Jobs Timeline and look for three patterns:

  • Failed jobs (a red indicator) — clicking shows the failed stage and the specific reason, including links to task-level errors.
  • Long-running jobs — a job markedly longer than the others is the first candidate for a drill-down into the stages.
  • Gaps in the timeline — short pauses are normal (the driver coordinating), but a gap of more than a minute in the middle of a pipeline suggests an overloaded driver or a cluster failure.

In a problematic job, open the longest stage and read the task metrics: the Input, Output, Shuffle Read, and Shuffle Write columns show how much data is moving where.

💡
Tip: a diagnostic shortcut — a stage with a single task means insufficient parallelization (often after a coalesce(1) or a narrow read), while uneven task durations within the same stage point to data skew (see section 13.4).

Cluster metrics and driver vs. workers

Complement the Spark UI with a look at the cluster's Metrics tab. The Server load distribution visualization colors the nodes by load: red = overloaded, blue = underused. The classic pattern: a red driver and blue workers — the driver is overloaded (typically collecting large results into the notebook, thousands of tiny tasks, or single-threaded Python code) and needs a bigger instance or a code change. High shuffle volumes with a slow run, in turn, point to a network bottleneck — the answer is earlier filtering, a broadcast join, or repartitioning.

Restarting a cluster

Exhausted resources, stuck executors, or an outdated image are sometimes only solved by a restart. Before doing it, check the cluster's Event log (instance acquisition failures, spot reclaims, executor terminations) and restart through the UI or the CLI:

BASH
# restart a cluster with the Databricks CLI
databricks clusters restart CLUSTER_ID

# you can find CLUSTER_ID with
databricks clusters list
⚠️
Caution: restarting a cluster terminates running jobs and wipes the Spark UI history. Save the diagnostic information beforehand. For long-running streaming clusters, consider scheduled restarts during maintenance windows so they run on current images.
13.4

Caching, skew, spill, and shuffle

A query that ran for ten minutes yesterday runs for an hour today. Most such mysteries can be traced to four patterns: caching problems, data skew, memory spill, and excessive shuffle. They are not independent — skew typically causes spill and both make shuffle worse. That is why they are investigated together.

ToolWhat it showsWhere to find it
DAGThe execution plan, operator order, exchange (shuffle) nodesSpark UI / query profile
Spark UIJob, stage, and task metrics, spill, shuffle read/writeThe cluster page → Spark UI
Query profileA breakdown of a SQL query by operator (time, rows, memory)Query History → See query profile
💡
Tip: start with the DAG for the overall picture of the flow and only then go into the Spark UI or the query profile for the specific stage where the time is spent.

Caching: disk cache vs. Spark cache

Azure Databricks automatically caches Parquet files on the local disks of the workers — the so-called disk cache (formerly Delta cache). It works transparently; you can check whether it is on with the spark.databricks.io.cache.enabled configuration. Alongside it there is the classic Spark cache (.cache() / .persist()), which requires manual management. Two opposite problems: under-caching (repeatedly reading the same data from remote storage — a high Input on the same stages over and over in the Spark UI) and over-caching (the cache eats the memory needed for processing and contributes to OOM). Anyone expecting .cache() to always be a speed-up will be surprised — cached data that is never read again is just paid-for memory; and do not forget .unpersist().

Data skew: a few tasks toil, the rest wait

Data skew = some partitions are markedly larger than the others. A few tasks then run many times longer and the whole cluster waits for the stragglers. The typical causes: an uneven distribution of keys in joins and aggregations (one customer in 90 % of the records), NULL values all heading into one partition, time-based partitioning with "heavy" recent days.

The diagnosis: in the Spark UI open the stage detail and the Summary Metrics section. From the documentation: "If the Max is more than 50% higher than the 75th percentile, you likely have skew." The remedies, in the order you should try them:

  • Adaptive Query Execution (AQE) — breaks skewed partitions apart at run time during joins. It is enabled on modern Databricks Runtimes; verify the configuration.
  • Broadcast join — send the small table to every executor and sidestep skew in a shuffle join entirely.
  • Salting — manually adding a random component to the key when the automation is not enough (see the aside below).
PYTHON
# check the key configurations
spark.conf.get("spark.databricks.io.cache.enabled")          # disk cache
spark.conf.get("spark.databricks.optimizer.adaptive.enabled") # AQE

# let shuffle partitions be managed dynamically
spark.conf.set("spark.sql.shuffle.partitions", "auto")

Memory spill: memory ran out, going through disk

Spill happens when intermediate results do not fit in memory and Spark puts them on disk — every byte is written and read again. In the stage detail, look for the Shuffle Spill (Memory) and Shuffle Spill (Disk) metrics: any non-zero value means memory pressure. The remedies: increase the number of partitions (less data per task — hence the "auto" above), workers with a higher memory-to-core ratio, and above all reduce the data being processed (column selection, early filtering).

⚠️
Caution: spill is often only a symptom of skew — an overly large partition does not fit in memory and overflows to disk. Fix the skew first; the spill usually disappears on its own.

Shuffle: the most expensive operation in Spark

Shuffle moves data between nodes during joins, aggregations, and repartitioning. It involves serialization, writing to disk, network transfer, and deserialization — which is why it is typically the most expensive part of a query. In the Spark UI you read it from the Shuffle Read / Shuffle Write columns; in the DAG and the query profile it appears as Exchange nodes. When shuffle read markedly exceeds the size of the input data, you are moving data around needlessly.

  • Filter as early as possible — send only the data you really need into the shuffle.
  • Broadcast join for small tables — the Learn module gives a default automatic broadcast limit of about 30 MB (and AQE can also flip a sort-merge join to a broadcast at run time when runtime statistics reveal a small table); verify the exact thresholds for your runtime in the documentation.
  • Do not repartition needlessly — every repartition() is a full shuffle.
  • Co-locate data — partition/bucket tables that are frequently joined on the same key in the same way.
PYTHON
from pyspark.sql import functions as F

# explicit broadcast of a small dimension table
result = (fact_df
    .join(F.broadcast(dim_df), "customer_id")
    .groupBy("region")
    .agg(F.sum("amount").alias("total_amount")))
Salting: breaking up a skewed key by hand▼

When AQE is not enough (extreme skew in an aggregation), add a random "salt" to the key — the key splits into N sub-keys and you aggregate in two phases:

PYTHON
# phase 1: aggregate by key + salt (spreads the skewed key across 8 tasks)
salted = (df
    .withColumn("salt", (F.rand() * 8).cast("int"))
    .groupBy("customer_id", "salt")
    .agg(F.sum("amount").alias("partial")))

# phase 2: the final aggregation over the small subtotals
final = salted.groupBy("customer_id").agg(F.sum("partial"))

The price of salting is more complex code and a double aggregation — which is why it is only the third choice after AQE and a broadcast join.

✓
Summary: the diagnostic procedure — 1) Summary Metrics: Max vs. the 75th percentile → skew, 2) Spill (Memory/Disk) > 0 → memory pressure, 3) Shuffle Read ≫ Input → needless data movement, 4) a high Input on repeated reads → caching. The fixes: AQE, broadcast, salting, early filtering, "auto" shuffle partitions.

Log streaming into Azure Log Analytics

As soon as a company runs more than one workspace, searching logs "workspace by workspace" stops scaling. Log streaming into Azure Log Analytics centralizes audit and diagnostic logs from the whole environment into one place, where you query them with KQL (Kusto Query Language) and build alerts and dashboards on top of them.

The data flow: the workspace generates audit/diagnostic events (cluster creation, job run, notebook execution, permission change) → Azure diagnostic settings capture and route them → Log Analytics stores them in per-service tables → you query with KQL. Diagnostic settings are typically configured by the platform administrator in the Azure portal; a data engineer mostly consumes the logs.

ℹ️
Note: diagnostic logs require the Premium plan of Azure Databricks and typically appear in Log Analytics within ~15 minutes of the event. For querying audit logs inside Databricks the preferred route is the system.access.audit system table — choose Log Analytics when you need cross-service monitoring, KQL alerts, or integration with Azure Monitor.
TableContents
DatabricksClustersCluster creation, termination, resizing, and configuration
DatabricksJobsJob creation, runs, failures, schedule changes
DatabricksNotebookNotebook execution and edits
DatabricksSQLSQL warehouse and query operations
DatabricksTablesTable creation/deletion, access, permission changes
DatabricksSecretsAccess to secret scopes and secrets

Every table shares a standard set of columns: TimeGenerated, OperationName, Identity, SourceIPAddress, RequestParams, and Response. So investigating job failures starts in DatabricksJobs, and a security incident in DatabricksSecrets and DatabricksTables.

KQL
// which job operations failed in the last 7 days and when the failures cluster
DatabricksJobs
| where TimeGenerated > ago(7d)
| where Response contains "error" or Response contains "failed"
| summarize FailureCount = count() by OperationName, bin(TimeGenerated, 1h)
| order by FailureCount desc

From a query it is one step to an alert: in Log Analytics you choose New alert rule, set the condition and an action group (email, SMS, mobile app, ITSM integration). The typical scenarios: more than five job failures in an hour, table operations outside business hours, an unusual wave of cluster creation (runaway automation).

KQL
// alert: more than 5 job failures in the last 60 minutes
DatabricksJobs
| where TimeGenerated > ago(1h)
| where Response contains "error" or Response contains "failed"
| summarize FailureCount = count()
| where FailureCount > 5
💡
Tip: a proven cross-investigation approach — find the failed run in DatabricksJobs, check the state of the underlying cluster in DatabricksClusters, and if the job runs a notebook, track the detail down in DatabricksNotebook. Frequent autoscaling events, in turn, reveal an undersized default configuration.
