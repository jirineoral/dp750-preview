Select and configure compute

Compute types, performance tuning, cluster features, libraries, and access control
🗂 Selecting and configuring compute

Chapter objectives

  • Choose the right compute type for a given workload (serverless vs. classic, all-purpose vs. job, SQL warehouse).
  • Configure cluster performance: VM types, worker count, autoscaling, Photon, and spot instances.
  • Use compute features: policies, instance pools, and automatic termination.
  • Install libraries cluster-scoped as well as notebook-scoped from various sources.
  • Set up access control for compute: access modes, permission levels, and entitlements.
2.1

Choosing the right compute type

The choice of compute type directly determines cost, performance, and operational complexity. There are two basic axes. Serverless compute is fully managed by Databricks (it runs in their subscription, starts in a matter of seconds, and scales automatically), while classic compute is configured by you and runs in your Azure subscription (start-up typically in minutes, full control over VMs, networking, and the runtime version).

The second axis is purpose: all-purpose compute serves interactive development in notebooks and is shared by the team; job compute is created for an automated job run and terminates itself when it finishes — no idle cost; a SQL warehouse is compute optimized purely for SQL queries and BI.

A comparison of the main options in a nutshell:

Compute typeStart-upManagementSuitable forMain limitation
Serverless (notebooks, jobs)secondsminimaldevelopment, ETL, BIin notebooks, no Scala, R, RDD API, or JAR libraries
Classic — standard modeminutesmediumshared team clusterrequires Unity Catalog
Classic — dedicated modeminutesmediumRDDs, GPUs, R, custom containersa single user/group

⚠️
Caution: serverless in notebooks does not support Scala, R, JAR libraries, or the RDD API, and it restricts custom Spark configuration. The limitation applies to notebooks, though — JAR tasks in Lakeflow Jobs are supported on serverless (in public preview according to the documentation; verify the state in the docs). Anyone who needs Scala or R interactively, the RDD API, or JAR libraries in a notebook goes to classic compute in dedicated access mode.
Serverless performance modes: speed vs. cost▼

Serverless for jobs and pipelines offers two modes. Performance-optimized (the default) keeps a pool of pre-warmed resources — start-up in seconds, suitable for latency-sensitive workloads. Standard mode typically starts in 4–6 minutes but, according to the documentation, can reduce DBU consumption by up to 70 % — ideal for scheduled nightly batches where start-up time does not matter. You switch it with the Performance optimized toggle in the job detail; for notebooks only performance-optimized is available, and standard mode does not work for continuous pipelines or runs/submit.

💡
Tip: on classic job compute, spot instances (Azure Spot VMs) save a great deal — surplus Azure capacity discounted often by up to 90 %. Azure can take them back with a 30-second warning; Spark, however, survives the loss of a worker by rescheduling the tasks. Details in section 2.2.

2.2

Configuring performance: VMs, workers, autoscaling

The performance of a classic cluster is determined by three components: the total number of cores (maximum parallelism — 8 workers × 4 cores = 32 concurrent tasks), the total memory (how much data joins and aggregations can handle in RAM before spilling to disk begins), and the local storage (scratch space for shuffle operations and caching).

You choose the VM family according to the nature of the workload:

VM familyOptimized forWhen to use
E-seriesmemorylarge joins, aggregations, in-memory analytics
F-seriesCPUcompute-intensive transformations with a small memory footprint
L-seriesstorage (NVMe)repeated reads of the same data, intensive caching
NC/ND-seriesGPUdeep learning, model training (requires Runtime ML)

At the same total capacity you can choose fewer larger workers (less network traffic during shuffles — better for analytical workloads with joins) or more smaller ones (higher parallelism — cheaper for simple batch processing). You enable autoscaling by entering a min/max worker count; Databricks uses optimized autoscaling, which scales up in two steps and can scale down even on a non-idle cluster based on the state of the shuffle files.

💡
Tip: autoscaling pays off with variable load (data exploration, ad-hoc analysis). For predictable steady-state workloads, a fixed worker count gives more stable performance and simpler capacity planning.
⚠️
Caution: use spot instances only for workers, never for the driver — when Azure reclaims the driver, the whole cluster goes down. To soften the impact, enable decommissioning: after receiving the preemption notice, a worker still manages to move shuffle and cache data to healthy nodes.
Flexible node types — insurance against a stockout▼

When Azure runs out of capacity for the chosen VM type in a region, the cluster fails with the error CLOUD_PROVIDER_RESOURCE_STOCKOUT. Flexible node types automatically reach for a compatible alternative (the same vCPU count, memory in the 100–110 % range, the same architecture and disk configuration). A workspace admin enables it with the Enable auto flexible node types toggle in the Compute admin settings; for a specific cluster it can be disabled through the Clusters API by setting alternate_node_type_ids to an empty list. It is especially valuable with spot instances — it tries several types before falling back to on-demand.

ℹ️
Note: look for bottlenecks in the Spark UI — the Jobs Timeline shows long stages, and the stage detail then shows Shuffle Spill (Memory) and Shuffle Spill (Disk). Frequent spilling = too little memory, so reach for E-series or larger nodes. A later chapter is devoted to monitoring.

2.3

Compute features: Photon, policies, pools, auto-termination

Photon is a native execution engine that replaces parts of Spark with optimized C++ code. It speeds up joins, aggregations, and scans of wide tables the most; on Runtime 9.1 LTS+ it is enabled by default. For small jobs finishing in under two seconds it may not pay off (Photon has a higher DBU rate) and it is not supported on GPU clusters at all — turn it off for ML on GPUs.

Choose the Databricks Runtime according to purpose: for interactive development the newest version is fine, for production jobs use LTS versions (longer support, proven stability). The Spark version is tied to the runtime — upgrading the runtime means upgrading Spark, so test it in a dev environment first in production. For ML, choose Databricks Runtime ML with preinstalled libraries and GPU drivers (CUDA).

Auto-termination shuts a cluster down after a given period of inactivity — the configuration stays and the cluster can be started again at any time. For interactive work a sensible timeout is around 15–45 minutes depending on the team's working habits; job clusters terminate automatically once the job finishes.

Instance pools keep a set of pre-allocated idle VMs: a cluster from a pool starts in under a minute because the VMs are already running. You configure the minimum idle instances (how many clusters typically run concurrently), the maximum capacity (a fair split of the quota between teams), and the pool's idle auto-termination; pre-warming a specific runtime version on the instances speeds start-up up further. You pay for the VMs in the idle state (not DBUs), so a pool only pays off with frequent starts — in the serverless era it is more of a tool for classic-only scenarios.

Compute policies restrict what users are allowed to configure: an admin uses them to enforce allowed VM types, a maximum cluster size, an LTS runtime, or mandatory auto-termination. Databricks ships predefined policies (e.g. Personal Compute, Shared Compute, Job Compute — the last one enforcing an LTS runtime and production defaults); a custom policy is JSON with rules:

JSON
{
  "spark_version": { "type": "regex", "pattern": ".*-lts.*" },
  "node_type_id": { "type": "allowlist",
                     "values": ["Standard_E4ds_v5", "Standard_E8ds_v5"] },
  "autotermination_minutes": { "type": "range",
                                "maxValue": 60, "defaultValue": 30 },
  "autoscale.max_workers": { "type": "range", "maxValue": 8 }
}
ℹ️
Note: the policy sample is illustrative — verify the complete syntax of attributes and virtual fields in the Databricks documentation (Compute policies).
✓
Summary: Photon = faster queries (default, not on GPUs) · LTS runtime = production stability · auto-termination = no forgotten running clusters · pools = fast start-up for classic clusters · policies = guardrails and cost control for the whole workspace.

2.4

Installing libraries

The runtime contains hundreds of preinstalled packages, but sooner or later you need something extra. The crucial thing is the difference between two installation scopes:

You install compute-scoped (cluster-scoped) libraries on the Libraries tab of the given cluster (this requires the CAN MANAGE permission). They support Python wheels, Java JARs, and R packages, and are reinstalled automatically at every cluster start — a consistent environment for the whole team. The downside: you resolve version conflicts on behalf of everyone; when two teams need different versions of the same library, they have to move to separate clusters or to notebook-scoped installation.

You install notebook-scoped libraries directly in the notebook and they apply only to the current session:

PYTHON
# notebook-scoped install — applies to this session only
%pip install faker==40.8.0

# the Python interpreter restarts after the install
dbutils.library.restartPython()

Package sources: public repositories (PyPI for Python, Maven for Java/Scala with the coordinates groupId:artifactId:version, CRAN for R), or files — workspace files (a 500 MB limit) and Unity Catalog volumes (full governance: access through UC permissions, audit log). Since Runtime 15.0 you can also install from requirements.txt. A path then looks like /Volumes/main/engineering/libraries/mypackage-1.0.0-py3-none-any.whl — the installing identity needs READ VOLUME.

⚠️
Caution: on clusters with standard access mode, Maven coordinates, JAR files, and init scripts all require approval in an allowlist by the metastore admin (Catalog Explorer → metastore settings → Allowed JARs/Init Scripts). The allowlist works by prefix — /Volumes/prod-libraries/ allows the whole directory; do not forget the trailing slash, otherwise it will also match unintended prefixes.
💡
Tip: in production always pin versions (pymssql==2.3.9). Without a version you install "latest" and one day your pipeline will fail on someone else's breaking change. The exception: CRAN always pulls the latest version — pin R packages by storing the file in a volume.
Init scripts — when (not) to reach for the shell▼

Init scripts run at cluster start before the Spark driver launches — they are useful for system-level things libraries cannot solve: apt-get install of system packages, environment variables, monitoring agents. For installing ordinary libraries Databricks does not recommend them — cluster-scoped libraries are more manageable. Store the script in a UC volume (Runtime 13.3 LTS+), for example /Volumes/main/engineering/scripts/setup.sh; a non-zero exit code from any script stops the cluster start. Treat them as a last resort — environment variables and Spark configuration are often handled more elegantly by a compute policy.

2.5

Access control for compute

Access to compute is managed in the workspace UI (not in the Azure portal) and has two levels: the cluster's access mode (who may work on it and how isolated they are) and the permission levels (what a specific user may do with a given cluster).

The access mode is set to Auto by default in the UI: it picks Standard unless you select an ML runtime or a runtime below 14.3 — then the choice automatically falls to Dedicated. Standard access mode (formerly shared) allows a cluster to be safely shared by several users — code isolation between users is provided by Lakeguard. Dedicated access mode (formerly single-user) assigns the cluster to a single user or group and grants full machine privileges — necessary for the RDD API, R, GPU workloads, and custom containers.

Permission levelWhat it allowsTypical holder
NO PERMISSIONSthe cluster is not visiblethe default state
CAN ATTACH TOattach a notebook, see the Spark UI and metricsanalyst
CAN RESTART+ start, stop, restartsenior engineer, team lead
CAN MANAGE+ edit configuration, libraries, resize, permissionscluster owner, admin

You set permissions through Compute → the cluster menu → Permissions; changes take effect immediately without a restart. The creator of a cluster is its owner with CAN MANAGE, and workspace admins have CAN MANAGE everywhere automatically. Alongside this there are workspace-level entitlements — for example unrestricted cluster creation lets a non-admin create clusters with no size limits (without promoting them to admin); for ordinary users, assign a compute policy instead.

⚠️
Caution: avoid the legacy No isolation shared mode entirely — on it, users with nothing more than CAN ATTACH TO can see service account keys in log4j files. Migrate existing clusters in this mode to standard or dedicated.
ℹ️
Note: by default only CAN MANAGE sees the driver logs — stdout/stderr may contain secrets. The behavior is controlled by the Spark configuration spark.databricks.acl.needAdminPermissionToViewLogs; think carefully before loosening it, and always keep secrets in secret scopes rather than in code.

Dedicated group access (Unity Catalog + Runtime 15.4+) makes it possible to assign a cluster to a whole group: each member's permissions are automatically narrowed to the group's permissions on attach (no privilege escalation) and objects created on the cluster are owned by the group, not by an individual. Create a workspace folder for the group (for example /Workspace/Groups/<groupName>) with CAN MANAGE for notebooks and experiments.

💡
Tip: grant permissions to groups rather than individuals, and stick to the principle of least privilege: analyst = CAN ATTACH TO, availability owner = CAN RESTART, CAN MANAGE for owners only. Audit access regularly through the system.access.audit table.

fake = Faker()
