5.1

Table definitions: comments, tags, and discovery

Governance does not start with permissions but with metadata. Well-described tables and columns are what separates a trustworthy data estate from a dump of parquet files — and with the rise of AI-driven discovery tools (such as AI/BI Genie) the relationship is direct: the quality of your comments and tags determines the quality of the answers AI generates over your data.

Comments are free descriptive text — you can add them to a catalog, schema, table, view, and individual columns, either when creating the table or later. They support markdown as well:

SQL
-- comments right in the table definition
CREATE TABLE sales.customers.profiles (
    customer_id  BIGINT COMMENT 'Unique identifier for each customer',
    email        STRING COMMENT 'Customer primary email address',
    created_date DATE   COMMENT 'Date when customer account was created'
);

-- adding / editing a comment later
COMMENT ON TABLE sales.customers.profiles
IS 'Contains customer profile information including contact details';

ALTER TABLE sales.customers.profiles
ALTER COLUMN email COMMENT 'Primary email address used for notifications';

Tags are key-value pairs for structured classification — unlike comments, they are searchable and policies can be built on top of them:

SQL
-- tags on a table and on a column
ALTER TABLE sales.customers.profiles
SET TAGS ('domain' = 'sales', 'data_classification' = 'internal');

ALTER TABLE sales.customers.profiles
ALTER COLUMN email
SET TAGS ('pii' = 'email', 'sensitivity' = 'high');

-- removing a tag
ALTER TABLE sales.customers.profiles UNSET TAGS ('domain');

The limits: max. 50 tags per object, 1,000 column tags per table, key and value max. 256 characters each; keys are case-sensitive. And because tags are stored as plain text, never put sensitive values in them.

For exploring there is Catalog Explorer (the Columns, Sample Data, Details, History, and Insights tabs) or SQL:

SQL
SHOW CATALOGS;
SHOW SCHEMAS IN sales;
SHOW TABLES IN sales.customers LIKE 'profiles_*';
DESCRIBE TABLE EXTENDED sales.customers.profiles;
SHOW TBLPROPERTIES sales.customers.profiles;
💡
Tip: Catalog Explorer can generate comments with AI (the AI generate button). Always review the suggestions, though — they are produced by analyzing the schema and column names and can be inaccurate. Do not rely on them for classifying PII.
ℹ️
Note: to edit comments you need ownership of the object, or MODIFY + SELECT on the table (plus USE CATALOG / USE SCHEMA on the parents). Anyone with the BROWSE privilege can read them.
5.2

ABAC: governed tags and central policies

The row filters and masks from chapter 4 (section 4.4) have one weakness: they are configured table by table. Attribute-based access control (ABAC) turns the problem around — instead of permissions for every table × user combination, you define a policy bound to a tag. Tag a new table and the policy applies to it automatically, with no further configuration.

The foundation is governed tags — unlike standard tags they have centrally defined keys and allowed values, and only users with the ASSIGN permission may apply them:

AspectStandard tagsGoverned tags
Scopeany key-value pairpredefined keys and values
Controlanyone with APPLY TAGonly users with ASSIGN
Purposeorganization and discoverypolicy enforcement, compliance
UI indicator—a lock icon in Catalog Explorer

You create a governed tag in the UI: Catalog → Governance → Governed Tags — for example the key pii with the allowed values ssn, email, address. Tags on a catalog or a schema are inherited by every object inside; column tags are not inherited.

A policy then ties together a UDF, a target group, and a condition on a tag:

SQL
-- masking function (deterministic, no external calls)
CREATE OR REPLACE FUNCTION mask_ssn(ssn STRING)
RETURNS STRING
DETERMINISTIC
RETURN '***-**-****';

-- central policy: mask every column tagged pii=ssn in the whole schema
CREATE POLICY mask_sensitive_ssn
ON SCHEMA sales.customers
COLUMN MASK mask_ssn
TO `all_users`
EXCEPT `compliance_team`
FOR TABLES
MATCH COLUMNS
    has_tag_value('pii', 'ssn') AS ssn_col
ON COLUMN ssn_col;

A ROW FILTER policy at the catalog or schema level works the same way — one statement covers every table that has a column with the given tag. Policies are inherited: a policy on a catalog applies to all schemas and tables inside it. Only one row filter may apply to a table and one mask to a column — a policy collision blocks access with an error.

⚠️
Caution: the UDF in an ABAC policy runs on every query against the protected tables. Keep the logic simple and deterministic, with no subqueries, joins, or calls to is_account_group_member() inside the function — the "for whom" decision belongs in the policy (TO/EXCEPT), the function only handles "how to transform". Test the performance on at least a million rows.
ℹ️
Note: according to the documentation, accessing tables protected by ABAC requires Databricks Runtime 16.4+ or serverless compute. Quotas: 100 policies per catalog and per schema, 50 per table, 10,000 per metastore. ABAC row filter and column mask policies, governed tags, and automatic data classification are generally available in Unity Catalog (since April 2026); verify the quotas and behavioral details in the documentation.
✓
Summary: per-table filters and masks (chapter 4) for individual exceptions; ABAC for blanket rules of the kind "mask all PII fields for everyone except compliance". Tagging a new table immediately brings it under the existing protection.

5.3

Retention policies: Delta retention, VACUUM, and predictive optimization

Delta Lake keeps history — the transaction log and old versions of the data files. That is what makes time travel possible, but it also means deleted data does not physically disappear until VACUUM removes it. Retention is governed by two table properties:

PropertyDefault valuePurpose
delta.logRetentionDuration30 dayshow long the transaction log history is kept
delta.deletedFileRetentionDuration7 daysfrom when VACUUM may remove unreferenced files

The two properties work together — if you want 30 days of history even on tables with frequent VACUUM, set both:

SQL
ALTER TABLE sales.customers.transactions
SET TBLPROPERTIES (
    'delta.logRetentionDuration' = 'interval 30 days',
    'delta.deletedFileRetentionDuration' = 'interval 30 days'
);

-- VACUUM: default threshold 7 days, or explicitly
VACUUM sales.customers.transactions;
VACUUM sales.customers.transactions RETAIN 168 HOURS;
⚠️
Caution: after VACUUM, time travel queries against the removed versions stop working — the data physically does not exist. And on tables with deletion vectors enabled, VACUUM alone is not enough: rows marked for deletion are removed only by REORG TABLE … APPLY (PURGE).

Retention is closely tied to the GDPR "right to be forgotten": DELETE only marks the record in a new version of the table, and physical removal happens only with VACUUM. On top of that you have to propagate deletions through the medallion layers — materialized views catch up on refresh, but streaming tables expect an append-only source and an upstream delete breaks them; the answer is skipChangeCommits:

PYTHON
# the stream ignores upstream deletes and updates
spark.readStream.option('skipChangeCommits', 'true').table("bronze.users")

Manually scheduling VACUUM/OPTIMIZE across hundreds of tables is exactly the work you do not want to do. Predictive optimization automates it for managed tables — it runs VACUUM, OPTIMIZE, and ANALYZE based on how the tables are actually used:

SQL
ALTER SCHEMA sales.customers ENABLE PREDICTIVE OPTIMIZATION;

-- monitoring of completed maintenance including cost
SELECT * FROM system.storage.predictive_optimization_operations_history;
💡
Tip: before you enable predictive optimization, set delta.deletedFileRetentionDuration on tables with longer compliance requirements — otherwise automatic VACUUM will run with the default 7 days. For accounts created after 11 November 2024, predictive optimization is enabled by default.
Archiving to the cool/archive tier: what to watch out for▼

Delta retention can be complemented with Azure Storage lifecycle policies (moving old blobs into the cool/archive tier). The catch: operations such as UPDATE, MERGE, or OPTIMIZE rewrite parquet files, which resets their creation time and postpones archiving. A query against a file in the offline archive tier will also fail until the file is rehydrated.

The recommended strategy: partition by date, set delta.timeUntilArchived to match the lifecycle rules, restrict access to "old" data with a view carrying a date filter, and run maintenance commands with predicates (OPTIMIZE … WHERE ingestion_date >= …) so they do not touch archived partitions.

5.4

Data lineage: where data flows from and to

Unity Catalog captures runtime data lineage automatically — for every language, down to the column level, including links to notebooks, jobs, and dashboards. You do not have to instrument anything: queries just have to run on Unity Catalog-enabled compute and tables have to be referenced by their three-level name catalog.schema.table (access through a direct file path generates no lineage).

In Catalog Explorer you open the Lineage tab on a table and use the See Lineage Graph button for an interactive visualization: nodes are tables, arrows show the direction of flow, and the + icon expands further upstream/downstream levels. Clicking an edge shows which notebook or job created the link; the Jobs and Dashboards tabs show the table's consumers — ideal for impact analysis before a schema change.

For reporting there are two system tables:

SQL
-- the most frequently queried tables over the last week
SELECT
  source_table_full_name,
  COUNT(DISTINCT event_id) AS query_count
FROM system.access.table_lineage
WHERE event_date > CURRENT_DATE() - INTERVAL 7 DAYS
  AND source_table_full_name IS NOT NULL
GROUP BY source_table_full_name
ORDER BY query_count DESC
LIMIT 10;
ℹ️
Note: the system tables system.access.table_lineage and system.access.column_lineage keep a rolling window of 1 year; Catalog Explorer and the lineage API retain events captured after 1 September 2024 with no time limit. DESCRIBE HISTORY adds the table's version history.
⚠️
Mind the limits: lineage is not preserved when an object is renamed, tables read by path (delta.`abfss://…`) show up only as a path, and some UDFs can obscure the column-level mapping. Nodes the user does not have at least BROWSE on appear masked in the graph.

5.5

Audit logging through system tables

Who accessed what and when — that is answered by the audit log system table system.access.audit. It is configured at the account level, covers every workspace attached to the metastore, and turns a compliance investigation into an ordinary SQL query instead of searching through log files.

The key columns: event_time, user_identity, workspace_id (0 = an account-level event), service_name (e.g. unityCatalog, notebook, clusters), action_name (e.g. getTable, updatePermissions), request_params, response, and source_ip_address.

SQL
-- who accessed a specific table over the last 7 days
SELECT
  user_identity.email AS user_email,
  action_name AS access_type,
  event_time
FROM system.access.audit
WHERE request_params.full_name_arg = 'catalog.schema.table_name'
  AND action_name IN ('getTable', 'createTable', 'deleteTable')
  AND event_date > CURRENT_DATE() - INTERVAL 7 DAYS
ORDER BY event_time DESC;

-- audit of permission changes in the metastore
SELECT event_time, user_identity.email, request_params.securable_full_name, request_params.changes
FROM system.access.audit
WHERE service_name = 'unityCatalog' AND action_name = 'updatePermissions'
ORDER BY event_time DESC;
ℹ️
Note: system tables must first be enabled by an account admin; the system.access.audit table was in Public Preview when the module was written — verify the current state in the documentation. Audit logs are retained for up to 1 year; handle longer retention with an export.

The default logging does not capture the full text of the commands that were run. For a detailed forensic trail, enable verbose audit logs (Admin Settings → Advanced) — this adds the runCommand (notebooks, jobs) and commandSubmit (Databricks SQL) events. Enabling or disabling verbose logging is itself an audited event.

⚠️
Caution: verbose logs contain the command text — so potentially query parameters or hardcoded values as well. Take that into account in your security policies.

For central monitoring, logs can be delivered through Azure diagnostic settings into Log Analytics (KQL queries, dashboards, typical latency ~15 minutes), a Storage account (cheap long-term archiving), or Event Hubs (real-time streaming into a SIEM). The combination "system table for ad-hoc investigations + SIEM for continuous monitoring" covers both needs.

5.6

Designing a Delta Sharing strategy

Delta Sharing makes it possible to share live data with partners and other organizations without copying it — the recipient reads directly from your data while you keep full control over who sees what. Strategic decision number one is the choice of protocol:

FactorDatabricks-to-DatabricksOpen sharing
Recipient platformDatabricks with Unity Cataloganything (pandas, Spark, BI…)
Authenticationmanaged by the platform (sharing identifier)bearer token or OIDC federation
Shared assetstables, views, volumes, notebooks, modelstables only
Token managementnot neededexpiry + rotation required

A share is a securable object — a collection of shared assets. A recipient represents the receiving party. You can manage the whole lifecycle in SQL:

SQL
CREATE SHARE IF NOT EXISTS partner_analytics
COMMENT 'Sales analytics data for partner integration';

ALTER SHARE partner_analytics ADD TABLE catalog.schema.sales_summary;
ALTER SHARE partner_analytics ADD TABLE catalog.schema.transactions WITH HISTORY;

-- D2D recipient via the sharing identifier (the recipient finds it with: SELECT CURRENT_METASTORE())
CREATE RECIPIENT IF NOT EXISTS contoso_analytics
USING ID 'azure:westeurope:a1b2c3d4-e5f6-7890-abcd-ef1234567890';

GRANT SELECT ON SHARE partner_analytics TO RECIPIENT contoso_analytics;

-- overview and revoking
SHOW SHARES;
SHOW ALL IN SHARE partner_analytics;
REVOKE SELECT ON SHARE partner_analytics FROM RECIPIENT contoso_analytics;

When different recipients are meant to see different slices of the data, do not share the whole table — use a dynamic view with the CURRENT_RECIPIENT() function over the recipient's custom properties:

SQL
ALTER RECIPIENT regional_partner SET PROPERTIES ('country_region' = 'US');

CREATE VIEW catalog.schema.regional_sales AS
SELECT * FROM catalog.schema.all_sales
WHERE region = CURRENT_RECIPIENT('country_region');
💡
Tip: with open sharing, set token expiry at the metastore level and restrict sensitive shares with IP access lists (up to 100 IP/CIDR values per recipient). Better than token rotation in the long run is OIDC federation — short-lived OAuth tokens exchanged for a JWT from the recipient's identity provider.
⚠️
Caution: sharing a whole schema (ADD SCHEMA) automatically includes future tables in it as well. Convenient, but dangerous — a new internal table in the schema flows out to the partner with no further approval. Share only the necessary minimum.

Track the activity in the audit log: the deltaSharingQueriedTable event (open sharing) and generateTemporaryTableCredential (D2D). Once you introduce a monthly review of active recipients, a check of the shares' contents, and tracking of failed access attempts, your governance loop is closed. Delegate administration through specific privileges (CREATE SHARE, CREATE RECIPIENT, SET SHARE PERMISSION) to groups of data stewards — not to blanket metastore admins.
