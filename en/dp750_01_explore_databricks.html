1.1

What Azure Databricks is and how a workspace is created

Azure Databricks is a cloud analytics platform built on Apache Spark and operated as a first-party service directly in Azure — you pay for it through your Azure subscription, sign in with Microsoft Entra ID, and it integrates with Azure Data Lake Storage, Key Vault, and Power BI. So it is not "Spark you have to install yourself", but a managed platform covering the entire data lifecycle: ingestion, transformation, SQL analytics, and machine learning.

The basic unit of deployment is a workspace — an isolated environment for a defined group of users where notebooks, clusters, jobs, and data live. You create a workspace in the Azure portal, or in an automated way through an ARM/Bicep/Terraform template, the Azure CLI, or PowerShell:

BASH
# create a workspace with the Azure CLI
az databricks workspace create \
    --resource-group rg-dp750 \
    --name dbw-citymoves \
    --location westeurope \
    --sku premium
POWERSHELL
# create a workspace with Azure PowerShell
New-AzDatabricksWorkspace -Name dbw-citymoves `
    -ResourceGroupName rg-dp750 `
    -Location westeurope `
    -ManagedResourceGroupName rg-dbw-managed `
    -Sku premium

When creating one you choose a region, a pricing tier, and — newly — a workspace type:

ParameterOptionsNote
Pricing tierPremium / Trial (14 days)Premium = RBAC, Unity Catalog, Databricks SQL, serverless, Mosaic AI
Workspace typeServerless / Hybrid (Classic)Serverless: Databricks manages both compute and storage — recommended for most cases; Hybrid: compute in your own subscription (custom network, on-premises connectivity)
Managed Resource Groupoptional nameAzure automatically manages the workspace infrastructure inside it
⚠️
Caution: the Standard tier no longer exists for new workspaces — since April 2026 every new workspace is created as Premium. You will still run into Standard in older materials and StackOverflow answers; for the exam and for practice, count on Premium only.
💡
Tip: for self-study there is a Free Edition — no time limit and no credit card, with daily limits and without classic compute. You will find a comparison with the trial version in the Databricks documentation.
1.2

Finding your way around the workspace UI

From the Azure portal you get into the workspace with the Launch Workspace button. The workspace UI is the web interface where you create and manage every object — notebooks, queries, clusters, jobs. The left sidebar has a shared part (Workspace, Recents, Catalog, Jobs & Pipelines, Compute, Marketplace) and then sections by product area:

AreaSidebar items
SQLSQL Editor, Queries, Dashboards, Genie, Alerts, Query History, SQL Warehouses
Data EngineeringJob Runs, Data Ingestion
Machine LearningPlayground, Experiments, Features, Models, Serving

The + New button is the universal entry point for creating objects (notebook, query, job, pipeline, experiment) as well as compute resources (cluster, SQL warehouse). The search box at the top searches everything in one place: notebooks, tables registered in Unity Catalog, dashboards, jobs, and repositories.

Part of the platform is the Databricks Assistant — replaced in the current UI by its successor agentic product Genie Code — an AI pair programmer built right into the notebook, dashboards, and file editor. It generates, explains, and fixes code, diagnoses job failures, and can answer questions in natural language. Thanks to metadata from Unity Catalog it knows the names of your tables and columns, so its suggestions match your data rather than generic examples.

ℹ️
Note: Genie Code also has an Agent mode that can autonomously plan and carry out multi-step tasks (data engineering, data science, building dashboards). The feature set is evolving quickly — verify the exact state in the documentation.
💡
Tip: each user switches the UI language for themselves: user name in the top right → Settings → the Preferences tab. In class we recommend leaving it in English — it matches the documentation and the exam questions.

1.3

Three workloads on one platform

Azure Databricks covers three main kinds of work with data over one copy of the data and one governance model. That is the whole point of the lakehouse approach: the data engineer, the analyst, and the data scientist all work over the same Delta tables — nothing is copied into a separate DWH or an ML sandbox.

Data engineering is the core of this course: collaborative development of data pipelines on Spark in Python, R, Scala, and SQL — from exploring data through transformations to orchestrating production jobs. The SQL workload targets analysts: SQL Editor, dashboards, and automatic visualizations running on SQL warehouses — compute optimized purely for SQL queries. The machine learning workload adds MLflow for managing the model lifecycle, support for frameworks such as TensorFlow, PyTorch, and scikit-learn, and tooling for generative AI.

ℹ️
Note: Databricks SQL and SQL warehouses are Premium tier features. Since new workspaces are always Premium today, in practice you will only hit this limit on historical Standard workspaces.
1.4

Key concepts: architecture, compute, notebooks

Azure Databricks has a two-layer architecture. The control plane is the internal layer managed by Microsoft/Databricks — it runs the workspace UI, the REST API, job orchestration, and metadata. The compute plane is the layer that actually processes data: with classic compute the cluster virtual machines run in your Azure subscription (you will see them in the managed resource group), while with serverless compute they run in the Databricks subscription and nothing shows up in yours.

A cluster is the compute engine: the driver node coordinates execution and the worker nodes perform the distributed computation; the number of workers can be fixed or driven by autoscaling. Alongside clusters there are SQL warehouses — compute separated from storage and optimized for SQL (serverless, pro, and classic variants). Chapter 2 is devoted entirely to choosing and configuring compute.

A notebook is an interactive document combining runnable code, visualizations, and text. It is made up of code cells and Markdown cells; languages can be mixed within a single notebook using magic commands:

PYTHON
# cell 1 — the default notebook language is Python
df = spark.read.csv("/Volumes/main/default/lab_data/routes.csv",
                    header=True, inferSchema=True)
display(df)

# cell 2 — switch to SQL with a magic command
%sql
SELECT route_type, COUNT(*) AS total
FROM csv.`/Volumes/main/default/lab_data/routes.csv`
GROUP BY route_type;

# cell 3 — documentation in Markdown
%md
## CityMoves Transit — exploring the route data

Code on a cluster is executed by the Databricks Runtime — a modified Apache Spark build with performance optimizations and preinstalled libraries. Runtime versions go through a lifecycle (Legacy → Deprecated → End of Support → End of Life); production sticks to LTS versions. Orchestration is handled by Lakeflow Jobs: a job is a container for one or more tasks (notebook, Spark job, external code…) triggered on a schedule, by an event, or manually.

DBFS vs. volumes — where files belong today▼

DBFS (Databricks File System) is a historical abstraction over object storage, available through dbfs:/ paths. Its root (the DBFS root) is considered legacy today: it has no governance through Unity Catalog and Databricks recommends other mechanisms for storing data. Volumes, on the other hand, are Unity Catalog objects for non-tabular data (CSV files, images, models…) — with full access control, auditing, and uniform paths /Volumes/<catalog>/<schema>/<volume>/.

DBFS root (legacy)UC volume
Governancenone (workspace-level)Unity Catalog: grants, audit, lineage
Pathdbfs:/FileStore/…/Volumes/catalog/schema/volume/…
Recommendationdo not use for new datathe standard for files in the lakehouse

If you are coming from the older DP-203 course: everywhere you used to upload into /FileStore, you upload into a volume today. Verify the exact state of the DBFS restrictions in the documentation.

💡
Tip: notebooks support version control, scheduling as a job, and simultaneous editing by several users. In practice it is common for the same notebook to serve both for exploring data and as a production task in a job — the boundary between "ad-hoc" and "production" is deliberately low here.

1.5

Lakehouse and Delta Lake

A lakehouse is an architecture combining the cheap, scalable storage of a data lake with the properties of a data warehouse — transactions, schemas, and governance. What makes it possible is Delta Lake: an open-source storage framework that adds a transactional layer on top of object storage (Azure Data Lake Storage). Data is typically organized into the layers of the so-called medallion architecture:

Classic data lakes suffered from inconsistent data, partial writes, and concurrent access problems. Delta Lake solves this with four pillars:

  • ACID transactions — reliable reads and writes, no half-written files after a failed job.
  • Scalable metadata — tables with billions of files without degrading performance.
  • Versioning and time travel — query a historical state of a table, roll back after a bad write.
  • Unified batch and streaming — the same table serves real-time ingestion and historical batches.

On top of this foundation, Delta tables provide the ordinary table abstraction for both SQL and the DataFrame API. From the documentation: "Delta tables are the default table format in Azure Databricks" — when you create a table in Databricks and do not say otherwise, it is Delta:

SQL
-- CREATE TABLE without USING = automatically Delta
CREATE TABLE main.default.routes AS
SELECT * FROM read_files('/Volumes/main/default/lab_data/routes.csv');

-- history of table changes (time travel)
DESCRIBE HISTORY main.default.routes;

-- query an older version
SELECT * FROM main.default.routes VERSION AS OF 2;
⚠️
Caution: anyone expecting "lakehouse" to be just a marketing name for a data lake misses the main difference: without the Delta Lake transaction layer you have no guarantee that two concurrent writes will not break the table. It is precisely the ACID properties that turn a lake into a usable warehouse.

1.6

Data governance: Unity Catalog and Microsoft Purview

Data in organizations tends to be fragmented across databases, warehouses, and lakes, in different formats — and besides tables you also need to manage files, ML models, notebooks, and dashboards. Unity Catalog answers this with centralized management of access, discovery, lineage, audit logs, and quality monitoring across all workspaces in a region.

At the top of the hierarchy is the metastore — a container of metadata and permissions, typically one per region, shared by several workspaces. Data objects are addressed at three levels:

SQL
-- three levels: catalog.schema.object
SELECT * FROM citymoves.transit.routes;

-- permissions are managed with ANSI SQL grants
GRANT CREATE TABLE ON SCHEMA citymoves.transit TO `data-engineers`;
GRANT SELECT ON TABLE citymoves.transit.routes TO `analysts`;
  • Catalog — the top level, typically per team or environment (dev/test/prod).
  • Schema (database) — a finer split by project or use case.
  • Objects — tables (managed/external), views, volumes, functions, and ML models.

For managed tables, Unity Catalog manages both governance and the storage itself (Delta Lake as the default format, with Apache Iceberg also supported). For external tables it manages only access from Databricks — the data lifecycle is outside and the format may also be CSV, JSON, or Parquet. Permissions can be granted from the metastore through catalog and schema all the way down to rows and columns; for discovery there is Catalog Explorer with tags, comments, AI-generated descriptions, and lineage down to the column level.

ℹ️
Note: in most accounts Unity Catalog is enabled automatically when a workspace is created today — you do not have to install anything, only fine-tune the optional configuration if needed. Verify the exact state in your tenant in the admin console.

Microsoft Purview then handles governance beyond Databricks: it is a company-wide catalog covering on-premises systems, multiple clouds, and SaaS platforms. Its integration with Unity Catalog can ingest lakehouse metadata into the Purview Data Map, so you get one view of your data across the whole environment.

What exactly a Purview scan of Azure Databricks can do▼
  • Scan workspaces on public as well as private networks (managed integration runtime).
  • Scan the whole Unity Catalog metastore, or only selected catalogs; on top of that the workspace-level Hive metastore.
  • Extract metadata: metastore, catalogs, schemas, tables/views, columns.
  • Automatically classify sensitive data using built-in as well as custom rules.
  • Track lineage — how data is transformed and moved across systems, including Databricks.
  • Run on demand or on a schedule (daily/weekly/monthly).
✓
Summary: Unity Catalog = governance inside Databricks (access, lineage, auditing over data and AI assets). Purview = governance across the whole organization (catalog, classification, compliance). In practice they complement each other — Purview pulls metadata from Unity Catalog.
