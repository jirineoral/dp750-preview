Ingest data into Unity Catalog

Lakeflow Connect, notebooks, SQL methods, CDC, Structured Streaming, Auto Loader, and declarative pipelines
🗂 Loading data into Unity Catalog, ETL and pipelines

Chapter objectives

  • Choose a suitable ingestion route into Unity Catalog based on the source type and the required latency
  • Configure Lakeflow Connect with managed connectors for SaaS applications and databases
  • Load batch and streaming data in a notebook with the DataFrame API and write it into Delta tables
  • Use the SQL statements COPY INTO and CTAS for idempotent file loading
  • Set up Auto Loader with exactly-once semantics and automatic schema inference
7.1

Lakeflow Connect: managed connectors

Before we get into the individual techniques, let us look at the overall map. Several ingestion routes lead into Unity Catalog and each has its sweet spot: managed connectors for SaaS and databases, a notebook with custom code for anything non-standard, SQL statements for one-off and repeated file loading, Auto Loader for files that keep arriving, and Structured Streaming for message buses. All the routes end at the same point — in the Delta tables of the bronze layer governed by Unity Catalog.

Lakeflow Connect is a set of managed connectors — instead of writing extraction code you just configure a pipeline, through the UI, Asset Bundles (today Declarative Automation Bundles, see section 12.4), a notebook, or the CLI — and Databricks takes care of extraction, staging, and writing into streaming tables. The connectors fall into three categories:

Connector typeSourcesMechanism
SaaS connectorsSalesforce, HubSpot, Jira, Workdayextraction directly through the source API
Database (CDC)SQL Server, MySQL, PostgreSQLan ingestion gateway reads changes from the transaction log (binlog)
Query-baseddatabases without CDCscheduled queries with a cursor column (increasing timestamp/ID), no gateway

Every ingestion pipeline is made up of three components: a connection (stored credentials and endpoint — created once, used repeatedly), an ingestion definition (which tables and where in Unity Catalog), and a schedule. Database connectors additionally create an ingestion gateway, which continuously pulls changes out of the source database.

YAML
# ingestion definition in Declarative Automation Bundles (formerly Asset Bundles)
resources:
  pipelines:
    pipeline_sqlserver:
      name: customer-orders-pipeline
      catalog: sales
      schema: bronze
      ingestion_definition:
        # connection_name points to the UC connection with the source credentials
        connection_name: sqlserver_prod_connection
        # database connectors also need a gateway pipeline with the source changes
        ingestion_gateway_id: ${resources.pipelines.gateway_sqlserver.id}
        objects:
          - table:
              source_schema: dbo
              source_table: orders
              destination_catalog: sales
              destination_schema: bronze

The key choices during configuration: SCD type 1 (the target always reflects the current state of the source — an update overwrites the row) vs. SCD type 2 (history is preserved and the table gets the columns __START_AT and __END_AT). Then column selection through include_columns / exclude_columns and the option of a full refresh when incremental processing cannot recover from a schema change.

💡
Tip: a single pipeline can write the same source table into several target catalogs and schemas — useful when both marketing and sales need their own copy of the data under their own governance. You do not have to build a second pipeline.
⚠️
Caution: with include_columns, newly added columns in the source do not reach the target automatically. With exclude_columns it is the other way round — new columns are added automatically. Choose according to whether you want to govern the schema or let it evolve. The connector offering is expanding quickly — verify the current list and status (preview/GA) in the documentation.

7.2

Ingestion in a notebook: spark.read and the DataFrame API

When no managed connector exists or you need custom logic, you reach for a notebook. The basis of batch ingestion is spark.read — it returns a DataFrame, a distributed collection of data organized into named columns.

PYTHON
df = (spark.read
    .format("csv")
    .option("header", "true")
    .option("inferSchema", "true")
    .load("/Volumes/catalog/schema/volume/data.csv"))

# write into a Delta table in Unity Catalog
df.write.mode("overwrite").saveAsTable("catalog.schema.table_name")

The same pattern loads JSON, Parquet, and XML (there the rowTag option is mandatory, telling Spark which XML element corresponds to one row). The write always ends in the Delta format — the default in Databricks, giving ACID transactions and time travel. The behavior when the table already exists is controlled by mode():

ModeBehavior
overwritecompletely replaces the table contents
appendadds rows to the existing ones
ignoredoes nothing if the table exists
error (default)throws an exception if the table exists

For relational sources without a Lakeflow connector, JDBC does the job. Never write credentials into the notebook — they belong in Databricks secrets:

PYTHON
df_jdbc = (spark.read
    .format("jdbc")
    .option("url", "jdbc:sqlserver://server.database.windows.net:1433;database=mydb")
    .option("dbtable", "schema.tablename")
    .option("user", dbutils.secrets.get(scope="jdbc", key="username"))
    .option("password", dbutils.secrets.get(scope="jdbc", key="password"))
    .load())
💡
Tip: instead of a table name you can put a subquery into the dbtable option — the filter is then executed on the database side (pushdown) and only the relevant rows travel over the network. On large source tables that is the difference between minutes and hours.
Semi-structured data and the VARIANT type▼

When the schema of JSON records differs between rows or evolves over time, you do not have to enforce it at ingestion. The VARIANT data type stores the whole nested structure and you can query specific fields later:

PYTHON
from pyspark.sql.functions import parse_json, variant_get, col

df = spark.read.text("/path/to/data.json")
df_variant = df.select(parse_json(col("value")).alias("data"))
df_variant.select(variant_get(col("data"), "$.customer.name", "string")).display()

That is exactly the "schema-on-read" pattern for the bronze layer: raw data in without loss, structure dealt with in silver.

7.3

SQL methods: CTAS, CREATE OR REPLACE, and COPY INTO

If you prefer declarative SQL to procedural code, three statements are available. They differ mainly in what they do with an existing table — and that is exactly what you have to remember about them.

CTAS (CREATE TABLE AS SELECT) combines creating a table and filling it with data in one step. The schema is derived from the query result. For reading from files it is combined with the table-valued function read_files:

SQL
CREATE TABLE catalog.schema.sales_data AS
SELECT * FROM read_files(
    '/Volumes/catalog/schema/volume/sales/*.parquet',
    format => 'parquet'
);

CREATE OR REPLACE TABLE replaces the table completely, but unlike DROP + CREATE it preserves the table history, the granted permissions, row filters, and column masks. Downstream consumers notice nothing. It suits periodic full refreshes.

COPY INTO is meant for repeatedly appending files: it loads files from cloud storage and appends them to an existing table. Its key property is idempotence — files already loaded are skipped automatically, even if you run the statement again:

SQL
-- the target table must exist beforehand
CREATE TABLE IF NOT EXISTS catalog.schema.events (
    event_id STRING, event_type STRING,
    event_timestamp TIMESTAMP, payload STRING);

COPY INTO catalog.schema.events
FROM '/Volumes/catalog/schema/volume/events/'
FILEFORMAT = JSON
FORMAT_OPTIONS ('multiline' = 'true');

You narrow the file selection with PATTERN (a glob) or FILES (specific names). The option COPY_OPTIONS ('mergeSchema' = 'true') allows the table schema to evolve, and VALIDATE ALL checks parsability and schema conformance without loading anything.

MethodBest forBehavior
CTASthe first load, one-off migrationscreates a new table; fails if it exists
CREATE OR REPLACEperiodic full refreshreplaces the whole table; preserves permissions
COPY INTOcontinuously adding filesappend; skips already loaded files
⚠️
Caution: COPY INTO scales well into the thousands of files. If the source will grow into millions of files, the documentation recommends Auto Loader (section 7.6) — it discovers files more efficiently and without the overhead of directory listing. Anyone expecting CTAS ... IF NOT EXISTS to "top up" the table will be surprised: the statement is simply skipped as a whole.
7.4

CDC feeds and the AUTO CDC API

When the source system generates millions of transactions a day, full reloads stop making sense. Change data capture (CDC) transfers only the changes — every feed record carries the data columns, the operation type (INSERT/UPDATE/DELETE), and a sequencing column (a timestamp or an ordinal number) that determines the order of the changes.

Applying a CDC feed by hand is full of pitfalls: out-of-order events, deduplication, deletes. The AUTO CDC API in Lakeflow Spark Declarative Pipelines handles this for you — you create the target streaming table, define a flow, and choose the SCD type:

SQL
CREATE OR REFRESH STREAMING TABLE employees;

CREATE FLOW employees_cdc_flow
AS AUTO CDC INTO employees
FROM stream(bronze.employee_changes)
KEYS (employee_id)
APPLY AS DELETE WHEN operation = 'DELETE'
SEQUENCE BY sequence_num
COLUMNS * EXCEPT (operation, sequence_num)
STORED AS SCD TYPE 1;
PYTHON
from pyspark import pipelines as dp
from pyspark.sql.functions import col, expr

dp.create_streaming_table("employees")

dp.create_auto_cdc_flow(
    target="employees",
    source="employees_cdf",
    keys=["employee_id"],
    sequence_by=col("sequence_num"),
    apply_as_deletes=expr("operation = 'DELETE'"),
    except_column_list=["operation", "sequence_num"],
    stored_as_scd_type=1
)

The choice of SCD type decides what happens to the previous version of a record:

  • SCD Type 1 — an update overwrites the row; an employee moves from Seattle to Portland and Seattle disappears from the table.
  • SCD Type 2 — the history stays: the Seattle record gets an __END_AT and a new row with Portland is added. With TRACK HISTORY ON * EXCEPT (...) you can specify which columns trigger a new historical version at all.
ℹ️
Note: a late-arriving older update (a lower value in SEQUENCE BY) is ignored automatically by the API if a newer one has already been applied. Without that you would be writing your own merge logic with version comparisons. For sources sending partial updates (only the changed columns) there is IGNORE NULL UPDATES — NULLs in the incoming record then do not overwrite existing values.

7.5

Spark Structured Streaming

Structured Streaming treats incoming data as an unbounded table that keeps growing. The API is the same as for batch — you just write spark.readStream instead of spark.read and writeStream instead of write. What has already been processed is tracked by a checkpoint.

For Azure Event Hubs the simplest route is through its Kafka-compatible endpoint — the same connector as for Kafka, only with SASL authentication through a connection string from secrets. There is also a native eventhubs connector (the payload is then in the body column instead of value).

PYTHON
# reading from a Kafka topic and writing into a Delta table
df_stream = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker-server:9092")
    .option("subscribe", "sensor-readings")
    .option("startingOffsets", "latest")
    .load())

(df_stream.writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/checkpoints/sensor-ingestion")
    .toTable("iot.bronze.sensor_readings"))

The Kafka connector returns a standard schema (key, value, topic, partition, offset, timestamp) — the values are binary, so you typically cast them to string and parse them with from_json. The processing frequency is governed by the trigger: with no trigger the stream runs continuously, processingTime="10 seconds" processes at intervals, and availableNow=True processes everything available and finishes — ideal for scheduled jobs.

⚠️
Caution: every streaming query must have its own unique checkpoint location. Sharing a checkpoint between two streams leads to processing errors. And no lifecycle policies on checkpoint directories — deleting a checkpoint means starting from zero.
Monitoring streaming queries▼

You can see active streams in the Spark UI on the Structured Streaming tab. Programmatically: query.isActive, query.status, query.recentProgress. In production, wrap query.awaitTermination() in try/except and set up alerting on stream lag (the lag metrics in the progress report). A common misunderstanding: startingOffsets applies only to the very first start — once a checkpoint exists, processing continues from it and the option is ignored.

7.6

Auto Loader: cloudFiles and exactly-once

Auto Loader is a Structured Streaming source specialized in files: it watches a location in cloud storage and incrementally processes newly arriving files. It keeps the state of already processed files itself, so every file is ingested exactly once — no manual tracking, no duplicates after a restart.

Detection of new files runs in two modes: directory listing (a periodic listing of the directory, works with no further configuration) and file notification (notifications from the cloud when a file arrives — lower latency and API cost for large workloads; recommended with file events on a Unity Catalog external location).

PYTHON
(spark.readStream
  .format("cloudFiles")
  .option("cloudFiles.format", "json")
  .option("cloudFiles.schemaLocation", schema_path)
  .option("cloudFiles.inferColumnTypes", "true")
  .load("abfss://container@storage.dfs.core.windows.net/incoming/orders/")
  .writeStream
  .option("checkpointLocation", checkpoint_path)
  .trigger(availableNow=True)
  .toTable("sales.bronze.orders"))
SQL
-- a streaming table in a declarative pipeline: STREAM enables Auto Loader
CREATE OR REFRESH STREAMING TABLE bronze_orders
AS SELECT * FROM STREAM read_files(
  'abfss://container@storage.dfs.core.windows.net/incoming/orders/',
  format => 'json',
  schemaHints => 'order_id INT, amount DECIMAL(10,2)'
)

Schema inference: Auto Loader can infer the schema itself and store it in the schemaLocation. For JSON and CSV it infers everything as string by default — you enable automatic types with cloudFiles.inferColumnTypes and force specific columns with cloudFiles.schemaHints. When new columns appear in the source, the outcome is decided by cloudFiles.schemaEvolutionMode:

ModeBehavior
addNewColumns (default without a schema)the stream fails, the schema is extended, and it continues after a restart
rescuethe schema does not change, new columns land in _rescued_data, the stream does not fail
failOnNewColumnsthe stream fails and will not start until you adjust the schema
none (default with a schema)new columns are ignored
addNewColumnsWithTypeWideninglike addNewColumns + widening of compatible types (INT → LONG)

The _rescued_data column is a safety net: it captures data that does not match the schema (type mismatches, unexpected columns), so nothing is silently lost.

💡
Tip: you can list the state of ingested files at any time: SELECT * FROM cloud_files_state('/path/to/checkpoint'). And through the hidden _metadata column you get file_path, file_name, and file_modification_time for every row — very useful in the bronze layer for tracing the origin of the data.
Controlling throughput at large volumes▼

To stop a single micro-batch swallowing the whole backlog, limit it: cloudFiles.maxFilesPerTrigger (e.g. 1000 files) or cloudFiles.maxBytesPerTrigger (e.g. 1g). Track progress through the numFilesOutstanding and numBytesOutstanding metrics in the streaming dashboard. The schema location and the checkpoint can be the same directory, but keeping them apart pays off — you can reset the stream without losing the inferred schema.

7.7

Declarative pipelines as a framework over ingestion

The previous techniques are the building blocks; a declarative pipeline is the framework that assembles them into a complete pipeline. You declare what you want (tables and their sources in SQL or Python) and the framework handles how: execution order, parallelism, retries on failure, checkpoints, and incremental processing. The target of ingestion is typically a streaming table — a Delta table with built-in streaming support and an exactly-once guarantee.

PYTHON
from pyspark import pipelines as dp

# a streaming table defined by a decorator; the pipeline handles checkpoints
@dp.table
def orders_bronze():
    return (
        spark.readStream.format("cloudFiles")
            .option("cloudFiles.format", "json")
            .load("abfss://container@storage.dfs.core.windows.net/incoming/orders/")
    )

Besides the default flow (created automatically with the table) you can define explicit flows — for example two regional sources feeding one table without a UNION. You then add a new source with a new flow, without touching the existing ones or triggering a full refresh:

SQL
CREATE OR REFRESH STREAMING TABLE orders_us;

CREATE FLOW orders_west_flow
AS INSERT INTO orders_us BY NAME
SELECT * FROM STREAM(orders_west);

CREATE FLOW orders_east_flow
AS INSERT INTO orders_us BY NAME
SELECT * FROM STREAM(orders_east);

Pipelines can read from message buses too (read_kafka, Event Hubs through the Kafka interface) and for semi-structured JSON they offer from_json with automatic schema inference and evolution (schema NULL + schemaLocationKey). Monitoring is provided by the event log and the dependency DAG in the Lakeflow Pipelines Editor.

⚠️
Caution: the name of a flow identifies its streaming checkpoint. Rename a flow and the checkpoint does not follow — the renamed flow starts processing from the beginning as a new one. With large sources that means a complete re-ingest.
✓
Summary: Lakeflow Connect for managed sources · a notebook for custom logic · COPY INTO/CTAS for SQL work with files · AUTO CDC for change feeds · Structured Streaming for message buses · Auto Loader for growing file directories · a declarative pipeline as the orchestration framework over all of it. Declarative pipelines are covered in detail in section 10.6.
